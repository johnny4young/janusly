# Agent Notes — Janusly

Operational invariants only — how to run the project, what not to break. Keep temporary planning and status notes outside source comments and release-facing docs.

Janusly = the AI operator for business workflows. Internal packages live under the `@janusly/*` scope. Everywhere user-facing (UI brand-mark, page titles, marketing copy, `/ai/*` responses) say **Janusly**.

- **Stack baselines:** Node.js **24**, TypeScript 6, React 19, Vite 8 (Rolldown), Tailwind 4 (CSS-first via `@theme` + `@tailwindcss/vite`), Vitest 4, Zod 4, Drizzle 1.0 RC, Postgres 18, Redis 8, OpenAI SDK 6.
- **Design system:** Workflow palette (Cobalt `#245BFF` + Cyan `#06B6D4` + green/amber/red status). Tokens in `apps/web/src/index.css` (`@theme { --color-we-* }` + `:root` aliases). No inline hex.
- **Tailwind 4 is CSS-first.** No `tailwind.config.ts` or `postcss.config.js`. The plugin runs through `@tailwindcss/vite()` in `apps/web/vite.config.ts`.
- **Vite 8 / Rolldown:** `build.rollupOptions.output.manualChunks` must be a function, not an object literal.
- **Zod 4:** `z.record(z.string(), z.unknown())` — two-arg form.
- **Auth:** dev-mode uses `x-org-id` and `x-user-id` headers, allowed automatically when Supabase is unset **and** `NODE_ENV !== "production"`. Production without Supabase requires explicit `ALLOW_DEV_AUTH_HEADERS=true` or the API refuses to start. The `dev-headers` mode falls back to the `admin` role only when no `org_members` row exists; `service-token` mode does **not** auto-grant admin.
- **Human form resume tokens:** `human_form` nodes pause like `approval` but resume with structured input as the node output. Waiting metadata includes an HMAC-signed resume token from `packages/engine/src/secrets.ts`; production must provide a dedicated `JANUSLY_RESUME_TOKEN_SECRET` (do not reuse `JANUSLY_API_SERVICE_TOKEN`), while dev can use the local fallback. Tokens bind to org/run/node/purpose and expire after seven days. `/resume` validates the token, validates submitted input against the node's JSON-schema subset, and completes only a still-`waiting` node so replayed submissions cannot overwrite output or enqueue downstream work twice.
- **Org config:** `org_configs` is only for tenant runtime settings from the closed catalog in `packages/data/src/orgConfigRepo.ts` (AI provider/model/limits, outbound HTTP bounds, safe email delivery posture, run/subworkflow policy). Never store secrets, tokens, API keys, database URLs, Redis URLs, Supabase keys, service tokens, arbitrary env vars, or workflow secret values there. Secret material belongs in env/vault-backed `credentials.secret_ref`. New config keys must be typed (`string`/`number`/`boolean`), category-scoped (`ai`/`http`/`email`/`runs` unless the catalog intentionally grows), validated before insert/update, audited via the API, and rejected by the forbidden-name/value guards if they look like credentials.
- **HTTP/SSRF:** `ALLOW_PRIVATE_HTTP_TARGETS=false` blocks localhost/private/link-local for `http` nodes and the `http.request` tool. The validated DNS resolution is pinned for the actual TCP connect via an `undici.Agent` `connect.lookup` hook, so DNS rebinding (public IP at validation, private IP at connect time — e.g. `169.254.169.254` AWS metadata) cannot redirect the connect to a private target. Don't unwind the pinned dispatcher path in `packages/engine/src/http-policy.ts`.
- **Rate limiter:** API rate-limit state lives in Redis (`apps/api/src/redis.ts` + `apps/api/src/rate-limit.ts`) so counts are shared across all API replicas. Backed by `INCR` + `PEXPIRE` with a `janusly:rate:<name>:<orgId>` key. Fails **open** with a `[rate-limit]` warn log when Redis is unreachable — never fail closed; an AI Studio outage during a Redis blip is worse UX than a brief over-limit window. Don't reintroduce the in-memory `Map` fallback.
- **Usage events:** every LLM call writes one row to `usage_events` from the chokepoint `LlmClient.generateText`. The recorder is registered process-globally via `setUsageRecorder(recordUsage)` at api + worker boot; `packages/ai` itself stays DB-agnostic. `metric: "llm.completion"`, `quantity: totalTokens`, `metadata: { provider, model, inputTokens, outputTokens, latencyMs, costUsd, nodeId, mode, aiError }`. Cost is computed from `packages/ai/src/pricing.ts` (defaults + `JANUSLY_LLM_PRICE_<MODEL>` env override); unknown models record `costUsd: null`. Recorder failures are caught and dropped — telemetry must never break an LLM call. Don't bypass the chokepoint by calling `aiGenerateText` directly from outside `packages/ai`. Engine-side `orgId` plumbs through `NodeContext.orgId`, populated once per node execution by `executeNode` via `getRunOrgId(runId)`. The runtime's router-decision and improvement-evaluation paths use a sister helper, `getRunMetadata(runId)` (`packages/engine/src/persistence.ts`), loaded once per `executeQueuedNode` call — same pattern, but returns `{ orgId, workflowVersionId, workflowId, createdBy }` (joined through `workflow_versions`). Don't read `orgId` / `workflowId` off the loose `RunContext` bag for routing-stats or improvement writes; both paths go through `getRunMetadata` so the writes are structured-org-scoped instead of silently no-op'ing.
- **AI integration:** every AI surface (`/ai/generate-workflow`, `/ai/explain-workflow`, `/ai/review-workflow`, `/ai/suggest-improvement`, `/ai/patch-workflow`, `/ai/explain-run`, the `agent` planner `"openai"`, the `ai` step type) routes through the provider-neutral `LlmClient` in `packages/ai/src/llm-client.ts` (built on the Vercel AI SDK). Env still supplies provider API keys; `org_configs` may override safe tenant-level provider/model/limits before the API or engine creates the client. The runtime registry still contains `openai` + `anthropic` for compatibility and future expansion, but **the supported operating posture is Anthropic-only for AI surfaces until explicit new direction** (`anthropic/claude-haiku-4-5-20251001`). Production deployments, tenant config, demos, evals, and release smoke should use `ai.provider=anthropic` / `JANUSLY_LLM_PROVIDER=anthropic`. Treat OpenAI / Mistral / Ollama as unverified and do not switch a tenant's `ai.provider` or per-call model override away from Anthropic unless product explicitly re-opens that provider and a verification plan exists. The currently-known blocker on OpenAI is the `oneOf` strict-mode rejection on `/ai/generate-workflow`; the patch route keeps provider-safe schema constraints for future compatibility, but OpenAI is not a supported runtime target right now. Per-call overrides go through the `model` field on workflow nodes / API request bodies: a bare id uses the configured provider; `"<provider>/<model>"` (e.g. `"anthropic/claude-haiku-4-5-20251001"`) overrides provider for that one call, but supported use is Anthropic-only until further notice. Adding a new provider (Ollama, Mistral, Google) is a four-field entry in the `PROVIDERS` registry — no other code changes; see `packages/ai/README.md`. Every AI path has a deterministic fallback **and** wraps the SDK invocation in try/catch — on any failure (quota, rate, network, bad output, unknown provider, missing key for an override) the response stays `{ mode: "fallback", aiError: "<reason>", ... }` with the local content attached. Never break the fallback or remove the try/catch. `GET /ai/health` reports `enabled`, `provider`, and `model` reflecting the current tenant runtime config. `/ai/generate-workflow` stays capped at 11 Anthropic grammar branches: `noop`, `http`, `transform`, `condition`, `ai`, `tool`, `agent`, `router`, `approval`, `human_form`, and `loop`. Advanced/operator-only types (`multi_agent`, `schedule`, `webhook`, `wait_until`, `subworkflow`, `parallel_fork`, `join`, `router_llm`, `agent_reflection`) are emitted as `noop` placeholders and promoted in the Inspector. `/ai/generate-workflow` calls `llm.generateObject({ schema: AiGenerationWorkflowSchema })` so the model returns one of the Anthropic-safe node shapes directly — no `JSON.parse` + looser pre-pass needed. The route still runs a small `sanitizeAiWorkflow` step (`apps/api/src/index.ts`) that filters edge `condition` strings and `condition`-node expressions through `validateExpression` (Janusly's limited grammar). Don't drop the sanitize step — `WorkflowSchema` + `validateWorkflow` remain the runtime gate after AI generation; the engine's expression evaluator is stricter than Zod's `z.string()`. Schema-validation failures and sanitize throws both flow through the route's existing try/catch into `{ mode: "fallback", aiError, ... }`. **Two-pass promotion (Pass 2):** `/ai/generate-workflow` runs an optional second pass between `llm.generateObject` and `sanitizeAiWorkflow` via `promoteNoopPlaceholders` in `packages/ai/src/promote-noop.ts`. Detection is **id-prefix heuristic + multi-family lookup**: each wired family in `PROMOTE_FAMILIES` (`packages/ai/src/promote-noop.ts`) pairs a list of id prefixes with a typed target node type. Today two families are wired — `wait_until` (`wait_*` / `sleep_*` / `pause_*` / `delay_*`) and `schedule` (`schedule_*` / `cron_*` / `every_*` / `daily_*` / `weekly_*` / `monthly_*` / `hourly_*`). Matching is case-insensitive and requires a non-alphanumeric separator directly after the prefix (so `wait_3_days` matches but `waiting_room` does not). When a noop matches a family, Pass 2 calls the corresponding typed schema (`AiWaitUntilConfigSchema` or `AiScheduleConfigSchema` — single-shape, provider-strict-safe: no `oneOf`, no `propertyNames`, no open `additionalProperties`) with the operator's verbatim prompt as the hint and flips the noop's `type` to the target with the typed config. The Pass-1 system prompt teaches the LLM the id conventions; we did NOT use a Pass-1 `config.promote` flag because the model empirically ignored that instruction and kept emitting empty configs — id-based detection is the reliable signal because descriptive ids are what the LLM picks naturally. Per-noop failures (LLM throws, schema rejects, whitespace-only duration, non-cron string, empty operator prompt) degrade silently — the offending noop stays unpromoted and the response stays `mode: "ai"` with `promotionsSucceeded < promotionAttempts` surfaced in `audit_logs.metadata`. Audit metadata also carries `promotionsByFamily: { wait_until: { attempts, succeeded }, schedule: { attempts, succeeded } }` so operators can see per-family exercise rates. Pass 2 fires N additional LLM calls (one per detected wait/schedule noop) against the same `"ai"` rate-limit bucket; the bucket is billed but Pass-2 calls are NOT individually gated. **Adding a new promotable family** means a new entry in `PROMOTE_FAMILIES`, a new schema in `promoted-schemas.ts`, a new helper paired with the schema, and a new `case` in the dispatcher inside `promoteNoopPlaceholders`; the other 7 operator-only types (`multi_agent` / `webhook` / `subworkflow` / `parallel_fork` / `join` / `router_llm` / `agent_reflection`) stay noop-promoted in the Inspector for now. Don't relocate the call after `sanitizeAiWorkflow` — sanitize must validate the promoted workflow against the engine's strict `WorkflowSchema` + structural `validateWorkflow` gate; a node flip past sanitize would bypass that.
- **Decision engine / RL:** `packages/domain` is pure logic, no I/O. `packages/data` owns the drizzle repos. Don't put DB queries in `domain`; don't put scoring logic in `data`.
- **Tool registry:** entries in `packages/engine/src/tool-registry.ts` are typed `ToolDefinition`s with required `inputSchema` + `outputSchema` (Zod 4). `validateToolInput` and `executeTool` route inputs through `safeParse`; outputs are validated before return so executor drift surfaces immediately. Adding a new tool without both schemas is a TS error at registration. The public `listTools()` JSON shape (`name`, `description`, `required`, `optional`, `inputExample`) is part of the AI Studio contract — `required`/`optional` are derived from the input schema; don't drift the field names.
- **MCP server:** `packages/mcp-server` exposes a stdio MCP server. Eleven read-only tools (`workflows.list`, `workflows.get`, `workflows.versions`, `workflows.health`, `recipes.list`, `tools.list`, `runs.get`, `runs.list`, `dlq.list`, `workflows.validate`, `workflows.readiness`) are always advertised; a gated write surface (`workflows.save`) is advertised only when `JANUSLY_MCP_WRITES_ENABLED=true`. Boot via `pnpm --filter @janusly/mcp-server start` (or `dev` for tsx watch). The server is a thin proxy over the existing HTTP API — still no DB access, no audit writes of its own. Auth via `JANUSLY_API_SERVICE_TOKEN` (production) or dev headers (`JANUSLY_API_ORG_ID` / `JANUSLY_API_USER_ID`); the API enforces org scope. MCP descriptors use JSON Schema (the protocol's native shape) — distinct from the engine's Zod-backed tool registry.
- **MCP write consent:** MCP write tools are gated by TWO server-controlled flags: process-wide `JANUSLY_MCP_WRITES_ENABLED=true` (default false) AND per-tenant `org_configs.mcp.writeConsent: boolean` (default false). Both must be true for any MCP write to proceed; either being false returns HTTP 403 with `code: "mcp_process_disabled"` or `code: "mcp_tenant_disabled"`. The MCP client sets `x-janusly-source: mcp` on every request via `packages/mcp-server/src/api-client.ts`; the API auth layer (`apps/api/src/auth.ts`) honors this header in service-token and dev-header modes and stamps the resolved `AuthContext.source`. The header is informational (audit tagging + rate-limit bucketing), NEVER an authorization gate — the gate is the env + tenant flag pair, both server-controlled. Every accepted MCP write writes an audit row with `metadata.source: "mcp"` plus an `actor` block carrying `userId`, `mode`, and `serviceTokenSuffix` (last 4 chars only when service-token auth was used). Per-tool rate-limit bucket naming is `mcp.<actionKey>` (e.g. `mcp.workflows.save`, default 60/min/org via the existing Redis-backed limiter). `workflows.save` accepts an optional `dryRun: true` argument that routes the call to `/validate` so an MCP client can preview without persisting. Adding a new MCP write tool means: (1) push to `WRITE_TOOLS` in `packages/mcp-server/src/tools.ts`, (2) the route handler runs `isMcpWriteAllowed(auth.orgId)` and `enforceRateLimit(auth.orgId, { name: mcpRateLimitBucket("<actionKey>"), ... })` when `auth.source === "mcp"`, (3) the audit row merges `mcpAuditMetadata(auth)`. Don't bypass any of the three — the helpers in `apps/api/src/mcp-consent.ts` are the chokepoint. The consent gate is **MCP-source-scoped on purpose**: a non-MCP service-token caller (CI, internal script — no `x-janusly-source` header) follows the regular service-token auth path with role check from `org_members` and writes a standard audit row. The MCP gate is purely additive defense-in-depth for caller-declared MCP traffic, not a tightening of existing service-token integrations.
- **Maintainer docs convention:** new maintainer-facing docs in `packages/*` and `apps/*` use a file-header block comment (one-line purpose, "Used by:" cross-references, invariants worth knowing) and per-export JSDoc on classes/functions/types/constants. Tone matches AGENTS.md — practical, not narrative. Keep status/progress notes out of source comments and release docs.
- **Causal reasoning:** runs without an LLM. Always available.
- **Cross-panel reactivity:** when an action invalidates server data (save, run start, terminal run, member invite/remove, DLQ replay), call `bumpPlatformVersion()` on the Zustand store. Independent panels listen to it as an effect dep.
- **DLQ:** every failed node beyond `retryPolicy.maxAttempts` lands in `dead_letters`. Replay via `POST /dlq/replay`. The Operations card in Runs surfaces counts and filters. `BullMQQueueAdapter` composes `DeadLetterQueueAdapter` so DLQ insertion is part of the queue contract — don't bypass it.
- **Concurrency:** `enqueueReadyNodes` claims downstream nodes via `tryClaimNodeForQueue` (atomic `UPDATE … WHERE status='pending'`). With multiple workers two predecessors can complete simultaneously; only one wins the claim, so don't reintroduce a non-atomic `markNodeQueued` here. The `parallel_fork` / `join` node-type pair is a declarative shell over this same fan-in atomicity — the fork is a passthrough validator and the join reads predecessor outputs from `ctx.context` to assemble `output.branches`; "wait for all branches" is provided by `enqueueReadyNodes`'s ALL-AND readiness check, "single atomic checkpoint" by `tryClaimNodeForQueue`. Don't introduce a parallel runtime primitive for fan-out — the existing edge graph + atomic claim already covers it. Three readiness rules guard authoring mistakes: `fork_without_join_pair` (warn) flags forks with no transitively-reachable join; `fork_join_missing_branch_sources` (fail) flags forks whose downstream joins don't map every declared branch label; `join_sources_unreachable` (fail) flags joins whose `sources: Record<branchLabel, predecessorId>` references a node that isn't an upstream of the join. Fail-level rules are enforced by the production-mode gate at `POST /start`.
- **Run setup:** `startRun` wraps the `runs` insert + batch `runNodes` insert + `run.started` event in one Drizzle transaction. Don't split it back into per-node inserts.
- **Worker lifecycle:** `worker.ts` listens to `SIGTERM`/`SIGINT` and calls `worker.close()` to drain in-flight jobs. Container restarts don't orphan `running` nodes.
- **Pagination:** `GET /runs` and `GET /workflows` cap at 100 rows by default (max 200 via `?limit=`). `GET /run` and `GET /status` cap nested `events` at 200 by default (max 500 via `?eventsLimit=`) and emit `eventsCursor` / `eventsHasMore`; older history loads via `GET /run?runId=<id>&eventsCursor=<iso>|<eventId>` (URL-encoded by clients). Don't return unbounded lists, and don't reintroduce a full-event-list fetch on the runs view.
- **Observability:** OTel tracer/meter Resource carries `service.name="janusly"`, `service.namespace="janusly"`, and `service.instance.id` (resolved via `OTEL_SERVICE_INSTANCE_ID` env, falling back to `HOSTNAME`, then `os.hostname()`). Set in `packages/engine/src/observability/resource.ts` and threaded into both the `NodeTracerProvider` (`otel.ts`) and the `MeterProvider` (`prometheus.ts`). External dashboards filtering on the legacy `workflow-engine` name need updating; multi-instance dashboards now disambiguate per-process via `service.instance.id`.
- **Scheduler:** the `schedule` node type fires runs on a cron expression. Persistent state lives in `schedule_entries` (id / orgId / workflowId / workflowVersionId / nodeId / cronExpression / enabled / lastRunAt / lastRunId), unique on `(orgId, workflowVersionId, nodeId)`. Trigger mechanism is BullMQ 5's `upsertJobScheduler` API keyed by the deterministic id `schedule:<orgId>:<workflowVersionId>:<nodeId>`. Save-time sync (`syncWorkflowSchedules` in `packages/engine/src/schedule-scheduler.ts`) runs outside the save transaction and is idempotent — a save → register crash recovers via the next save or the worker's cold-start `replayAllScheduleEntries()` (awaited before the BullMQ `Worker` constructor at boot). Pause/resume is in-band: re-save the workflow with `schedule.config.enabled = false` (and back to `true` to resume); there is no separate pause/resume endpoint. Workflow delete is `DELETE /workflows/:id` (Open/Closed routing, single registry entry, hard-deletes `workflows` + `workflow_versions` + unregisters every BullMQ scheduler; orphaned `runs` / `audit_logs` rows are tolerated since `workflow_version_id` is a text column with no FK). The trigger handler (`handleScheduleTrigger`) reads `orgId` from the PERSISTED `schedule_entries` row via `getScheduleEntryById` — never from the BullMQ payload — so a spoofed payload can't cross-tenant trigger another org's workflow; stale cleanup when the row is gone removes only the BullMQ `repeatJobKey` attached to the actual scheduler job, not `orgId` / `workflowVersionId` / `nodeId` hints from `job.data`. Cron parsing goes through `cron-parser` 4.x via the shared `validateCronExpression` helper, applied at three layers (workflow-validation rule `schedule_invalid_cron`, `syncWorkflowSchedules` skip-on-invalid, executor `resolveScheduleConfig`). Don't bypass `upsertJobScheduler` / `removeJobScheduler` by calling `workflowQueue.add(..., { repeat: ... })` directly — the scheduler module owns the lifecycle. AI generation does NOT include `schedule` in `AiGenerationWorkflowSchema` — the 11/20 node-type cap is preserved; operators promote a `noop` placeholder via the inspector, same pattern `multi_agent` / `wait_until` / `webhook` / `agent_reflection` / `router_llm` / `subworkflow` / `parallel_fork` / `join` use.
- **Integration tools:** third-party API tools (`slack.post`, `github.create_issue`, `webhook.send`, future additions in `packages/engine/src/integration-tools.ts`) follow a single chokepoint pattern. (1) Credential resolution: `getCredentialByName(orgId, kind, name)` from `packages/data/src/credentialsRepo.ts` — multi-tenant scoped via `eq(credentials.orgId, orgId)`. The credential row's `secretRef` names an env var; the actual API key / webhook URL / signing secret lives in `process.env[secretRef]`. Workflow JSON carries only the credential name for credential material; destination URLs such as `webhook.send.url` are ordinary tool input, not secrets. The env-var name is NEVER echoed in error envelopes (when missing, return `credential secret missing for <name>` — generic). (2) Outbound HTTP through `fetchHttpTarget` ONLY — no vendor SDKs (`@slack/web-api`, `@octokit/*`, `axios`, etc.). The SSRF / DNS-pin / body-cap / timeout / redirect guards apply uniformly. (3) Per-org rate limit via the shared Redis-backed limiter, bucket name `tool.<actionKey>` (e.g. `tool.slack.post`), per-tenant override via `org_configs.{slack,github,webhook}.rateLimitPerMin`, fail-open on Redis blips (existing posture). (4) Usage event via `setIntegrationUsageRecorder` (DI seam in `packages/engine/src/integration-usage.ts`, registered at api + worker boot to `packages/data/src/usageRepo.ts:recordIntegrationUsage`) — fires on success AND failure with `metric: "tool.<name>"` so cost / quota dashboards include the failed-call traffic. (5) `writeSide: true` on every integration tool so sandbox / validation-mode runs skip them via the existing `dryRun` path. (6) Return envelope is `{ ok, statusCode?, error?, latencyMs, ...result }`; tools NEVER throw on runtime failures (rate-limit, missing credential, upstream non-2xx) — the workflow run consumes the envelope and decides via downstream `condition` nodes. `webhook.send` signs the body with Stripe-style HMAC-SHA256: `X-Janusly-Signature: t=<unix-seconds>,v1=<hex>` where the signed payload is `<timestamp>.<body>` — receivers verify with a 5-line check using the same shared secret. Don't add a new integration tool by reaching for the vendor SDK; reuse the chokepoint.
- **PDF generation + object store:** the `pdf.generate` tool routes Markdown templates through the `pdfkit`-backed renderer in `packages/engine/src/pdf-renderer.ts` (no Chromium dep) and uploads via the pluggable object-store abstraction in `packages/engine/src/object-store.ts` — three providers (`S3Provider` using `@aws-sdk/client-s3` + presigned URL fallback / `LocalDirProvider` for dev/tests / `NoopProvider`) selected per org by the safe `org_configs` key `objectstore.provider`, with env fallback `JANUSLY_OBJECT_STORE_PROVIDER`. Bucket / region / endpoint / public base URL come from `JANUSLY_OBJECT_STORE_*` env (never `org_configs`); the S3 endpoint override supports MinIO / Cloudflare R2 / Backblaze without extra plumbing. The S3 provider intentionally bypasses `fetchHttpTarget` because the bucket endpoint is operator-supplied infrastructure config, not workflow-author input — don't try to "harden" the S3 SDK call by routing it through the SSRF chokepoint. Per-org key prefix `orgs/<orgId>/pdfs/<runId>/<nodeId>/<filename>` (assembled by the tool wrapper) is the only thing keeping tenants from reading each other's PDFs — never bypass `getObjectStore()` from outside the tool. Per-org rate limit via the shared limiter, bucket name `tool.pdf.generate`, default 30/min, override via `org_configs.integrations.pdf.rateLimitPerMin` or `JANUSLY_PDF_RATE_LIMIT_PER_MIN`. Render is gated BEFORE upload so over-limit calls don't waste CPU. Every call (success, render-fail, upload-fail, AND rate-limit-rejected) writes a `usage_events` row with `metric: "pdf.generated"` and `quantity` = produced PDF byte length via `packages/engine/src/pdf-usage.ts` + `setPdfUsageRecorder` (registered at both api + worker boot to `packages/data/src/usageRepo.ts:recordPdfUsage`). The provider's `put()` NEVER throws — all failures degrade to `{ ok: false, provider, error }` so write-side tools mirror the AI-fallback contract. HTML template rendering is intentionally deferred (Markdown only in v1).
- **Mailer:** the `email.send` tool routes through a pluggable mailer abstraction in `packages/engine/src/mailer.ts` — three providers (Resend / SendGrid / Noop) selected per org by the safe `org_configs` keys `email.provider`, `email.from`, and `email.rateLimitPerMin`, with env fallbacks `JANUSLY_MAILER_PROVIDER`, `JANUSLY_MAILER_FROM`, and `JANUSLY_EMAIL_RATE_LIMIT_PER_MIN`. Provider API keys still come only from env/vault (`RESEND_API_KEY` / `SENDGRID_API_KEY`), never `org_configs`; Resend's sandbox `onboarding@resend.dev` is the smoke-friendly default sender. Both real providers call out via `fetchHttpTarget` so the existing SSRF guards + bounded timeout / body / redirect apply (no Resend / SendGrid SDK dep). Provider `send()` NEVER throws — all failures (network, non-2xx, malformed body) degrade to `{ ok: false, provider, error }`. The per-org `"email.send"` bucket is enforced through `setEngineRateLimiter` in both API and worker processes, backed by the shared Redis limiter from `packages/data/src/rate-limit.ts`; default 100/min and fail-open on Redis blips. Every send (success, failure, AND rate-limit-rejected) writes a `usage_events` row with `metric: "email.sent"` via `packages/engine/src/email-usage.ts` + `setEmailUsageRecorder` (registered at both api + worker boot to `packages/data/src/usageRepo.ts:recordEmailUsage`). The metadata shape (provider, providerMessageId, ok/error, latencyMs, nodeId, workflowId) surfaces in the existing `?breakdown=workflow,provider` UI. Don't bypass the chokepoint by calling `getMailer().send` from outside the tool.
- **AI audit:** `/ai/generate-workflow` and `/ai/explain-workflow` write `audit_logs` rows on AI-mode success (`ai.workflow.generated` / `ai.workflow.explained`). `/ai/review-workflow`, `/ai/patch-workflow`, and `/ai/suggest-improvement` audit on AI-mode AND fallback (`ai.workflow.reviewed` / `ai.workflow.patch_suggested` / `ai.workflow.improvement_suggested`) per the AI-mutation contract — don't ship a new AI mutation surface that skips the fallback audit row. `/ai/suggest-improvement` is read-only by design (no DB mutation) but counts as a mutation surface for audit purposes because the operator picks one of the suggestions and applies it through the existing `/workflows/save` chain. Keep the audit when adding new AI endpoints.
- **AI improvement suggestions:** `POST /ai/suggest-improvement` uses `AiSuggestImprovementEnvelope` with `suggestions: Array<{ patchedWorkflowJson, rationale, approachLabel, confidence }>` and `min(1).max(3)`. Keep this 1-3 shape; single-suggestion responses are just an array of length 1. The model emits each full workflow as a JSON-stringified blob to stay below provider grammar caps, and the route must run every item through `JSON.parse` → `WorkflowSchema.safeParse` → `sanitizeAiWorkflow`, drop invalid items, sort survivors by confidence desc, and fallback when none survive. Don't replace this with a "one improvement" prompt or a nested typed workflow schema unless the provider grammar cap has been revalidated.
- **Safe persistence chokepoint:** every jsonb write to `run_events.payload`, `run_nodes.state_json`, `run_nodes.error_json`, `dead_letters.error_json` (+ `workflow_json` / `node_json` key-redaction only), and `audit_logs.metadata` goes through `safePersistPayload` from `packages/engine/src/safe-persist.ts`. - **Failure recovery patch surface:** `POST /ai/patch-workflow` (`role: "editor"`, rate-limited via the shared `"ai"` bucket) is the AI route the Recovery dialog calls. The route reads the failing node's type from `dlq.nodeJson.type`, picks one of ten per-type config envelopes via `patchEnvelopeForNodeType` (`apps/api/src/ai-schemas.ts`) — `AiPatchHttpConfigEnvelope` / `AiPatchToolConfigEnvelope` / `AiPatchAgentConfigEnvelope` / `AiPatchTransformConfigEnvelope` / `AiPatchConditionConfigEnvelope` / `AiPatchAiConfigEnvelope` / `AiPatchRouterConfigEnvelope` (also handles `router_llm`) / `AiPatchApprovalConfigEnvelope` / `AiPatchLoopConfigEnvelope` / `AiPatchGenericConfigEnvelope`. `multi_agent`, `human_form`, and `noop` intentionally fall through to the generic envelope — multi_agent's `agents` array is structurally too complex for v1, human_form is a resume-schema surface rather than a config-repair target, and noop has no actionable runtime config (empty patches trip the no-op guard). Each envelope wraps a `suggestions: Array<{ patchedConfig, rationale, approachLabel, confidence }>` with `min(1).max(3)` items — multi-suggestion is the only shape; single-suggestion responses are just an array of length 1. The http/tool/agent `patchedConfig` schemas are single non-union object schemas with leaf fields declared `.nullable()` (NOT `.optional()`). The http envelope's `headers` and the tool envelope's `input` use a bounded `Array<{ name, value: string | null }>` patch form (`max(20)` / `max(30)`) instead of an open `Record<string, ...>` (which OpenAI strict mode rejects via `propertyNames`). Transform `mapping` and loop `mapping` use the same array-of-pairs patch form. The merge layer in `apps/api/src/patch-workflow-merge.ts` folds each pair against the failing node's existing record (`PAIR_ARRAY_FIELDS_BY_NODE_TYPE = { http: ['headers'], tool: ['input'], transform: ['mapping'], loop: ['mapping'] }` scopes the fold per node type — generic-envelope nodes like `subworkflow` whose `config.input` is structurally different flow through verbatim); non-null `value` sets/replaces the key, `null` removes it, an empty array is a no-op preserving the existing record. Router `candidates` is an array but a verbatim-replace shape (no fold) — the LLM either replaces the full list or emits `null` to preserve. For `tool`-typed failures, the route enriches the prompt with `extraContext.toolInputContract` (the failing tool's `listTools()` entry: `name` / `description` / `required` / `optional` / `inputExample`) so the LLM has the exact required-field names instead of having to infer them from the runtime error message — closes the gap where the runtime error (e.g. "search is required") and the existing config's wrong key (e.g. `input.input`) would otherwise have the LLM emit field names that don't match the registered tool schema. This satisfies BOTH provider strict-mode contracts for the primary resilience patch path: Anthropic's compiled-grammar cap holds because each typed envelope has 3-7 leaf fields and the array is ONE repeated `items` constraint (not three branches), and OpenAI's strict-mode rule "every property in `properties` must be in `required`" holds because nullable-required is the fix (a `.optional()` field would be missing from `required` and OpenAI rejects). The generic envelope is best-effort for non-resilience node types until they get concrete provider-strict envelopes. Don't reintroduce a `discriminatedUnion` to a structured-output schema — `oneOf` is rejected outright by OpenAI strict mode and bloats Anthropic's grammar. The LLM emits ONLY the patched configs for the failing node (sending `null` for fields it doesn't want to change), each tagged with `approachLabel` (closed enum: `add_retry` / `raise_timeout` / `swap_secret_ref` / `add_approval` / `fix_url` / `other`) and a self-rated `confidence` 0-100. The route fan-out-merges each suggestion's `patchedConfig` into the original workflow snapshot after stripping nulls, validates each through the same `WorkflowSchema.safeParse` + `sanitizeAiWorkflow` chain `/ai/generate-workflow` uses, drops invalid suggestions, sorts survivors by confidence desc, and degrades to fallback when none survive. The route's response carries the new `suggestions: Array<{ workflow, rationale, approachLabel, confidence }>` AND legacy `suggestedWorkflow`/`rationale` fields mirroring `suggestions[0]` for back-compat — older clients reading just the legacy fields keep working. The patch helper (`packages/ai/src/patch-workflow.ts`) stays schema-agnostic — its `SYSTEM_PROMPT` instructs the LLM to emit 1-3 distinct alternatives ordered most-likely-fix first, with self-rated confidence and approachLabel. Per the AGENTS.md AI-fallback contract the helper never throws — null LLM / quota / network / schema mismatch all degrade to `mode: "fallback"` returning a single 0-confidence "other" item with the original workflow untouched. Don't bypass the sanitize step, the per-suggestion validation, or the audit row — all three are required for the AI-mutation invariant. **Release verification is Anthropic-only until explicit new direction**: smoke against `anthropic/claude-haiku-4-5-20251001` and expect `mode: "ai"` with a real structural diff on the failing node. OpenAI-compatible schema constraints may remain in code/tests for future expansion, but OpenAI smoke is not a shipping gate while the product is Anthropic-only.
