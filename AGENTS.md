# Agent Notes — Janusly

Operational invariants only — how to run the project, what not to break. Keep temporary planning and status notes outside source comments and release-facing docs.

Janusly = the AI operator for business workflows. Internal packages live under the `@janusly/*` scope. Everywhere user-facing (UI brand-mark, page titles, marketing copy, `/ai/*` responses) say **Janusly**.

- **Stack baselines:** Node.js **24**, TypeScript 6, React 19, Vite 8 (Rolldown), Tailwind 4 (CSS-first via `@theme` + `@tailwindcss/vite`), Vitest 4, Zod 4, Drizzle 1.0 RC, Postgres 18, Redis 8, OpenAI SDK 6.
- **Design system:** Workflow palette (Cobalt `#245BFF` + Cyan `#06B6D4` + green/amber/red status). Tokens in `apps/web/src/index.css` (`@theme { --color-we-* }` + `:root` aliases). No inline hex.
- **Tailwind 4 is CSS-first.** No `tailwind.config.ts` or `postcss.config.js`. The plugin runs through `@tailwindcss/vite()` in `apps/web/vite.config.ts`.
- **Vite 8 / Rolldown:** `build.rollupOptions.output.manualChunks` must be a function, not an object literal.
- **Zod 4:** `z.record(z.string(), z.unknown())` — two-arg form.
- **Auth:** dev-mode uses `x-org-id` and `x-user-id` headers, allowed automatically when Supabase is unset **and** `NODE_ENV !== "production"`. Production without Supabase requires explicit `ALLOW_DEV_AUTH_HEADERS=true` or the API refuses to start. The `dev-headers` mode falls back to the `admin` role only when no `org_members` row exists; `service-token` mode does **not** auto-grant admin.
- **Org config:** `org_configs` is only for tenant runtime settings from the closed catalog in `packages/data/src/orgConfigRepo.ts` (AI provider/model/limits, outbound HTTP bounds, run/subworkflow policy). Never store secrets, tokens, API keys, database URLs, Redis URLs, Supabase keys, service tokens, arbitrary env vars, or workflow secret values there. Secret material belongs in env/vault-backed `credentials.secret_ref`. New config keys must be typed (`string`/`number`/`boolean`), category-scoped (`ai`/`http`/`runs` unless the catalog intentionally grows), validated before insert/update, audited via the API, and rejected by the forbidden-name/value guards if they look like credentials.
- **HTTP/SSRF:** `ALLOW_PRIVATE_HTTP_TARGETS=false` blocks localhost/private/link-local for `http` nodes and the `http.request` tool. The validated DNS resolution is pinned for the actual TCP connect via an `undici.Agent` `connect.lookup` hook, so DNS rebinding (public IP at validation, private IP at connect time — e.g. `169.254.169.254` AWS metadata) cannot redirect the connect to a private target. Don't unwind the pinned dispatcher path in `packages/engine/src/http-policy.ts`.
- **Rate limiter:** API rate-limit state lives in Redis (`apps/api/src/redis.ts` + `apps/api/src/rate-limit.ts`) so counts are shared across all API replicas. Backed by `INCR` + `PEXPIRE` with a `janusly:rate:<name>:<orgId>` key. Fails **open** with a `[rate-limit]` warn log when Redis is unreachable — never fail closed; an AI Studio outage during a Redis blip is worse UX than a brief over-limit window. Don't reintroduce the in-memory `Map` fallback.
- **Usage events:** every LLM call writes one row to `usage_events` from the chokepoint `LlmClient.generateText`. The recorder is registered process-globally via `setUsageRecorder(recordUsage)` at api + worker boot; `packages/ai` itself stays DB-agnostic. `metric: "llm.completion"`, `quantity: totalTokens`, `metadata: { provider, model, inputTokens, outputTokens, latencyMs, costUsd, nodeId, mode, aiError }`. Cost is computed from `packages/ai/src/pricing.ts` (defaults + `JANUSLY_LLM_PRICE_<MODEL>` env override); unknown models record `costUsd: null`. Recorder failures are caught and dropped — telemetry must never break an LLM call. Don't bypass the chokepoint by calling `aiGenerateText` directly from outside `packages/ai`. Engine-side `orgId` plumbs through `NodeContext.orgId`, populated once per node execution by `executeNode` via `getRunOrgId(runId)`. The runtime's router-decision and improvement-evaluation paths use a sister helper, `getRunMetadata(runId)` (`packages/engine/src/persistence.ts`), loaded once per `executeQueuedNode` call — same pattern, but returns `{ orgId, workflowVersionId, workflowId, createdBy }` (joined through `workflow_versions`). Don't read `orgId` / `workflowId` off the loose `RunContext` bag for routing-stats or improvement writes; both paths go through `getRunMetadata` so the writes are structured-org-scoped instead of silently no-op'ing.
- **AI integration:** every AI surface (`/ai/generate-workflow`, `/ai/explain-workflow`, `/ai/review-workflow`, `/ai/explain-run`, the `agent` planner `"openai"`, the `ai` step type) routes through the provider-neutral `LlmClient` in `packages/ai/src/llm-client.ts` (built on the Vercel AI SDK). Env still supplies provider API keys; `org_configs` may override safe tenant-level provider/model/limits before the API or engine creates the client. `JANUSLY_LLM_PROVIDER` defaults to `openai`; today `openai` + `anthropic` are registered. Per-call overrides go through the `model` field on workflow nodes / API request bodies: a bare id (`"gpt-4o-mini"`) uses the configured provider; `"<provider>/<model>"` (e.g. `"anthropic/claude-haiku-4-5"`) overrides provider for that one call. Adding a new provider (Ollama, Mistral, Google) is a four-field entry in the `PROVIDERS` registry — no other code changes; see `packages/ai/README.md`. Every AI path has a deterministic fallback **and** wraps the SDK invocation in try/catch — on any failure (quota, rate, network, bad output, unknown provider, missing key for an override) the response stays `{ mode: "fallback", aiError: "<reason>", ... }` with the local content attached. Never break the fallback or remove the try/catch. `GET /ai/health` reports `enabled`, `provider`, and `model` reflecting the current tenant runtime config. `/ai/generate-workflow` calls `llm.generateObject({ schema: WorkflowSchema })` so the model returns a typed object directly — no `JSON.parse` + looser pre-pass needed. The route still runs a small `sanitizeAiWorkflow` step (`apps/api/src/index.ts`) that filters edge `condition` strings and `condition`-node expressions through `validateExpression` (Janusly's limited grammar). Don't drop the sanitize step — Zod validates shape, but the engine's expression evaluator is stricter than Zod's `z.string()`. Schema-validation failures and sanitize throws both flow through the route's existing try/catch into `{ mode: "fallback", aiError, ... }`.
- **Decision engine / RL:** `packages/domain` is pure logic, no I/O. `packages/data` owns the drizzle repos. Don't put DB queries in `domain`; don't put scoring logic in `data`.
- **Tool registry:** entries in `packages/engine/src/tool-registry.ts` are typed `ToolDefinition`s with required `inputSchema` + `outputSchema` (Zod 4). `validateToolInput` and `executeTool` route inputs through `safeParse`; outputs are validated before return so executor drift surfaces immediately. Adding a new tool without both schemas is a TS error at registration. The public `listTools()` JSON shape (`name`, `description`, `required`, `optional`, `inputExample`) is part of the AI Studio contract — `required`/`optional` are derived from the input schema; don't drift the field names.
- **MCP server:** `packages/mcp-server` exposes a stdio MCP server with seven tools — five read-only (`workflows.list`, `workflows.get`, `recipes.list`, `tools.list`, `runs.get`), one validation pre-flight with no side effects (`workflows.validate`), and one write (`workflows.save`). Boot via `pnpm --filter @janusly/mcp-server start` (or `dev` for tsx watch). The server is a thin proxy over the existing HTTP API — still no DB access, no audit writes of its own. The write tool goes through the API's `requireRole("editor")` + `audit()` path (the `workflow.saved` audit row carries the configured `JANUSLY_API_USER_ID`, default `mcp-user`), so MCP-origin saves are auditable end-to-end. Auth via `JANUSLY_API_SERVICE_TOKEN` (production) or dev headers (`JANUSLY_API_ORG_ID` / `JANUSLY_API_USER_ID`); the API enforces org scope. Don't add more write tools without an explicit product/security review matching the same posture (RBAC enforced upstream + audit row written by the API + safe to expose to a remote MCP client). MCP descriptors use JSON Schema (the protocol's native shape) — distinct from the engine's Zod-backed tool registry.
- **Maintainer docs convention:** new maintainer-facing docs in `packages/*` and `apps/*` use a file-header block comment (one-line purpose, "Used by:" cross-references, invariants worth knowing) and per-export JSDoc on classes/functions/types/constants. Tone matches AGENTS.md — practical, not narrative. Keep status/progress notes out of source comments and release docs.
- **Causal reasoning:** runs without an LLM. Always available.
- **Cross-panel reactivity:** when an action invalidates server data (save, run start, terminal run, member invite/remove, DLQ replay), call `bumpPlatformVersion()` on the Zustand store. Independent panels listen to it as an effect dep.
- **DLQ:** every failed node beyond `retryPolicy.maxAttempts` lands in `dead_letters`. Replay via `POST /dlq/replay`. The Operations card in Runs surfaces counts and filters. `BullMQQueueAdapter` composes `DeadLetterQueueAdapter` so DLQ insertion is part of the queue contract — don't bypass it.
- **Concurrency:** `enqueueReadyNodes` claims downstream nodes via `tryClaimNodeForQueue` (atomic `UPDATE … WHERE status='pending'`). With multiple workers two predecessors can complete simultaneously; only one wins the claim, so don't reintroduce a non-atomic `markNodeQueued` here.
- **Run setup:** `startRun` wraps the `runs` insert + batch `runNodes` insert + `run.started` event in one Drizzle transaction. Don't split it back into per-node inserts.
- **Worker lifecycle:** `worker.ts` listens to `SIGTERM`/`SIGINT` and calls `worker.close()` to drain in-flight jobs. Container restarts don't orphan `running` nodes.
- **Pagination:** `GET /runs` and `GET /workflows` cap at 100 rows by default (max 200 via `?limit=`). `GET /run` and `GET /status` cap nested `events` at 200 by default (max 500 via `?eventsLimit=`) and emit `eventsCursor` / `eventsHasMore`; older history loads via `GET /run?runId=<id>&eventsCursor=<iso>|<eventId>` (URL-encoded by clients). Don't return unbounded lists, and don't reintroduce a full-event-list fetch on the runs view.
- **Observability:** OTel tracer/meter Resource carries `service.name="janusly"`, `service.namespace="janusly"`, and `service.instance.id` (resolved via `OTEL_SERVICE_INSTANCE_ID` env, falling back to `HOSTNAME`, then `os.hostname()`). Set in `packages/engine/src/observability/resource.ts` and threaded into both the `NodeTracerProvider` (`otel.ts`) and the `MeterProvider` (`prometheus.ts`). External dashboards filtering on the legacy `workflow-engine` name need updating; multi-instance dashboards now disambiguate per-process via `service.instance.id`.
- **AI audit:** `/ai/generate-workflow` and `/ai/explain-workflow` write `audit_logs` rows on AI-mode success (`ai.workflow.generated` / `ai.workflow.explained`). Keep the audit when adding new AI endpoints.
- **Safe persistence chokepoint:** every jsonb write to `run_events.payload`, `run_nodes.state_json`, `run_nodes.error_json`, `dead_letters.error_json` (+ `workflow_json` / `node_json` key-redaction only), and `audit_logs.metadata` goes through `safePersistPayload` from `packages/engine/src/safe-persist.ts`. The chokepoint stacks value-based redaction (when `redactedValues` is provided), sensitive-key redaction (closed regex covering `secret*` / `password*` / `token*` / `api*key` / `authorization` / `cookie` / `x-api-key` / `client*secret` / `private*key`), and size bounding (default 256 KB, env `JANUSLY_PERSIST_MAX_BYTES`, per-call `maxBytes`). Over-cap payloads become a `{ __truncated: true, originalBytes, maxBytes, preview }` sentinel. The DLQ workflow/node JSONs use `maxBytes: Number.POSITIVE_INFINITY` to skip truncation (replay needs the exact failed job) but still get key-redacted. Don't write jsonb to those columns without the chokepoint — bypassing it is a wire-leak regression.
- **Production-mode readiness gate:** when env `JANUSLY_PRODUCTION_MODE=true`, `POST /start` runs `checkWorkflowReadiness` (`packages/engine/src/workflow-readiness.ts`) before delegating to `startRun` and rejects fail-level workflows with HTTP 422 + the issue list. The check is deterministic (no LLM, no fallback) and runs the same set of rules `POST /workflows/readiness` exposes for the AI Studio badge: external-call retries, http bounds, declared outputs, approval ancestor for write-side actions, no hardcoded secret-shaped field values (must be `{{secret.X}}` / `{{env.X}}` / `{{credential.X}}` templates), and rollback availability (`workflow_versions` ≥ 2). The eval-coverage warn is opt-in via `JANUSLY_REQUIRE_EVAL_COVERAGE=true` so clean workflows can reach `status: "pass"` while orgs that want operators reminded until eval tracking lands flip the env on. Dev mode (`JANUSLY_PRODUCTION_MODE` unset) keeps the existing behaviour — anything structurally valid runs. Adding a new readiness rule means extending the rule list inside the engine module and adding a stable issue `code` (the web matches on codes for localised messages). Don't bypass the gate from `/start`; if a future surface needs the same gate, route through `checkWorkflowReadiness` + `mergeReadiness` rather than re-implementing.
- **Workflow health rollup:** `GET /workflows/health?workflowId=…` (`role: "viewer"`) composes `collectHealthSignals` (`packages/data/src/workflowHealthRepo.ts`, 30-day window) + `computeWorkflowHealth` (`packages/engine/src/workflow-health.ts`) into a single 0–100 score plus six per-category sub-scores: reliability (success rate − DLQ/retry penalties), safety (readiness fail/warn penalties), cost ($/run band), latency (p95 band), maintainability (declared outputs + multiple versions + approval node), AI risk (AI-node count + token volume + raw-secret findings). Weights and bands are constants exported from the engine module — tune in one place. Status thresholds: `≥80 healthy / ≥60 warn / <60 unhealthy`. Neutral default 80 covers brand-new workflows (totalRuns < 5 → reliability/cost neutral; p95 null → latency neutral) so an untested workflow isn't graded as if it were unhealthy. The repo's signal-collection queries enforce multi-tenant scope by joining through `workflow_versions` with `eq(workflowVersions.orgId, orgId)` AND `eq(workflowVersions.workflowId, workflowId)`. The `HealthSignals` type is defined in the data layer and re-shaped structurally in the engine to keep the dependency direction clean (engine → data, never the reverse) — adding a field means editing both definitions; engine tests plus TypeScript structural checks pin the contract. Compute is on-demand per request, not persisted; tracking score history / drift alerts is a future ticket.
- **Sensitive-key regex:** the closed list of secret-shaped object keys (`secret*` / `password*` / `token*` / `api*key` / `authorization` / `cookie` / `x-api-key` / `client*secret` / `private*key`) lives in `packages/shared/src/sensitive-keys.ts` as `SENSITIVE_KEY_PATTERN`. `safe-persist.ts` re-exports it (so engine consumers don't change), and `packages/shared/src/workflow-diff.ts` imports it for the structural-diff's `secret_ref` tagging. Adding a new key shape here improves redaction at write time AND secret-ref tagging at diff time without one layer depending on the other. Don't fork the regex into a second module.
- **Workflow version diff:** `computeWorkflowDiff(before, after)` (`packages/shared/src/workflow-diff.ts`) is the canonical structural-diff helper between two workflow snapshots — added / removed / changed nodes + edges + workflow-level fields, plus a tag classifier (`secret_ref` / `retry` / `timeout` / `bounds` / `approval` / `rationale`) the UI uses to colour severity. Lives in `@janusly/shared` (zero runtime deps) so the web bundle imports it via `@janusly/shared/src/workflow-diff` subpath; no API route involved. Reuses `SENSITIVE_KEY_PATTERN` from the same package. The `VersionHistoryPanel.tsx` Compare-mode toggle and (future) the Recovery MVP both render `WorkflowDiffView` over the same diff shape.
- **Recovery metrics rollup:** `GET /recovery/metrics?windowDays=…` (`role: "viewer"`) composes `collectRecoveryMetricsSignals` (`packages/data/src/recoveryMetricsRepo.ts`, 30-day window default, six parallel windowed queries with caps: 1k MTTR samples, 10k usage rows, 5k events) + `composeRecoveryMetrics` (`packages/engine/src/recovery-metrics.ts`) into the org-level Operations dashboard payload — six metric cards (success rate, MTTR, p95 latency, approvals pending, replay rate, cost) each with `value` / `display` / `severity` / `rationale`. Severity bands are exported constants (`SUCCESS_RATE_BANDS` / `MTTR_BANDS_MS` / `LATENCY_BANDS_MS` / `APPROVALS_BANDS` / `REPLAY_RATE_BANDS`) so future tuning lives in one place. Multi-tenant scope on every query (`eq(<table>.orgId, orgId)` direct or via `workflow_versions` join). `approvals pending` is current-state, not windowed — operators read it as "right now blocking", documented in the card's rationale. Cost is grouped in JS (not via PG JSON ops) — keeps the query plan identical to other repos and microsecond-cheap at the 10k cap. "Auto-fixes suggested/applied" + "rollbacks triggered" counters from the AC are deferred — they need new audit-log actions that don't exist yet; will plug in when the Recovery MVP ships the apply path.
- **Failure clustering:** `GET /dlq/clusters?windowDays=…` (`role: "viewer"`) composes `collectFailureSamples` (`packages/data/src/failureClusterRepo.ts`, 30-day window default, 500-sample cap, parallel queries over `dead_letters` + failed `run_nodes`) + `clusterFailureSamples` (`packages/engine/src/cluster-failures.ts`) into a list of normalized failure clusters. Multi-tenant scope comes from persisted owner rows (`dead_letters.org_id`, `runs.org_id`); saved workflows left-join `workflow_versions` for names, and ad-hoc runs fall back to the persisted workflow snapshot. The DLQ writer carries `orgId` from run metadata, defaulting only as last resort. The pure normalizer `normalizeErrorSignature` (`packages/engine/src/error-signature.ts`) runs 7 first-match-wins rules — `secret_missing` / `http_error` / `network_timeout` / `ai_provider` / `parse_error` / `tool_input` / `unknown` — to produce a stable cluster label like `"Missing secret: GITHUB_TOKEN"` or `"HTTP 401 on http node"`. Hard safety property: **no secret value ever appears in a returned signature**. Every produced label passes through `scrubSecretShapes` (closed regex: `sk-…` / `ghp_…` / `xox[baprs]-…` / `AKIA…` / `Bearer …` / 3-segment JWT) before return — defense-in-depth on top of the safe-persist chokepoint that already key-redacts the JSON we read from. Free-form error MESSAGES escape key-redaction, so this final scrub is the last line of defence. `(runId, nodeId)` deduplication preserves the DLQ-source sample over the failed-`run_nodes` sample so a failed run that landed in DLQ counts once. The route registers BEFORE the wildcard `/dlq` dispatcher in the route registry — first-match-wins; reordering would silently break the cluster surface. Compute is on-demand per request; cluster persistence + drift alerts are a future ticket.
- **Web deps:** `apps/web` only imports `react`, `react-dom`, `@xyflow/react`, `@supabase/supabase-js`, `zustand`, `lucide-react`, and the zero-dependency `@janusly/shared/src/status` / `@janusly/shared/src/workflow-diff` subpaths. Do not import the broad `@janusly/shared` barrel from web; it pulls workflow Zod schemas into the browser bundle. No `@radix-ui`, `class-variance-authority`, `clsx`, or `tailwind-merge` — the design system is hand-written CSS in `index.css`. Don't reintroduce shadcn-style scaffolding.
- **Migrations:** schema lives in `packages/db/src/schema.ts`; checked-in SQL under `packages/db/migrations/` is generated via `pnpm --filter @janusly/db db:generate`. Apply with `pnpm migrate` (delegates to `drizzle-kit migrate`) before booting the API or worker — both call `assertMigrationsApplied()` at startup and fail fast if the `drizzle.__drizzle_migrations` table is missing. Don't reintroduce a runtime `CREATE TABLE` bootstrap. The e2e harness runs `pnpm migrate` between Compose-up and API boot.
- **API routing (Open/Closed):** every HTTP route is one entry in the `routes: Route[]` array exported from `apps/api/src/index.ts`. The `http.createServer` dispatcher iterates the array (first-match-wins), runs `requireAuth` + `requireRole` based on the route's declared shape, and calls the handler. Don't reintroduce inline `if (req.method === "POST" && req.url === ...)` branches outside the registry — new routes plug in via `routes.push({...})` (or by appending to the literal). `Route` types live in `apps/api/src/routes.ts`. Multi-tenant scope (`eq(<table>.orgId, auth.orgId)`) still lives inside the handler.
- **Tests:** `pnpm test` runs Vitest 4 in shared, engine, ai, domain, db, api, and web (jsdom + Testing Library; `*.browser.test.tsx` files are excluded from this run by the jsdom config and execute separately via the browser-mode pool). `pnpm test:browser` runs Vitest browser mode against `apps/web/src/**/*.browser.test.tsx` via `@vitest/browser` + the existing Playwright/Chromium binary (run `pnpm --filter @janusly/web exec playwright install chromium` once on a fresh checkout). `pnpm test:e2e` boots Postgres/Redis via Compose, runs `pnpm migrate`, starts API + worker, lets Playwright bring up the UI, shuts Compose down on exit. `pnpm evals` runs `scripts/run-evals.mjs` against a running API (assumes `pnpm dev` is up; override the URL via `JANUSLY_EVALS_API_URL`); reads `evals/generate-workflow.jsonl`, POSTs each prompt to `/ai/generate-workflow`, asserts node-type shape, and exits 0 if no cases failed and 1 otherwise. Cases marked `requiresMode: "ai"` are skipped only when the API returns fallback without `aiError`, so devs without an `OPENAI_API_KEY` still see a green run while live-AI degradation remains a failure.
- **CI:** `.github/workflows/ci.yml` runs four parallel jobs on PR + push to `main` — `build_test` (`pnpm build` + `pnpm test`), `test_browser` (`pnpm test:browser` with Playwright/Chromium cached at `~/.cache/ms-playwright`), `test_e2e` (`pnpm test:e2e`, full Compose lifecycle), and `dep_audit` (`pnpm audit --audit-level high`, fails the build only on high+ advisories — keep moderate fixes in their own follow-up changes). All jobs pin `pnpm@10.23.0` and `node@24` to match the root `packageManager` and `engines.node`. Don't add Compose orchestration to the workflow YAML directly — `scripts/run-e2e.mjs` already owns that lifecycle and CI must reuse it so local and CI behaviour stay identical.
- **Compose lifecycle:** if a task started Compose, run `docker compose down` before finishing unless told otherwise. The dev orchestrator at `scripts/run-dev.mjs` (invoked by `pnpm dev`) brings Compose up, runs `pnpm migrate`, spawns api/worker/web, and tears Compose down on `Ctrl+C` or any child crash. Don't reintroduce a `pnpm -r dev` fan-out at the root — it skips the Compose + migrate steps and silently breaks fresh checkouts.
- **Don't reintroduce** the deleted tRPC stub or Stripe SDK; the API is plain HTTP, billing schema columns are placeholders.
