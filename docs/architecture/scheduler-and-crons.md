## Scheduler

**Scheduler:** the `schedule` node type fires runs on a cron expression. Persistent state lives in `schedule_entries` (id / orgId / workflowId / workflowVersionId / nodeId / cronExpression / enabled / lastRunAt / lastRunId), unique on `(orgId, workflowVersionId, nodeId)`. Trigger mechanism is BullMQ 5's `upsertJobScheduler` API keyed by the deterministic id `schedule:<orgId>:<workflowVersionId>:<nodeId>`. Save-time sync (`syncWorkflowSchedules` in `packages/engine/src/schedule-scheduler.ts`) runs outside the save transaction and is idempotent — a save → register crash recovers via the next save or the worker's cold-start `replayAllScheduleEntries()` (awaited before the BullMQ `Worker` constructor at boot). Pause/resume is in-band: re-save the workflow with `schedule.config.enabled = false` (and back to `true` to resume); there is no separate pause/resume endpoint. Workflow delete is `DELETE /workflows/:id` (Open/Closed routing, single registry entry, hard-deletes `workflows` + `workflow_versions` + unregisters every BullMQ scheduler; orphaned `runs` / `audit_logs` rows are tolerated since `workflow_version_id` is a text column with no FK). The trigger handler (`handleScheduleTrigger`) reads `orgId` from the PERSISTED `schedule_entries` row via `getScheduleEntryById` — never from the BullMQ payload — so a spoofed payload can't cross-tenant trigger another org's workflow; stale cleanup when the row is gone removes only the BullMQ `repeatJobKey` attached to the actual scheduler job, not `orgId` / `workflowVersionId` / `nodeId` hints from `job.data`. Cron parsing goes through `cron-parser` 4.x via the shared `validateCronExpression` helper, applied at three layers (workflow-validation rule `schedule_invalid_cron`, `syncWorkflowSchedules` skip-on-invalid, executor `resolveScheduleConfig`). Don't bypass `upsertJobScheduler` / `removeJobScheduler` by calling `workflowQueue.add(..., { repeat: ... })` directly — the scheduler module owns the lifecycle. AI generation does NOT include `schedule` in `AiGenerationWorkflowSchema` — the 11/20 node-type cap is preserved; operators promote a `noop` placeholder via the inspector, same pattern `multi_agent` / `wait_until` / `webhook` / `agent_reflection` / `router_llm` / `subworkflow` / `parallel_fork` / `join` use. **Global cron jobs** (non-tenant recurring tasks like the memory retention sweep — `packages/engine/src/memory-retention-scheduler.ts`) use the reserved `system:` id prefix to distinguish them from per-tenant `schedule:<orgId>:...` ids; the memory-retention sweep registers at worker boot via `registerMemoryRetentionScheduler()` and reads `JANUSLY_MEMORY_RETENTION_CRON` from env (default `0 3 * * *` UTC, validated via the shared `validateCronExpression` with warn-fallback to default on parse failure). The handler calls `deleteExpiredMemory({})` and never throws — a Postgres outage during the sweep logs but doesn't compound via BullMQ retries; the next daily fire is the natural retry because the WHERE clause is idempotent. The repo's existing per-org `memory.retention.purged` audit chokepoint is the canonical observable signal — operators read absence-of-row as the failure indicator. **Two sibling retention sweeps** live alongside `memory-retention-scheduler.ts` for the other unbounded append-only tables: `packages/engine/src/audit-logs-retention-scheduler.ts` (default cron `0 2 * * *` UTC env `JANUSLY_AUDIT_LOGS_RETENTION_CRON`, default 730-day retention env `JANUSLY_AUDIT_LOGS_RETENTION_DAYS` clamped `[30..3650]`) and `packages/engine/src/scim-events-retention-scheduler.ts` (default cron `0 4 * * *` UTC env `JANUSLY_SCIM_EVENTS_RETENTION_CRON`, default 90-day retention env `JANUSLY_SCIM_EVENTS_RETENTION_DAYS` clamped `[7..365]`). Both share the same shape as the memory sweep: reserved `system:<name>-retention` id, cron validated via `validateCronExpression` with warn-fallback to default on parse failure, retention days clamped to the documented range with warn-fallback when out-of-range or non-numeric (so a typo like `5` lands on the default, not five days). The repo helpers in `packages/data/src/auditLogsRepo.ts` (`deleteExpiredAuditLogs`) and `packages/data/src/scimProcessedEventsRepo.ts` (`pruneOldProcessedEvents`) batch the DELETE in 10k-row chunks via `DELETE FROM <table> WHERE <pk> IN (SELECT <pk> FROM <table> WHERE <ts> < $cutoff LIMIT 10_000) RETURNING <pk>` — each batch is its own short transaction so a sweep on a 10M-row table never holds a long lock. A `maxBatches=1000` runaway-safety cap (= 10M-row ceiling per fire) prevents a misconfigured cutoff from spinning forever; the cap state lands in the audit metadata as `cappedByMaxBatches: true` so operators see when one fire ran out of budget. Each handler writes exactly one system-sentinel audit row per fire (`audit_logs.retention.purged` / `scim.event_log.retention.purged`) with `orgId: "system"`, `userId: null`, `metadata: { rowsDeleted, cutoffAt, runtimeMs, retentionDays, cappedByMaxBatches }`. **Per-org configurable retention sweep** is built ON TOP of those three standalone sweeps — `packages/engine/src/retention-scheduler.ts` (reserved `system:retention` id, default cron `0 5 * * *` UTC env `JANUSLY_RETENTION_CRON`, after the 02:00/03:00/04:00 sweeps) walks `listOrgIdsForRetention()` and purges FIVE tenant tables (`run_events` / `usage_events` / `audit_logs` / `recovery_feedback` / `memory_entries`) per org against that org's `org_configs.retention.*` bounds (new `retention` category: `runEventsDays` 7..365/90, `auditLogsDays` 30..730/365, `usageEventsDays` 30..365/90, `recoveryFeedbackDays` 30..365/180, `memoryEntriesDays` 7..730/90; env fallbacks `JANUSLY_RETENTION_*_DAYS`; the narrow `getRetentionPolicyConfig(orgId)` reader re-clamps a stored out-of-range value back to the catalog default). The repo helpers (`packages/data/src/retentionRepo.ts` — `deleteExpired<Table>ForOrg`) reuse the same 10k-batched-DELETE + `maxBatches` 1k-cap shape but carry `org_id = $orgId` per the multi-tenant invariant AND a per-row **legal-hold bypass** conjunct `(hold_until IS NULL OR hold_until <= now())` — every one of the five tables gained an additive nullable `hold_until timestamptz` column for this (a future-dated value exempts the row from the sweep). `run_events` has no org column so it scopes through the parent `runs.org_id` via a join. Unlike the cross-org siblings this sweep is per-ORG: one `retention.purged` audit row per org per fire with the real `orgId` + a per-table breakdown; a per-table or per-org failure is isolated (the loop continues). An **export-before-delete** DI seam (`setRetentionExporter` / `runRetentionExport`) lets an operator wire an archiver that runs BEFORE each org's purge — best-effort, a thrown exporter degrades to a warn and the purge proceeds. Adding a table to this sweep means a new `deleteExpired<Table>ForOrg` helper + a `RETENTION_TARGETS` entry + a catalog key + (if the table lacks one) a `hold_until` column. **Consent-revocation bulk purge** lives in the sibling `packages/engine/src/memory-purge-scheduler.ts` — a one-shot delayed BullMQ job (deterministic `memory-purge:<orgId>` id, 7-day delay from `JANUSLY_MEMORY_PURGE_DELAY_MS` env with positive-integer validation + warn-fallback) scheduled by an awaited bounded call from `apps/api/src/routes/org-routes.ts` on every `memory.enabled` true→false flip AFTER the `memory.consent.revoked` audit fires, and cancelled by an awaited `cancelPendingMemoryPurge` BEFORE the `memory.consent.granted` audit fires (the boolean result rides the audit metadata as `pendingPurgeCancelled`). The handler re-reads `org_configs.memory.enabled` at fire time and SKIPS the purge when consent was re-granted — cancellation is best-effort, the handler's consent re-check is the load-bearing safety. `schedulePendingMemoryPurge` removes any existing job FIRST before adding the new one (rapid revoke-grant-revoke cycles converge cleanly); the schedule + cancel + handler all NEVER throw and queue calls are bounded, so a Redis blip returns false/logs without hanging the config route or wiping data (manual `purgeMemoryForOrg(orgId)` REPL fallback documented) and a Postgres outage on fire degrades to a warn log. Adding a new global cron-style job (not consent-driven) means another `system:`-prefixed module mirroring `memory-retention-scheduler.ts`; adding a new consent-driven delayed job means another module mirroring `memory-purge-scheduler.ts` plus a worker `job.name` dispatch branch + a route-side schedule/cancel call. **Stalled-node reaper** (`packages/engine/src/stalled-node-reaper.ts`, reserved `system:stalled-node-reaper` id, default cron `*/5 * * * *` env `JANUSLY_STALLED_NODE_REAPER_CRON`) is the recovery mechanism for the one failure the atomic claim can't self-heal: a worker that dies (kill -9 / OOM / eviction) mid-node leaves the `run_nodes` row `running`, and because the redelivered BullMQ job's `markNodeRunning` only matches a `queued` row, the claim fails → `node.skipped` → the node stays `running` forever and `updateRunStatusFromNodes` is never called again, so the run is stuck non-terminal with NO DLQ row, recovery item, or terminal signal (a silent break of the recoverability + observability promises). The sweep (`findStalledRunningNodes` in `packages/data/src/stalledNodesRepo.ts` — production runs only via `replay_mode IS NULL`, non-terminal parent run, oldest-first, capped at `STALLED_NODE_REAPER_LIMIT = 500`) finds nodes `running` past `JANUSLY_STALLED_NODE_THRESHOLD_MINUTES` (default 60, clamped `[15..1440]` — the floor keeps an operator from reaping a legitimately long node; the threshold matches on `started_at`, NOT the BullMQ lock, so it must exceed any single legitimate node execution) and per node: a CAS `failStalledRunningNode` (`running → failed`, the per-node claim so concurrent replicas + a node that just finished are both safe), then a BEST-EFFORT dead-letter via the existing `DeadLetterQueueAdapter` (payload reconstructed from `runs.input_json.workflow` — a missing/unparseable snapshot still fails the node so the run terminates, just without a replay surface), a `node.failed` run event (`reason: "worker_stalled"`), and `updateRunStatusFromNodes` to flip the run terminal. The node is failed-into-DLQ, NOT auto-re-executed (a stalled node may have already run a non-idempotent side effect — the operator decides on replay, same as every other DLQ entry). One `run.stalled_node.reaped` system-sentinel audit row per fire that found work (skipped on the healthy `scanned === 0` path to avoid 5-minute spam). Same never-throws boot + handler posture as the retention sweeps; the pure `reapStalledNodes(deps, config)` core is DI-tested. Known residual: a process crash in the sub-millisecond window between the CAS fail and the rollup matches the engine's existing non-transactional multi-step posture (self-corrected if the run has another stalled node; otherwise a manual rollup is the fallback). **Supervised auto-healing** runs as a sibling cron pair in the **API process** (NOT the engine worker) because the per-candidate handler calls `patchEnvelopeForNodeType` + `applyConfigPatchToWorkflow` which live in `apps/api`; both jobs share a dedicated `auto-healing-system` BullMQ queue + Worker booted from `apps/api/src/auto-healing-bootstrap.ts` only when `JANUSLY_AUTO_HEALING_ENABLED=true`. Scanner (`system:auto-healing-scanner`, default `0 */6 * * *` env `JANUSLY_AUTO_HEALING_SCAN_CRON`) walks `org_configs.autoHealing.enabled = true` orgs, clusters recent DLQ samples, gates each candidate on loop breaker + budget + idempotency, calls `suggestWorkflowPatch`, merges via `applyConfigPatchToWorkflow` / `applyStructuralPatchToWorkflow`, and enqueues sandbox validation via `replayDeadLetterAsValidation`. Watcher (`system:auto-healing-watcher`, default `* * * * *` env `JANUSLY_AUTO_HEALING_WATCH_CRON`) polls validating rows, compares the new failure signature against the original (signature_changed defense), and on success + `isAutoApplyAllowed` replays against the patched workflow with `decisionActor: "auto"`. The auto-apply path is double-gated: both `JANUSLY_AUTO_HEALING_AUTO_APPLY=true` AND `org_configs.autoHealing.autoApply=true` must be set; defaults leave validated rows pending operator decision via `POST /auto-healing/:id/decide`. Both that route and the watcher use a CAS-style `recordDecision` (`UPDATE … WHERE status='validated'`) so concurrent operator-click vs auto-apply cannot double-apply — loser returns 409 `signature_already_resolved`. Two-hour stale-row sweep auto-declines stuck `validating` rows with reason `validation_timeout`. Schedule + cancel + handler all NEVER throw; an LLM fallback skips the candidate (records `scanner_error:llm_fallback:<aiError>`) rather than persisting a 0-confidence row. Loop breaker is configurable per-org via `autoHealing.maxAttemptsPerSignature` (default 3) + `autoHealing.loopWindowDays` (default 14). Audit actions: `auto_healing.diagnosed` / `.proposed` / `.validated` / `.applied` / `.declined` / `.failed` / `auto_healing.decline.manual` / `auto_healing.scan.triggered`. Permissions: `autohealing.read` (viewer+) and `autohealing.decide` (editor+). The web surface is a single new `AutoHealingPendingCard` mounted inside the existing DLQ panel — no new top-level UI panel, no new sidebar entry. Adding a new auto-healing decline reason means an entry in `AUTO_HEALING_DECLINE_REASONS` + a branch in the scanner or watcher that records it; the row's `declineReason` column carries the closed enum verbatim. **Cron observability** rides on the SAME persisted shape: `GET /workflows/:id/schedule-history` (viewer, `workflows.read`, read-only — no audit) returns a 90-day UTC day-of-week × hour-of-day heatmap of scheduled fires plus a next-N-fires preview. There is NO trigger-node-id column on `runs`; a scheduled run is identified by the `input_json -> 'input' ->> 'triggeredBy' = 'schedule'` marker that `start-run` persists for cron fires (`handleScheduleTrigger`'s `input: { triggeredBy: "schedule", scheduleEntryId, nodeId, triggeredAt }`) — `packages/data/src/scheduleHistoryRepo.ts:queryScheduleFires` joins `runs` through `workflow_versions` (tenant + workflow scope) on that marker, window-clamped to `[1,90]` days + row-capped at ≤1000. Don't rename or drop that marker without updating the query — the heatmap silently empties otherwise. Bucketing + the cron-preview are pure (`packages/engine/src/schedule-history.ts`, lives in engine for the `cron-parser` dep; `computeNextFires` is DST-safe and degrades to `[]` on a malformed cron, never throws). The web `ScheduleHistoryPanel` renders a HAND-WRITTEN SVG heatmap (no charting dep) in the Inspector right panel; ENG-141 anomaly red dots are a documented seam (`cell.anomaly: false` rides the response today, no overlay yet).
