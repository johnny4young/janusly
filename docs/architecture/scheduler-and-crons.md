## Queue isolation

Customer execution and platform maintenance use separate BullMQ delivery lanes. `workflow-nodes` owns node execution, workflow schedules, delayed approval/timer checkpoints, and paced replay steps. `maintenance-jobs` owns retention, confidence calibration, upstream-health polling, stalled-node repair, durable reconcilers, and consent-revocation purge jobs. Both producers share the process-wide BullMQ Redis pool, but independent Workers prevent a long sweep from consuming customer concurrency. `MAINTENANCE_WORKER_CONCURRENCY` is closed to 1..4 (default 2); invalid values fall back to 2.

`packages/engine/src/maintenance-jobs.ts` is the closed maintenance catalog and dispatcher. At boot, each recurring scheduler is first registered on `maintenance-jobs`; only a successful replacement allows removal of the same queue-local scheduler id from `workflow-nodes`. The workflow worker retains the same dispatcher solely to drain jobs already materialized by an older deployment. Consent-revocation purge status/cancel/reschedule operations inspect both queues during this compatibility window, while all new purge jobs publish only to maintenance. Unknown maintenance jobs fail unrecoverably instead of falling through to node payload parsing. Graceful shutdown drains both Workers before closing Redis, metrics, and tracing resources.

Queue pressure is independently observable: Prometheus exports `workflow_queue_waiting_jobs` / `_active_jobs` and `maintenance_queue_waiting_jobs` / `_active_jobs`; admin `GET /system/queue` preserves the workflow snapshot at the top level and adds `maintenance`, which may independently be `null`. Public `GET /health` still reveals only `{ queue: { degraded } | null }`, with `degraded` true when either available lane exceeds its own threshold. Operations renders both admin signals. Bounded observability clients import queue names from the side-effect-free `queue-names.ts` and never import the delivery connection owner.

## Scheduler

**Scheduler:** the `schedule` node type fires runs on a cron expression. Persistent state lives in `schedule_entries` (id / orgId / workflowId / workflowVersionId / nodeId / cronExpression / enabled / lastRunAt / lastRunId), unique on `(orgId, workflowVersionId, nodeId)`. Trigger mechanism is BullMQ 5's `upsertJobScheduler` API keyed by the deterministic id `schedule:<orgId>:<workflowVersionId>:<nodeId>`. Version-write sync (`syncWorkflowSchedules` in `packages/engine/src/schedule-scheduler.ts`) runs outside the save or rollback transaction and is idempotent — a commit → register crash recovers via the next version write or the worker's cold-start `replayAllScheduleEntries()` (awaited before the BullMQ `Worker` constructor at boot). Pause/resume is in-band: re-save the workflow with `schedule.config.enabled = false` (and back to `true` to resume); there is no separate pause/resume endpoint. Workflow delete is `DELETE /workflows/:id` (Open/Closed routing, single registry entry, SOFT-deletes by setting `workflows.deletedAt`, unregisters every BullMQ scheduler, and keeps `workflow_versions` + `workflow_metadata` for `POST /workflows/:id/restore`; orphaned `runs` / `audit_logs` rows are tolerated since `workflow_version_id` is a text column with no FK). The version-write chokepoints (`POST /workflows/save` and `POST /workflows/rollback`) also reject tombstoned workflows with `workflow_not_found`, so writes do not append hidden versions; restore first. The web soft-delete loop is the Flows-list Delete action plus a Trash toggle backed by `GET /workflows/trash` (read-only, org-scoped, `deletedAt DESC`, capped by the retention-bounded set) and per-row Restore. The `system:retention` sweep later hard-purges workflows whose tombstone is older than `retention.deletedWorkflowsDays`, plus their versions + metadata. Scheduler-entry worker reads (`getScheduleEntryById` / `listAllEnabled`) require an active parent workflow, so a stale `schedule_entries` row left behind by a teardown blip can't re-run a tombstoned workflow. The trigger handler (`handleScheduleTrigger`) reads `orgId` from the PERSISTED `schedule_entries` row via `getScheduleEntryById` — never from the BullMQ payload — so a spoofed payload can't cross-tenant trigger another org's workflow; stale cleanup when the row is gone removes only the BullMQ `repeatJobKey` attached to the actual scheduler job, not `orgId` / `workflowVersionId` / `nodeId` hints from `job.data`. Cron parsing goes through `cron-parser` 4.x via the shared `validateCronExpression` helper, applied at three layers (workflow-validation rule `schedule_invalid_cron`, `syncWorkflowSchedules` skip-on-invalid, executor `resolveScheduleConfig`). Don't bypass `upsertJobScheduler` / `removeJobScheduler` by calling `workflowQueue.add(..., { repeat: ... })` directly — the scheduler module owns the lifecycle. AI generation does NOT include `schedule` in `AiGenerationWorkflowSchema` — the 11/20 node-type cap is preserved; operators promote a `noop` placeholder via the inspector, same pattern `multi_agent` / `wait_until` / `webhook` / `agent_reflection` / `router_llm` / `subworkflow` / `parallel_fork` / `join` use. **Global cron jobs** (non-tenant recurring tasks like the memory retention sweep — `packages/engine/src/memory-retention-scheduler.ts`) use the reserved `system:` id prefix to distinguish them from per-tenant `schedule:<orgId>:...` ids; the memory-retention sweep registers at worker boot via `registerMemoryRetentionScheduler()` and reads `JANUSLY_MEMORY_RETENTION_CRON` from env (default `0 3 * * *` UTC, validated via the shared `validateCronExpression` with warn-fallback to default on parse failure). The handler calls `deleteExpiredMemory({})` and never throws — a Postgres outage during the sweep logs but doesn't compound via BullMQ retries; the next daily fire is the natural retry because the WHERE clause is idempotent. The repo's existing per-org `memory.retention.purged` audit chokepoint is the canonical observable signal — operators read absence-of-row as the failure indicator. **Two sibling retention sweeps** live alongside `memory-retention-scheduler.ts` for the other unbounded append-only tables: `packages/engine/src/audit-logs-retention-scheduler.ts` (default cron `0 2 * * *` UTC env `JANUSLY_AUDIT_LOGS_RETENTION_CRON`, default 730-day retention env `JANUSLY_AUDIT_LOGS_RETENTION_DAYS` clamped `[30..3650]`) and `packages/engine/src/scim-events-retention-scheduler.ts` (default cron `0 4 * * *` UTC env `JANUSLY_SCIM_EVENTS_RETENTION_CRON`, default 90-day retention env `JANUSLY_SCIM_EVENTS_RETENTION_DAYS` clamped `[7..365]`). Both share the same shape as the memory sweep: reserved `system:<name>-retention` id, cron validated via `validateCronExpression` with warn-fallback to default on parse failure, retention days clamped to the documented range with warn-fallback when out-of-range or non-numeric (so a typo like `5` lands on the default, not five days). The repo helpers in `packages/data/src/auditLogsRepo.ts` (`deleteExpiredAuditLogs`) and `packages/data/src/scimProcessedEventsRepo.ts` (`pruneOldProcessedEvents`) batch the DELETE in 10k-row chunks via `DELETE FROM <table> WHERE <pk> IN (SELECT <pk> FROM <table> WHERE <ts> < $cutoff LIMIT 10_000) RETURNING <pk>` — each batch is its own short transaction so a sweep on a 10M-row table never holds a long lock. A `maxBatches=1000` runaway-safety cap (= 10M-row ceiling per fire) prevents a misconfigured cutoff from spinning forever; the cap state lands in the audit metadata as `cappedByMaxBatches: true` so operators see when one fire ran out of budget. Each handler writes exactly one system-sentinel audit row per fire (`audit_logs.retention.purged` / `scim.event_log.retention.purged`) with `orgId: "system"`, `userId: null`, `metadata: { rowsDeleted, cutoffAt, runtimeMs, retentionDays, cappedByMaxBatches }`. **Per-org configurable retention sweep** is built ON TOP of those three standalone sweeps — `packages/engine/src/retention-scheduler.ts` (reserved `system:retention` id, default cron `0 5 * * *` UTC env `JANUSLY_RETENTION_CRON`, after the 02:00/03:00/04:00 sweeps) walks `listOrgIdsForRetention()` and purges SIX tenant data families (`run_events` / `usage_events` / `audit_logs` / `recovery_feedback` / `memory_entries` / soft-deleted `workflows`) per org against that org's `org_configs.retention.*` bounds (new `retention` category: `runEventsDays` 7..365/90, `auditLogsDays` 30..730/365, `usageEventsDays` 30..365/90, `recoveryFeedbackDays` 30..365/180, `memoryEntriesDays` 7..730/90, `deletedWorkflowsDays` 1..365/30; env fallbacks `JANUSLY_RETENTION_*_DAYS`; the narrow `getRetentionPolicyConfig(orgId)` reader re-clamps a stored out-of-range value back to the catalog default). The append-only repo helpers (`packages/data/src/retentionRepo.ts` — `deleteExpired<Table>ForOrg`) reuse the same 10k-batched-DELETE + `maxBatches` 1k-cap shape but carry `org_id = $orgId` per the multi-tenant invariant AND a per-row **legal-hold bypass** conjunct `(hold_until IS NULL OR hold_until <= now())` — every append-only table in this sweep has an additive nullable `hold_until timestamptz` column for this (a future-dated value exempts the row from the sweep). `run_events` has no org column so it scopes through the parent `runs.org_id` via a join. Soft-deleted workflows are the exception: the helper purges by `deleted_at` after the restore window, and uses one atomic deferred-cascade statement so a crash cannot leave a restorable tombstone without its versions. Unlike the cross-org siblings this sweep is per-ORG: one `retention.purged` audit row per org per fire with the real `orgId` + a per-table breakdown; a per-table or per-org failure is isolated (the loop continues). An **export-before-delete** DI seam (`setRetentionExporter` / `runRetentionExport`) lets an operator wire an archiver that runs BEFORE each org's purge — best-effort, a thrown exporter degrades to a warn and the purge proceeds. Adding an append-only table to this sweep means a new `deleteExpired<Table>ForOrg` helper + a `RETENTION_TARGETS` entry + a catalog key + (if the table lacks one) a `hold_until` column; adding a recoverable tombstone family instead needs an atomic deferred-cascade helper keyed by the tombstone timestamp. **Consent-revocation bulk purge** lives in the sibling `packages/engine/src/memory-purge-scheduler.ts` — a one-shot delayed BullMQ job (deterministic `memory-purge-<sha256(orgId)>` id because `Queue.add` custom ids reject colons, 7-day delay from `JANUSLY_MEMORY_PURGE_DELAY_MS` env with positive-integer validation + warn-fallback) scheduled by an awaited bounded call from `apps/api/src/routes/org-routes.ts` on every `memory.enabled` true→false flip AFTER the `memory.consent.revoked` audit fires, and cancelled by an awaited `cancelPendingMemoryPurge` BEFORE the `memory.consent.granted` audit fires (the boolean result rides the audit metadata as `pendingPurgeCancelled`). `GET /memory/consent-status` (`viewer` + `recovery.read`, with a `/v1` alias) projects the effective two-flag consent plus the deterministic job state as `none` / `scheduled` / `running` / `unknown`; Redis failures become `unknown` and never expose queue keys or raw infrastructure errors. The handler re-reads `org_configs.memory.enabled` at fire time and SKIPS the purge when consent was re-granted — cancellation is best-effort, the handler's consent re-check is the load-bearing safety. `schedulePendingMemoryPurge` removes any existing job FIRST before adding the new one (rapid revoke-grant-revoke cycles converge cleanly); the schedule + cancel + handler all NEVER throw and queue calls are bounded, so a Redis blip returns false/logs without hanging the config route or wiping data (manual `purgeMemoryForOrg(orgId)` REPL fallback documented) and a Postgres outage on fire degrades to a warn log. Adding a new global cron-style job (not consent-driven) means another `system:`-prefixed module mirroring `memory-retention-scheduler.ts`; adding a new consent-driven delayed job means another module mirroring `memory-purge-scheduler.ts` plus a `maintenance-jobs.ts` catalog/dispatch entry + a route-side schedule/cancel call. **Stalled-node reaper** (`packages/engine/src/stalled-node-reaper.ts`, reserved `system:stalled-node-reaper` id, default cron `*/5 * * * *` env `JANUSLY_STALLED_NODE_REAPER_CRON`) is the recovery mechanism for the one failure the atomic claim can't self-heal: a worker that dies (kill -9 / OOM / eviction) mid-node leaves the `run_nodes` row `running`, and because the redelivered BullMQ job's `claimNodeForExecution` only matches an exact `queued` generation, the claim fails → the node stays `running` forever and `updateRunStatusFromNodes` is never called again, so the run is stuck non-terminal with NO DLQ row, recovery item, or terminal signal (a silent break of the recoverability + observability promises). The sweep (`findStalledRunningNodes` in `packages/data/src/stalledNodesRepo.ts` — production runs only via `replay_mode IS NULL`, non-terminal parent run, oldest-first, capped at `STALLED_NODE_REAPER_LIMIT = 500`) finds nodes `running` past `JANUSLY_STALLED_NODE_THRESHOLD_MINUTES` (default 60, clamped `[15..1440]` — the floor keeps an operator from reaping a legitimately long node; the threshold matches on `started_at`, NOT the BullMQ lock, so it must exceed any single legitimate node execution) and per node calls `DeadLetterQueueAdapter.persistStalledTerminalFailure`: the adapter reconstructs the optional replay payload from `runs.input_json.workflow`, then commits the `running → failed` CAS, optional DLQ row, `node.failed` event (`reason: "worker_stalled"`), and first parent `run.failed` transition in one transaction. Concurrent replicas and a node that just finished lose the CAS cleanly; a missing or unparseable legacy snapshot still terminates the node and run atomically, but without a replay surface. The node is failed-into-DLQ, NOT auto-re-executed (a stalled node may have already run a non-idempotent side effect — the operator decides on replay, same as every other DLQ entry). One `run.stalled_node.reaped` system-sentinel audit row per fire that found work (skipped on the healthy `scanned === 0` path to avoid 5-minute spam). Same never-throws boot + handler posture as the retention sweeps; the pure `reapStalledNodes(deps, config)` core is DI-tested. Solution Pack worker-interruption drills create one threshold-old claim and pass an exact `{ orgId, runId }` scope into the same scan, proving the production boundary without killing a process or touching unrelated work; the response and audit retain bounded measured scan/reap/DLQ evidence. **Supervised auto-healing** runs as a sibling cron pair in the **API process** (NOT the engine worker) because the per-candidate handler calls `patchEnvelopeForNodeType` + `applyConfigPatchToWorkflow` which live in `apps/api`; both jobs share a dedicated `auto-healing-system` BullMQ queue + Worker booted from `apps/api/src/auto-healing-bootstrap.ts` only when `JANUSLY_AUTO_HEALING_ENABLED=true`. Scanner (`system:auto-healing-scanner`, default `0 */6 * * *` env `JANUSLY_AUTO_HEALING_SCAN_CRON`) walks `org_configs.autoHealing.enabled = true` orgs, clusters recent DLQ samples, gates each candidate on loop breaker + budget + idempotency, calls `suggestWorkflowPatch`, merges via `applyConfigPatchToWorkflow` / `applyStructuralPatchToWorkflow`, and enqueues sandbox validation via `replayDeadLetterAsValidation`. Watcher (`system:auto-healing-watcher`, default `* * * * *` env `JANUSLY_AUTO_HEALING_WATCH_CRON`) polls validating rows, compares the new failure signature against the original (signature_changed defense), and on success + `isAutoApplyAllowed` replays against the patched workflow with `decisionActor: "auto"`. The auto-apply path is double-gated: both `JANUSLY_AUTO_HEALING_AUTO_APPLY=true` AND `org_configs.autoHealing.autoApply=true` must be set; defaults leave validated rows pending operator decision via `POST /auto-healing/:id/decide`. Both that route and the watcher use a CAS-style `recordDecision` (`UPDATE … WHERE status='validated'`) so concurrent operator-click vs auto-apply cannot double-apply — loser returns 409 `signature_already_resolved`. Two-hour stale-row sweep auto-declines stuck `validating` rows with reason `validation_timeout`. Schedule + cancel + handler all NEVER throw; an LLM fallback skips the candidate (records `scanner_error:llm_fallback:<aiError>`) rather than persisting a 0-confidence row. Loop breaker is configurable per-org via `autoHealing.maxAttemptsPerSignature` (default 3) + `autoHealing.loopWindowDays` (default 14). Audit actions: `auto_healing.diagnosed` / `.proposed` / `.validated` / `.applied` / `.declined` / `.failed` / `auto_healing.decline.manual` / `auto_healing.scan.triggered`. Permissions: `autohealing.read` (viewer+) and `autohealing.decide` (editor+). The web surface is a single new `AutoHealingPendingCard` mounted inside the existing DLQ panel — no new top-level UI panel, no new sidebar entry. Adding a new auto-healing decline reason means an entry in `AUTO_HEALING_DECLINE_REASONS` + a branch in the scanner or watcher that records it; the row's `declineReason` column carries the closed enum verbatim. **Cron observability** rides on the SAME persisted shape: `GET /workflows/:id/schedule-history` (viewer, `workflows.read`, read-only — no audit) returns a 90-day UTC day-of-week × hour-of-day heatmap of scheduled fires plus a next-N-fires preview. There is NO trigger-node-id column on `runs`; a scheduled run is identified by the `input_json -> 'input' ->> 'triggeredBy' = 'schedule'` marker that `start-run` persists for cron fires (`handleScheduleTrigger`'s `input: { triggeredBy: "schedule", scheduleEntryId, nodeId, triggeredAt }`) — `packages/data/src/scheduleHistoryRepo.ts:queryScheduleFires` joins `runs` through `workflow_versions` (tenant + workflow scope) on that marker, window-clamped to `[1,90]` days + row-capped at ≤1000. Don't rename or drop that marker without updating the query — the heatmap silently empties otherwise. Bucketing + the cron-preview are pure (`packages/engine/src/schedule-history.ts`, lives in engine for the `cron-parser` dep; `computeNextFires` is DST-safe and degrades to `[]` on a malformed cron, never throws). The web `ScheduleHistoryPanel` renders a HAND-WRITTEN SVG heatmap (no charting dep) in the Inspector right panel; anomaly red dots use the documented seam (`cell.anomaly: false` rides the response today, no overlay yet).

**Unsaved schedule preview:** the Inspector previews the next three fires through contracted `GET /v1/workflows/schedule-preview?cron=...` (`viewer` plus `workflows.read`). The route is stateless and performs no database read or audit write; it first applies the runtime's canonical five-field `validateCronExpression` gate, then delegates DST-safe fire calculation to `computeNextFires`. The response contract is a dependent union: `valid: true` carries exactly three ISO instants, while `valid: false` carries an empty list. An empty input remains a local guidance state without a request, malformed expressions return an invalid preview, and the web localizes valid instants in the operator's locale/time zone. The browser request is debounced, abortable, generation-guarded, and keyed to both the normalized expression and activation lifecycle so a previous result cannot render against a newer edit or re-enabled schedule. Grammar failures set the associated input's `aria-invalid`; transport failures remain a distinct retryable state. Keep this parser server-side: do not add a second cron dependency to the web bundle.

## Delayed waiting checkpoints

**Approval deadlines:** `approval` accepts no deadline (the backward-compatible indefinite wait), a positive relative `decisionTimeoutMs`, or an absolute `until` instant with an explicit timezone. `decisionTimeoutMs` is separate from the universal executor `timeoutMs`, which keeps its existing execution-cancellation meaning. Before returning, the executor installs an immediate BullMQ `approval-deadline-arm` watcher; the runtime then materializes a relative `deadlineAt` from the SAME checkpoint clock as `waitingSince`, after the Redis write succeeds, so queue latency cannot consume the operator's window. The watcher schedules the exact delayed `approval-timeout` generation only after the node is waiting. If it arrives while the node is still `queued` / `running`, it requeues the durable handoff without a finite status-attempt gap until the node leaves execution (the stalled-node reaper bounds a crashed `running` row). Handler infrastructure failures use exponential BullMQ retries. Once waiting, the persisted `{ kind: "approval", decisionTimeoutMs?, deadlineAt, onTimeout, escalateTo? }` metadata is authoritative. `failWaitingApprovalNode` and `escalateWaitingApprovalNode` update only a still-waiting approval whose exact `deadlineAt` matches and whose `timeoutState` is absent. The fail/automatic-reject path locks the parent run and commits the node failure, policy event, `runs.status = "failed"`, and `run.failed` event in one transaction; a terminal/cancelled parent rejects the claim. That generation-bound CAS makes duplicate or stale jobs lose cleanly to manual resume, cancellation, replay, or later metadata. `escalate` atomically changes `assignee`, records `timeoutState: "escalated"`, emits enough waiting state for healthy SSE clients to patch live, and remains waiting. `assignee` is operator-visible routing metadata, never ACL; `/resume` keeps its existing editor authorization. Do not replace the exact persisted-deadline guard with a payload-only decision or split the terminal run transition from its node transition.

**Absolute waits:** `wait_until` accepts exactly one of positive ISO duration `duration` or timezone-qualified absolute `until`. Both forms resolve through `resolveWaitUntilSchedule` to one persisted `wakeAt`; elapsed absolute instants use zero delay. Its delayed `wait-resume` job uses the same no-finite-gap execution-to-waiting bridge and infrastructure retry posture as approval deadlines. The handler remains idempotent and manual resume may win before delivery. Both waiting families validate calendar fields and JavaScript Date range before scheduling, so impossible dates are rejected rather than normalized by `Date.parse` and oversized relative values cannot throw during ISO serialization.

**Overdue-checkpoint reconciliation:** finite job retries are not the final durability boundary. `packages/engine/src/waiting-checkpoint-reconciler.ts` registers the reserved `system:waiting-checkpoint-reconciler` once-per-minute scheduler. Each fire atomically claims at most 500 `waiting` nodes under a still-`running` parent whose approval `deadlineAt` or timer `wakeAt` is already due; escalated approvals are excluded. The claim uses `FOR UPDATE OF run_nodes SKIP LOCKED`, persists a two-minute `waiting_repair_after` lease, and orders unclaimed rows first. Consequently, a poisoned first batch cannot be selected forever or starve later checkpoints, concurrent workers do not claim the same generation, and a worker crash becomes retryable after the lease. The partial composite index `run_nodes_waiting_target_idx` covers `(waiting_repair_after NULLS FIRST, COALESCE(deadlineAt, wakeAt), run_id, node_id) WHERE status = 'waiting'`; its migration includes a concurrent `production-rollout.sql`. The sweep recreates the appropriate immediate job per row with fault isolation. A duplicate race with the original delayed delivery is harmless because approval execution checks the exact deadline generation and timer resume checks the current waiting status. This repairs Redis job loss and exhausted infrastructure retries without scanning future jobs on every cadence. Keep the claim bounded, leased, fairly ordered, and parent-run scoped; do not replace it with a read-only scan or remove the final handler CAS.

## Node queue publication repair

**Postgres→BullMQ outbox:** every transition to an executable `pending` or `queued` generation sets `run_nodes.queue_publication_repair_after` before `Queue.add`; only a successful Redis acceptance clears it. `run_nodes.queue_publication_generation` identifies the physical delivery: a producer retry reuses it, while a job consumed against a failed run returns to `pending` and increments it before republishing. Node jobs use `buildExecuteNodeJobId`, a deterministic SHA-256 id over `(runId, nodeId, attempt, recoveryClaimToken, publicationGeneration)`, so one publish is idempotent without colliding with an old active/completed job when a genuinely new delivery is required. Retries set the marker to their future backoff eligibility rather than `now`, preventing the repair loop from executing them early. `claimNodeForExecution` locks the parent `runs` row before `queued → running`; if it consumes an exact generation while that run is failed, it restores the node to `pending` with the attempt/token and marker intact, serializing safely with concurrent subworkflow reattachment.

Initial run constructors publish through `publishInitialNode` only after their Postgres transaction commits. That call is a non-throwing latency fast path: an enqueue or acknowledgement failure leaves the exact marker intact and still returns the committed run to the caller, preventing an infrastructure retry from creating a second run. The reconciler remains the durability boundary. A failed optional `node.queued` timeline append is logged after queue acknowledgement but does not turn an executable run into a caller-visible failure. Runtime-owned retry publication remains throwing because the owning BullMQ delivery supplies its own retry boundary.

`packages/engine/src/queue-publication-reconciler.ts` registers `system:queue-publication-reconciler` every minute. A fire claims at most 500 compact due rows under still-`running` parents via `FOR UPDATE OF run_nodes SKIP LOCKED`, advances each marker by a two-minute lease, directly republishes exact `queued` generations, and groups `pending` repairs by run before loading, processing, and releasing one workflow snapshot at a time while rerunning DAG readiness. Per-generation/run fault isolation leaves failures eligible after the lease. The partial `run_nodes_queue_publication_repair_idx` covers only marked `pending`/`queued` rows; its migration includes a concurrent production rollout for the append-heavy table. This protocol is not mixed-worker compatible: pause ingress and fully drain every pre-outbox API/worker before applying `production-rollout.sql` with its explicit acknowledgement, then deploy the new fleet in full before resuming. Keep the marker-before-publish/clear-after-acceptance ordering, deterministic generation id, attempt CAS, parent-run scope, cap, lease, and final execution CAS; never substitute a best-effort callback or fixed delay as the durability boundary.

## Subworkflow terminal handoff repair

Every linked child-run transition with `parent_link_kind='subworkflow'` to `succeeded`, `failed`, or `cancelled` writes a millisecond-precision `runs.parent_notification_after` in the same update as the terminal status. Replay Lab/validation source lineage uses `parent_link_kind='replay'` and is excluded, while a genuine subworkflow invoked inside validation keeps the executable kind plus inherited `replay_mode='validation'`, so it remains sandboxed and still completes its validation parent. The immediate notifier clears this marker only after the exact parent checkpoint is settled: success completes or reattaches the matching child generation and reruns DAG readiness; failure/cancellation fails the matching wait and reruns the parent status rollup, even when another sibling already made the parent failed. Successful parent-node state persists `state_json.subworkflow.childRunId`, allowing a retry after the node CAS but before readiness to verify the handoff it is repairing. A recovery replay atomically clears the obsolete terminal marker while reopening the child, reopening a nested parent clears that parent's old marker, and parent-node CAS predicates also require the child still has the delivered terminal status.

`packages/engine/src/subworkflow-terminal-reconciler.ts` registers `system:subworkflow-terminal-reconciler` every minute. Each fire claims at most 500 due production child rows through `FOR UPDATE SKIP LOCKED`, advances `parent_notification_after` by a two-minute lease, and passes that exact lease timestamp through delivery and acknowledgement while retrying each child independently. Only a fully settled handoff acknowledges the same status+marker generation; a false result, thrown dependency call, worker crash, or crash between parent-node CAS and readiness/rollup leaves it eligible after the lease. The partial `runs_parent_notification_idx` covers only marked rows and is built concurrently by the same stop-the-world production rollout as the node-publication index. Keep the status flip and marker atomic, the claim bounded/leased, the child-status and child-id checks exact, and the post-CAS readiness/rollup repair idempotent.

`packages/engine/src/workflow-rollout-reconciler.ts` registers `system:workflow-rollout-reconciler` every minute. The immediate terminal observer attempts rollout accounting before other terminal side effects, but never unwinds a committed run when that side-channel fails. The sweep therefore lists at most 500 oldest terminal production runs tied to an active rollout and lacking a `workflow_rollout_outcomes` receipt, then reuses `recordWorkflowRolloutOutcome` with per-run fault isolation. The receipt's run-id primary key plus transactional aggregate update makes duplicate/concurrent repair harmless. Finished rollouts are deliberately frozen and excluded. Scheduled canary allocation is keyed by BullMQ's stable delivery job id and retains the job's original timestamp, so a retried tick cannot drift between variants. Keep this repair bounded, exclude validation/replay runs, and never replace the stable delivery identity with handler wall-clock time.
