## DLQ

**DLQ:** every failed node beyond `retryPolicy.maxAttempts` lands in `dead_letters`. Replay via `POST /dlq/replay`. The Operations card in Runs surfaces counts and filters. `BullMQQueueAdapter` composes `DeadLetterQueueAdapter` so DLQ insertion is part of the queue contract — don't bypass it. **The recovery queue filters + sorts SERVER-SIDE** so the result is cap-correct: `GET /dlq` accepts `status` (on `dead_letters`) + `owner` (`me`→`auth.userId`) + `severity` + `search` (case-insensitive substring over node id / run id / `error_json->>'message'`, ≤100 chars, LIKE-escaped via the shared `escapeLikePattern`, applied before the cap like the other filters) + `sort` (`newest`/`oldest`/`severity`/`sla`) and routes through `listRecoveryQueue` (`apps/api/src/dlq.ts`), a `dead_letters` LEFT JOIN `recovery_items` (on `(orgId, deadLetterId)`) that applies the filter + ORDER BY BEFORE the 200-row cap (`DLQ_LIST_MAX_LIMIT`) and folds the recovery overlay (severity/owner/SLA/status/comments…) INLINE onto each row — so a P1 older than the newest 200 surfaces under a severity filter, and the panel renders from ONE cap-correct fetch (no separate `/recovery/items` overlay call). An `owner`/`severity` filter excludes a dead letter with no recovery item (its LEFT-joined columns are null → no match); `severity`/`sla` sorts push no-recovery-item rows last (`NULLS LAST`) with a `createdAt desc` tie-break. `GET /dlq` with no params preserves the existing newest-first default page (100 by default, 200 max via `limit`; the inline `recovery` field is additive and ignored by legacy callers), so the Recovery Center home preview remains behavior-compatible. The web `useRecoveryQueueFilters` hook OWNS this fetch (filter/sort state + localStorage persistence); `DeadLettersPanel` takes no `deadLetters` prop. **Keyset ("load more") pagination** lives on the sibling `GET /dlq/queue` route (registered BEFORE the `/dlq` wildcard, first-match-wins): it routes through `queryRecoveryQueuePage` (the SAME join, over-fetching `pageSize+1` through `listRecoveryQueue` then folding via the pure `buildRecoveryQueuePage`) and returns a `{ items, nextCursor, hasMore }` envelope. The cursor is an opaque `base64url(JSON)` `{ sort, createdAtIso, id, leadKey|null }` (a plain `(createdAt,id)` keyset for `newest`/`oldest`; a COMPOSITE `NULLS LAST` keyset for `severity`/`sla` where the lead key is the severity text / slaTargetAt ISO / `null` for the no-recovery-item tail) — `decodeRecoveryQueueCursor` is defensive (malformed / sort-mismatch / corrupt sla key → `null` → page 1, mirroring `parseEventsCursor`); every `recoveryQueueOrderBy` branch ends with a `deadLetters.id` tie-break for a stable total order. The cursor is UNSIGNED but org-scope is re-applied independently of it, so a tampered cursor can only reorder the caller's own page (never cross-tenant). **Bare `/dlq` stays a back-compat ARRAY** (no envelope, no cursor) for the Recovery Center home preview + the MCP `dlq.list` consumers; only `/dlq/queue` paginates. The hook's `loadMore()` appends pages (with a request-epoch guard against a stale append) and resets to page 1 on any filter/sort/refresh change; `DeadLettersPanel` renders a "Load more" button below the virtual list. **The mini-grid (Total/Open/Retried/Resolved) + the card warning stripe read a THIRD sibling route `GET /dlq/counts`** — `countDeadLettersByStatus(orgId)`, a single org-scoped `GROUP BY status` folded to `{ total, open, replayed, resolved }`, deliberately UNSCOPED by owner/severity/status (it is the whole-queue health summary, NOT the filtered page — restores the pre-ENG-222 semantics). The hook fetches it in a SEPARATE effect keyed ONLY on `[platformVersion, refreshNonce]` (NEVER refetched on a filter/sort change — that's the point), and the warning stripe keys off `counts.open > 0`. So the panel makes two server reads: the filtered/paginated `/dlq/queue` list + the org-wide `/dlq/counts` summary. Adding a recovery-queue sort key means extending `RECOVERY_QUEUE_SORTS` (api) + the web `SORT_KEYS` in lockstep AND adding its keyset branch to `recoveryQueueKeysetPredicate`. **List rows are SUMMARY projections:** `listRecoveryQueue` deliberately excludes `workflow_json` / `node_json` (persisted with `maxBytes: Infinity` for replay fidelity — a 200-row page would otherwise ship 200 unbounded workflow snapshots) and instead carries cheap `nodeType` (`node_json->>'type'`) + `workflowName` (`workflow_json->>'name'`) projections; the full row comes from the `GET /dlq?id=` detail read (`getDeadLetter`), which the web fetches on row selection / before opening the Recovery dialog (the summary row is the graceful fallback while the detail loads). Don't reintroduce full-column selects on the list path.

## Run-explain reports

**Run-explain reports:** `GET /reports/run-explain?runId=…&format=markdown|json` (`role: "viewer"`) returns a downloadable artefact built by `buildRunExplainReport` (`packages/engine/src/run-explain-report.ts`) — `RunExplainReportJson` envelope plus a sibling Markdown rendering. Multi-tenant gate on the `runs` lookup (`eq(runs.orgId, auth.orgId)`); cross-org and missing-id return a uniform 404 (no enumeration leak). Filename pattern is `janusly-<workflow_or_run>-<status>-<YYYY-MM-DD>-<short_id>.<ext>` via `buildReportFilename`, with both ASCII `filename="…"` and RFC 5987 `filename*=UTF-8''…` forms in `Content-Disposition` plus `Access-Control-Expose-Headers: Content-Disposition` so the web's `downloadFromApi` helper can read the name. Audited as `report.run_explain.exported`. Delivery surface — `POST /reports/run-explain/deliver` (`role: "editor"`, `"reports.deliver"` rate-limit bucket, default 60/min/org) — reuses the same `buildRunExplainReport` helper and dispatches via `executeTool` to one of `slack.post` / `github.create_issue` / `webhook.send`. Per-destination translation lives in `buildSlackText` / `buildGitHubTitle` / `dispatchDelivery` in `apps/api/src/routes/reports-routes.ts`: Slack receives a header + Root cause + Failed node + Next action lines truncated below the 3000-char per-block cap (with a Full-report footer when `JANUSLY_PUBLIC_APP_URL` is set), GitHub receives the full Markdown as the issue body, the webhook receives the structured `RunExplainReportJson` signed via the existing Stripe-style HMAC path. Per-`kind` required fields are enforced via Zod `superRefine` — the body shape stays a single non-union object (no discriminated union). Failures (missing credential, rate-limit reject, upstream non-2xx, network blip) NEVER throw — the route returns `{ ok: false, error, ... }`. Generic `"credential secret missing for <credentialName>"` errors from the tool chokepoint are propagated verbatim; the env-var name is NEVER echoed. Audit row `report.run_explain.delivered` is written on BOTH success AND failure with `{ destination, format, ok, statusCode, error, latencyMs, runId, workflowId, workflowName, runStatus, credentialName }` (`format` is `markdown` for Slack/GitHub and `json` for webhook; `credentialName` is the operator-visible identifier, not the env-var; `safePersistPayload` redacts anything secret-shaped on top). No new vendor SDK, no new credential kind — Slack URL / GitHub PAT / shared webhook secret reuse the existing `slack_webhook` / `github_token` / `webhook_secret` kinds. Don't bypass `executeTool` from the route; the per-tool chokepoint owns the inner per-tool rate-limit bucket (`tool.slack.post` / `tool.github.create_issue` / `tool.webhook.send`), credential lookup, usage events, and the SSRF / body-cap / timeout guards via `fetchHttpTarget`. The route's `writeSide` posture is by design distinct from the runtime workflow `dryRun` gate — the route runs outside a workflow run, so the rate-limit + credential + audit gates are the right safeguards at this layer.

## Audit evidence export

**Audit evidence export:** `POST /recovery/items/:id/evidence?format=json|markdown` (`role: "editor"` AND `permission: "recovery.read"` — registry requires both) returns ONE downloadable artefact per incident built by the pure `buildRecoveryEvidenceReport` (`packages/engine/src/recovery-evidence-report.ts`) over the snapshot bundle from `resolveRecoveryEvidence` (`packages/data/src/recoveryEvidenceRepo.ts`, the ONLY chokepoint that reads the evidence sources — recovery item → DLQ row → original run + nodes + bounded events → most-recent `replayMode="validation"` run → audit rows scoped to the run/DLQ/item ids → prior `workflow_versions` for the rollback link; multi-tenant on every read, null item short-circuits with a uniform 404). The builder REUSES `buildRunExplainReport` for the run summary + timeline (don't fork run rendering) and `computeWorkflowDiff(dlq.workflowJson, validationRun.inputJson.workflow)` for the selected patch diff; it scrubs every rendered free-form string through `scrubSecretShapes` as defense-in-depth on top of the write-time `safePersistPayload` redaction, and stamps the nested run block with the envelope's `generatedAt` so two exports are byte-identical. Download filename + dual-form (`filename=` ASCII + RFC 5987 `filename*=`) Content-Disposition come from the SHARED `apps/api/src/report-download.ts` helpers (`slugify` / `buildReportFilename` / `contentDispositionAttachment`, also used by `/reports/run-explain` + `/reports/value-dashboard` — don't re-inline them). Audited as `report.evidence.exported` (metadata never echoes the env-var behind a secret). No new table; the artefact is pure composition over existing rows. The web `RecoveryItemDrawer` exports it via `downloadFromApi(path, { method: 'POST' })` — read-only, no `bumpPlatformVersion`. **Delivery sibling:** `POST /recovery/items/:id/evidence/deliver` (same `role: "editor"` + `permission: "recovery.read"`, reuses the `reports.deliver` rate-limit bucket) dispatches the SAME report to Slack / a GitHub issue / a signed webhook through the shared `apps/api/src/report-delivery.ts` layer (`deliverDestinationSchema` + `refineDeliveryDestination` + `dispatchReportDelivery` → the `executeTool` chokepoint), which `POST /reports/run-explain/deliver` now ALSO uses — one source of truth; don't re-inline the dispatch. NEVER throws (missing-credential / non-2xx / network → `{ ok: false, error }`, the env-var behind the credential NEVER echoed); audited as `report.evidence.delivered` on BOTH success AND failure. The web reuses the generalized `ReportDeliveryDialog` (an `endpoint` + `copyKeys` prop point it at either deliver route) from the drawer's evidence section. Distinct from `/recovery/items/:id/handoff` (a short incident notification, not the full forensic report).

## Recovery alerting

**Recovery alerting:** org-scoped policies fan events into Slack / webhook / email / GitHub. Six closed-enum triggers: `dlq.entry_created` / `failure_cluster.threshold` / `budget.blocked` / `limiter.degraded` / `workflow.slo_breach` / `approval.stalled`. Persistence is two tables — `alert_policies` (`(orgId, name)` unique, jsonb `parameters` per-trigger, jsonb `channels` array referencing existing `credentials` rows — no new credential kind) + `alert_dispatches` (cooldown state + recent-feed source; suppression rows DO NOT land here, they fire `alert.policy.suppressed` audit only). **The dispatcher** lives in `packages/engine/src/alerts/dispatcher.ts` (NOT `apps/api`) so both API and worker processes can register the same function via the `setAlertDispatcher` DI seam in `@janusly/data/src/alert-dispatch.ts`. The worker bootstrap registers it so DLQ inserts inside the worker process fire alerts immediately. **Delivery** routes through `executeTool` against the existing `slack.post` / `webhook.send` / `email.send` / `github.create_issue` chokepoints — SSRF / DNS-pin / body-cap / rate-limit / usage events / audit / `safePersistPayload` all apply for free. The slack / webhook / github calls go through the shared `@janusly/engine/src/integration-dispatch` invocation helpers (the same ones `dispatchReportDelivery` + the recovery `/handoff` dispatcher use, so each tool's input-arg shape lives in ONE place); `email.send` stays inline (no shared helper). The dispatcher keeps its own wall-clock latency + error-cap + statusCode-truncation mapping. The dispatcher never throws; per-channel failures degrade to `{ ok: false, error, latencyMs }` envelopes and outcome is `delivered` when at least one channel reports ok. **Dedupe** per `(orgId, policyId, dedupeKey)` within `cooldownSeconds` (range 60..86400, default 900); `buildDedupeKey` (`packages/engine/src/alerts/dedupe-key.ts`) is the closed per-trigger key builder. **Per-trigger filtering** (`matchesPolicyFilter`): `dlq.entry_created` honours `errorSignaturePattern` (glob via `matchGlob` in `@janusly/shared/src/alert-pattern` — `*` + `?` only, NO regex, NO ReDoS surface) + `workflowIds` whitelist; `failure_cluster.threshold` honours `minFrequency`; `budget.blocked` honours `scope` + `workflowIds`; `limiter.degraded` honours `buckets`; `workflow.slo_breach` honours `workflowIds` + `metricNames` overlap; `approval.stalled` honours `workflowIds`. **Message composition** is `composeAlertMessage` (`@janusly/shared/src/alert-message`) — a deterministic Markdown template, NOT a prompt, with `scrubSecretShapes` running on string payload values before render (defense-in-depth on top of `safePersistPayload`'s key-redaction upstream). **Event-driven hooks** (3 sites, one line each): `packages/engine/src/adapters/dead-letter-queue.ts` after `db.insert(deadLetters)`, `apps/api/src/budget-gate.ts` after `billing.budget.exceeded` audit, `packages/data/src/rate-limit-degradation.ts` after the `rate_limit.degraded` audit. **State-driven scanner** `apps/api/src/alerts/scanner.ts` handles `failure_cluster.threshold` + `workflow.slo_breach` + `approval.stalled` via a single `system:alerts-scanner` BullMQ scheduler (default `*/2 * * * *`, env `JANUSLY_ALERTS_SCAN_CRON`). Booted behind `JANUSLY_ALERTS_ENABLED=true` from `apps/api/src/alerts-bootstrap.ts` (mirrors `auto-healing-bootstrap.ts` 1:1); the DI seam registration happens unconditionally so event-driven hooks reach the dispatcher even when the scanner Worker is off, but the scanner Worker itself only boots with the env flag on. The `limiter.degraded` trigger is operator-side-only (uses the `orgId: "system"` sentinel — mirrors `rate_limit.degraded` audit conventions); tenant orgs see only the other 5 triggers. Permission catalog adds `alerts.read` (viewer+) and `alerts.write` (admin) under a new `alerts` category. Five audit actions: `alert.policy.{created,updated,deleted,triggered,suppressed}`; `_updated` carries `{ before, after }` for traceability. Five routes (`POST/GET/POST :id/DELETE /alerts/policies`, `GET /alerts/recent`). The codebase's `Route.method` enum is closed to GET/POST/DELETE — `POST /alerts/policies/:id` is the update verb (matches the `/mcp/connections/:alias` POST-as-update convention). The web mounts `AlertPoliciesPanel` + `RecentAlertsCard` in `OperationsPage` Reliability; the policy form swaps its parameters sub-fields based on the selected trigger and filters the channel credential dropdown by destination kind so the operator can't pick a `github_token` credential for a Slack channel. Adding a new trigger means: extend `ALERT_TRIGGERS` + add a Zod params schema + extend `matchesPolicyFilter` + extend `buildDedupeKey` + (for state-driven) extend the scanner; for v2 message-template customization the chokepoint is `composeAlertMessage` — keep secrets scrubbed at compose time, NEVER pass raw payload to a per-channel formatter. The closed-enum trigger list has been extended with `recovery_item.created` (event-driven) and `recovery_item.sla_breached` (state-driven via `scanRecoveryItemSlaBreaches`) — both follow the same per-trigger filter/dedupe-key contract — plus `workflow.schedule_anomaly` (state-driven via `scanScheduleAnomalies` on the same `*/2 * * * *` cron): it walks the org's actively-scheduled workflows (`listScheduledWorkflowIds` = distinct `workflowId` from enabled `schedule_entries`, capped at `SCHEDULE_ANOMALY_MAX_WORKFLOWS = 200`), re-buckets each one's recent fires through the SAME `bucketScheduleFires` aggregator the Inspector heatmap renders (90-day `MAX_HISTORY_DAYS` window), and fires when any day/hour slot is flagged `anomaly` (the baseline-divergence signal `bucketScheduleFires` computes); honours a `workflowIds` allowlist; dedupe-key `schedule:<workflowId>` (per-workflow — one alert summarises all a workflow's anomalous slots). So 9 triggers total today.

## Recovery ownership workflow

**Recovery ownership workflow:** every open DLQ row gets a paired `recovery_items` row (one per `(orgId, deadLetterId)`) tracking `owner` + closed-enum `severity` (`p1`/`p2`/`p3`/`p4`) + `slaTargetAt` + closed-enum `status` (`open` → `acknowledged` → `in_progress` → `waiting_external` → `resolved`, with `reopened` for reflows) + closed-enum `resolutionReason` (`fixed_by_patch` / `rolled_back` / `upstream_fixed` / `accepted_loss` / `not_a_bug` / `sandbox_replay_succeeded`) + append-only `comments` jsonb (cap 200 via `MAX_COMMENTS_PER_ITEM`). **SLA defaults** in `@janusly/shared/src/recovery-item.ts` (`SLA_SECONDS_BY_SEVERITY`): p1=1h, p2=4h, p3=1d, p4=7d; overridable per item via `slaTargetAtOverrideIso` (capped 30 days). **Per-severity targets are org-configurable** via `org_configs.recovery.slaPolicies` — a JSON object of MINUTES keyed by `p1`..`p4` (empty default = the built-in map; partial map allowed, omitted severities keep their default; per-severity range 1..43200min = 30d, matching the per-item override cap). The scoped reader `getRecoverySlaSeconds(orgId)` (`orgConfigRepo.ts`; narrow single-row read, fail-open to defaults) merges the config over `SLA_SECONDS_BY_SEVERITY`; `defaultSlaTargetAt(severity, from, secondsBySeverity?)` takes the merged map (stays pure/zero-I/O) and `createRecoveryItem` / `acknowledgeRecoveryItem` / `escalateRecoveryItem` pass it (an explicit `slaTargetAtOverrideIso` still wins). Unconfigured (empty string) = byte-for-byte the built-in defaults. **State machine** enforced via CAS-style `UPDATE … WHERE status IN (allowed_pre_states)` in `packages/data/src/recoveryItemsRepo.ts` — mirrors `recordDecision` in `autoHealingRepo.ts:264-297`. CAS-loser transitions return HTTP 409 with `{ code: "recovery_item_transition_invalid", currentStatus }` so concurrent operator-click vs auto-apply can't double-apply. **Idempotent creation** by `(orgId, deadLetterId)` unique index: `createRecoveryItem` is safe to call N times from the cluster-apply fan-out without dup audit rows or alert events (the result type carries `wasCreated: boolean`; only `wasCreated === true` writes the audit and dispatches the `recovery_item.created` alert). **The creator helper** lives in `packages/engine/src/recovery/recovery-item-hook.ts` (NOT `apps/api`) so BOTH the API and worker processes can register it via the `setRecoveryItemCreator` DI seam in `@janusly/data/src/recovery-item-creator.ts`. The worker is the primary DLQ writer — registering only in api would miss every worker-side insert. Same posture as the alert dispatcher: inline audit writes via `db.insert(auditLogs)` + `safePersistPayload`, never throws on the caller. **Auto-create toggle** per org: `org_configs.recovery.autoCreateItems` (default `true` for new orgs, opt-in per existing legacy tenant to avoid audit-row explosion on day 1 — backfill script is a follow-up). **Failure-storm debounce** (`org_configs.recovery.debounceWindowSeconds`, default 300, range 0..3600, `0` = off): before creating, `createRecoveryItemForDeadLetter` calls `findOpenRecoveryItemForDebounce` — when a still-open item (`status <> 'resolved'`) shares the `(orgId, workflowId, errorSignature)` key AND its `lastOccurredAt` is within the (engine-clamped to `[30,3600]`s) sliding window, the new DLQ row attaches as a `recovery_item_children` row (idempotent on the `(recoveryItemId, deadLetterId)` unique index — a replayed insert is a no-op) and bumps the parent `occurrenceCount` + `lastOccurredAt` instead of spawning a new incident. The window is anchored on `lastOccurredAt` (each occurrence refreshes it), and the error signature is persisted on `recovery_items.error_signature` as the match key (a signature-less failure can't be grouped and always creates). The attach path returns BEFORE `recordAlertEvent`, so a storm fires `recovery_item.created` once — ENG-122 dedupes over the parent for free; the `recovery.item.occurrence_attached` audit fires only when a child was actually inserted (no double-count on replay); a defensive guard skips self-attaching a parent's own DLQ row; the hook's never-throws posture holds (a debounce read failure degrades to creating the item). Children have NO independent lifecycle — resolving the parent closes the incident for every attached occurrence; `dead_letters` rows still persist 1:1 so cluster-apply + auto-healing (which cluster `dead_letters` by signature) are unaffected. The decision lives in the hook; the SQL (`findOpenRecoveryItemForDebounce` / `attachDeadLetterToRecoveryItem` / `listRecoveryItemChildren` / `countRecoveryItemChildren`) is in `recoveryItemsRepo.ts`; `GET /recovery/items/:id/children` (viewer, `recovery.read`, org-gated) backs the drawer's occurrence list. **Cluster-apply fan-out** (route `POST /dlq/cluster-apply` loop) creates a recovery_item per accepted DLQ row pre-replay and auto-closes it post-replay with `resolutionReason: sandbox_replay_succeeded` — one DLQ cluster of N members generates N recovery_items that all close together. `/dlq/replay` (single) and `/dlq/resolve` (operator manual) also auto-close via `autoResolveRecoveryItemFromReplay`. **Eleven routes** in `apps/api/src/routes/recovery-items-routes.ts` — `GET /recovery/items` paginated (filters: `status` / `owner=me` / `severity` / `limit` / `cursor`), `GET /recovery/items/:id`, `GET /recovery/items/:id/children` (debounce occurrence list, viewer/`recovery.read`), plus 8 POST transition verbs (`acknowledge` / `in-progress` / `waiting-external` / `escalate` / `assign` / `resolve` / `reopen` / `comment`) under `permission: "recovery.write"` (`editor`/`admin` default — same key that already gated recovery-feedback writes; the three GETs are `recovery.read`). **Ten audit actions**: `recovery.item.{created,acknowledged,in_progress,waiting_external,assigned,escalated,resolved,reopened,commented,occurrence_attached}`; mutating verbs all carry `{ before, after }`. **Two new alert triggers** (extending ENG-122's enum): `recovery_item.created` (event-driven — fires inside `createRecoveryItemForDeadLetter` only on `wasCreated === true`) and `recovery_item.sla_breached` (state-driven — `scanRecoveryItemSlaBreaches` in `apps/api/src/alerts/scanner.ts` runs on the existing `*/2 * * * *` cron, reads `listOpenItemsWithBreachedSla(orgId)` = `status != 'resolved' AND sla_target_at <= now()`). Dedupe-key for the new triggers: `item:<deadLetterId>` and `sla:<itemId>` (NOT `sla:<deadLetterId>` — items can re-breach after reopen, so keying on itemId is correct). The web mounts `RecoveryItemBadge` inside `DeadLettersPanel`'s `we-list-row__meta` (severity pill cobalt→red for p4→p1, status chip, SLA timer with green/amber/red bands by % time remaining), and `RecoveryItemDrawer` (transition buttons enabled by current status, resolve sub-form with closed-enum reason select, comment textarea, escalate sub-buttons per remaining severity). Adding a new transition means: extend `ALLOWED_PRE_STATES` in shared + add a repo function via `applyCas(...)` + add a body schema + add a route + add an audit action + add EN/ES copy under `recoveryItems.action.*`; the CAS contract is the single source of truth.

## Recovery incident handoff

**Recovery incident handoff:** operator-driven cross-team dispatch of a `recovery_item`'s full context (severity, owner, error signature, recent comments, deep link) to one of four destinations: `slack` / `linear` / `github` / `webhook`. New route `POST /recovery/items/:id/handoff` (`role: "editor"`, `permission: "recovery.write"`, reuses the `"reports.deliver"` rate-limit bucket with default 60/min/org). Body validated via `HandoffRequestBodySchema` in `@janusly/shared/src/recovery-handoff` with per-destination `superRefine` (github requires `owner+repo`; webhook/linear require `url`; slack minimal). **The dispatcher** lives in `apps/api/src/recovery-handoff-dispatcher.ts` and routes through the shared per-tool `executeTool` invocation helpers in `@janusly/engine/src/integration-dispatch` (`callSlackPost` / `callGithubCreateIssue` / `callGithubAddIssueComment` / `callWebhookSend` — the SAME helpers `dispatchReportDelivery` AND the alert dispatcher use, so each tool's input-arg shape lives in ONE place) — slack via `slack.post`, github via `github.create_issue` (first call) or `github.add_issue_comment` (subsequent calls — the append-on-repeat branch), linear and webhook via `webhook.send` with `X-Idempotency-Key` header. Only the low-level invocation layer is shared; the dispatcher keeps its own result mapping (`externalId` / `externalUrl` / `commentId`), wall-clock latency, and error cap, which differ from the report-deliver envelope. All THREE callers of these tools (this handoff dispatcher, `dispatchReportDelivery`, and `packages/engine/src/alerts/dispatcher.ts`) now share the engine-side `integration-dispatch` helpers — the module lives in `packages/engine` so engine-side callers can import it (apps/api → engine is the established direction; engine never imports apps/api). The dispatcher NEVER throws; per-channel failures become `{ ok: false, error, latencyMs }`. **Idempotency** is enforced by the `recovery_item_handoffs` table — `(orgId, recoveryItemId, destination)` unique index makes `upsertHandoff` safe under concurrent operator clicks (Postgres serialises the INSERT ON CONFLICT). The `COALESCE(EXCLUDED.external_id, existing)` preserves the original GitHub issueNumber even when a later retry fails. **Slack cooldown** is the v1 substitute for thread-targeting (incoming webhooks are channel-bound — no Web API): if a `delivered` handoff exists within `SLACK_HANDOFF_COOLDOWN_SECONDS = 3600` (1h), the route short-circuits with 200 `{ alreadyDispatched: true, dispatchCount, lastDispatchedAt }` and audits `alreadyDispatched: true` — no second slack.post fires. v2 can move to Web API + `threadTs` when the demand justifies the auth flow. **GitHub append-on-repeat**: when the prior dispatch returned an `externalId` (issue number), the second call uses `github.add_issue_comment` instead of `github.create_issue` — the operator never spawns a duplicate issue, and the same UI panel surfaces both create + comment chains. `composeAppendMessage` re-composes the markdown with "Recovery item update (dispatch #N)" header to make the comment timeline readable. **Linear + webhook**: same dispatch path; `webhook.send`'s new optional `headers?: Record<string, string>` field (capped at 10 entries × 200 chars, CR/LF rejected — defense against header-injection via operator input) carries `X-Idempotency-Key: <recoveryItemId>:<destination>`. The receiver dedupes by that key; Janusly doesn't try to be smart about Linear's native API in v1. **Dry-run gate**: the route reads `runs.replayMode` for the run linked to the recovery item's `deadLetterId`; when it's `'validation'` the dispatch is skipped entirely (`{ ok: false, skipped: true, reason: "validation_run" }` response + audit row with `skipped: true`). Sandbox replays must NOT page the team channel. Four new audit actions: `recovery.handoff.{slack,linear,github,webhook}`; all carry `{ ok, statusCode, error, latencyMs, credentialName, idempotencyKey, dispatchCount, externalId, externalUrl }` — the env-var name behind the credential is NEVER echoed (same posture as `executeTool`'s `credential secret missing for <name>` envelope). ## Failure recovery patch surface

**Failure recovery patch surface:** `POST /ai/patch-workflow` (`role: "editor"`, rate-limited via the shared `"ai"` bucket) is the AI route the Recovery dialog calls. The route reads the failing node's type from `dlq.nodeJson.type`, picks one of ten per-type config envelopes via `patchEnvelopeForNodeType` (`apps/api/src/ai-schemas.ts`) — `AiPatchHttpConfigEnvelope` / `AiPatchToolConfigEnvelope` / `AiPatchAgentConfigEnvelope` / `AiPatchTransformConfigEnvelope` / `AiPatchConditionConfigEnvelope` / `AiPatchAiConfigEnvelope` / `AiPatchRouterConfigEnvelope` (also handles `router_llm`) / `AiPatchApprovalConfigEnvelope` / `AiPatchLoopConfigEnvelope` / `AiPatchGenericConfigEnvelope`. `multi_agent`, `human_form`, and `noop` intentionally fall through to the generic envelope — multi_agent's `agents` array is structurally too complex for v1, human_form is a resume-schema surface rather than a config-repair target, and noop has no actionable runtime config (empty patches trip the no-op guard). Each envelope wraps a `suggestions: Array<{ patchedConfig, rationale, approachLabel, confidence }>` with `min(1).max(3)` items — multi-suggestion is the only shape; single-suggestion responses are just an array of length 1. The http/tool/agent `patchedConfig` schemas are single non-union object schemas with leaf fields declared `.nullable()` (NOT `.optional()`). The http envelope's `headers` and the tool envelope's `input` use a bounded `Array<{ name, value: string | null }>` patch form (`max(20)` / `max(30)`) instead of an open `Record<string, ...>` (which OpenAI strict mode rejects via `propertyNames`). Transform `mapping` and loop `mapping` use the same array-of-pairs patch form. The merge layer in `apps/api/src/patch-workflow-merge.ts` folds each pair against the failing node's existing record (`PAIR_ARRAY_FIELDS_BY_NODE_TYPE = { http: ['headers'], tool: ['input'], transform: ['mapping'], loop: ['mapping'] }` scopes the fold per node type — generic-envelope nodes like `subworkflow` whose `config.input` is structurally different flow through verbatim); non-null `value` sets/replaces the key, `null` removes it, an empty array is a no-op preserving the existing record. Router `candidates` is an array but a verbatim-replace shape (no fold) — the LLM either replaces the full list or emits `null` to preserve. For `tool`-typed failures, the route enriches the prompt with `extraContext.toolInputContract` (the failing tool's `listTools()` entry: `name` / `description` / `required` / `optional` / `inputExample`) so the LLM has the exact required-field names instead of having to infer them from the runtime error message — closes the gap where the runtime error (e.g. "search is required") and the existing config's wrong key (e.g. `input.input`) would otherwise have the LLM emit field names that don't match the registered tool schema. This satisfies BOTH provider strict-mode contracts for the primary resilience patch path: Anthropic's compiled-grammar cap holds because each typed envelope has 3-7 leaf fields and the array is ONE repeated `items` constraint (not three branches), and OpenAI's strict-mode rule "every property in `properties` must be in `required`" holds because nullable-required is the fix (a `.optional()` field would be missing from `required` and OpenAI rejects). The generic envelope is best-effort for non-resilience node types until they get concrete provider-strict envelopes. Don't reintroduce a `discriminatedUnion` to a structured-output schema — `oneOf` is rejected outright by OpenAI strict mode and bloats Anthropic's grammar. The LLM emits ONLY the patched configs for the failing node (sending `null` for fields it doesn't want to change), each tagged with `approachLabel` (closed enum: `add_retry` / `raise_timeout` / `swap_secret_ref` / `add_approval` / `fix_url` / `other`) and a self-rated `confidence` 0-100. The route fan-out-merges each suggestion's `patchedConfig` into the original workflow snapshot after stripping nulls, validates each through the same `WorkflowSchema.safeParse` + `sanitizeAiWorkflow` chain `/ai/generate-workflow` uses, drops invalid suggestions, sorts survivors by confidence desc, and degrades to fallback when none survive. The route's response carries the new `suggestions: Array<{ workflow, rationale, approachLabel, confidence }>` AND legacy `suggestedWorkflow`/`rationale` fields mirroring `suggestions[0]` for back-compat — older clients reading just the legacy fields keep working. Audits both AI-mode and fallback paths as `ai.workflow.patch_suggested` with `envelopeKind` + `suggestionsCount` + `topApproachLabel` metadata. The patch helper (`packages/ai/src/patch-workflow.ts`) stays schema-agnostic — its `SYSTEM_PROMPT` instructs the LLM to emit 1-3 distinct alternatives ordered most-likely-fix first, with self-rated confidence and approachLabel. Per the AGENTS.md AI-fallback contract the helper never throws — null LLM / quota / network / schema mismatch all degrade to `mode: "fallback"` returning a single 0-confidence "other" item with the original workflow untouched. Don't bypass the sanitize step, the per-suggestion validation, or the audit row — all three are required for the AI-mutation invariant. **Release verification is Anthropic-only until explicit new direction**: smoke against `anthropic/claude-haiku-4-5-20251001` and expect `mode: "ai"` with a real structural diff on the failing node. OpenAI-compatible schema constraints may remain in code/tests for future expansion, but OpenAI smoke is not a shipping gate while the product is Anthropic-only. The recovery-matrix smoke (15 distinct failure shapes covering http / tool / transform / condition / ai / router / loop / approval-adjacent envelopes; `apps/api/src/recovery-matrix-fixtures.ts` + `scripts/seed-recovery-matrix.ts`) is the regression bed for the patch route — re-run it after any change to the envelopes, the merge layer, or the system prompt. Current observability target on Anthropic claude-haiku-4-5: ≥ 13/15 ai-mode rate, with each new envelope kind appearing in `audit_logs.metadata.envelopeKind` (the lone fallback was `write_side_without_approval`, now flipped to AI mode via the structural envelope described next). **Structural envelope (multi-node patches):** when the failing node is a write-side HTTP call (POST/PUT/PATCH/DELETE) AND has no `approval` ancestor in the upstream DAG, the route dispatches to `AiPatchStructuralEnvelope` (in `apps/api/src/ai-schemas.ts`) INSTEAD of the per-type config envelope. Dispatch reuses `isSensitiveAction` + `hasApprovalAncestor` exported from `packages/engine/src/workflow-readiness.ts` — the SAME rule that drives the production-readiness badge, so the readiness check and the recovery dispatcher can't drift. The structural envelope's suggestions emit `{ action: "insert_approval_upstream", approvalNodeId, approvalMessage, insertBeforeNodeId, rationale, approachLabel: "add_approval", confidence }` (single non-union object shape, provider-strict-safe — no `oneOf`, no `propertyNames`, no open `additionalProperties`). The `action` literal is the extensibility hook for future structural fix-classes (`split_for_retry`, `insert_error_handler`); v1 wires only `insert_approval_upstream`. The route swaps the helper's system prompt to `STRUCTURAL_PATCH_SYSTEM_PROMPT` (exported from `packages/ai/src/patch-workflow.ts`) which teaches the LLM the different output shape. Merge happens via `applyStructuralPatchToWorkflow` (in `apps/api/src/patch-workflow-merge.ts`) — pure function alongside `applyConfigPatchToWorkflow`: validates the target exists, rejects collisions with existing node ids, inserts a new `approval` node with `config: { message: approvalMessage }`, rewires every edge `to === insertBeforeNodeId` to flow through the new approval, and appends one outgoing `approval → target` edge. Multi-predecessor rewiring is comprehensive — no parallel-path bypass. The merged workflow re-validates through the same `WorkflowSchema.safeParse` + `sanitizeAiWorkflow` chain config patches use; invalid suggestions drop silently; all-invalid degrades to fallback. Audit metadata extends with `patchStyle: "structural" | "config_only"`. v1 covered HTTP write-side only; the dispatch gate now also opens for every `mcp_tool` node — every `mcp_tool` invocation is treated as write-side by default (the workflow JSON has no visibility into the per-tool `mcp_tool_descriptors.writeSide` flag at suggestion time, so `isSensitiveAction` returns `true` unconditionally for `mcp_tool`, matching the descriptor table's own `writeSide: true` fail-safe). False positives surface an extra approval suggestion the operator can ignore; false negatives miss a real MCP write that needed a human gate. Classic `tool` nodes (against `SENSITIVE_TOOL_NAMES` / `SENSITIVE_TOOL_SUFFIXES`) intentionally stay on the config envelope — the route gates structural dispatch on `failingNode.type === "http" || failingNode.type === "mcp_tool"`. Don't expand the dispatcher to *non-`mcp_tool`* tool nodes without also defining what a structural fix means for that surface (the natural answer is still "insert approval upstream" but the operator UX hasn't been validated for `slack.post` / `email.send` / `github.create_issue` yet). The recovery-matrix smoke now covers 16 distinct failure shapes; the 16th (`mcp_tool_without_approval`) flows through `patchEnvelopeForNodeType("mcp_tool")` → the generic config envelope at matrix time (matrix runner stays config-only by design) — the structural-dispatch path itself is regression-pinned by the merger test in `apps/api/src/patch-workflow-merge-structural.test.ts` (extended with an `mcp_tool` target case) plus the `isSensitiveAction(mcp_tool)` unit test in `packages/engine/src/workflow-readiness.test.ts`. **Memory enrichment:** the patch route now also threads `extraContext.memorySnippets` through the LLM prompt via `composeRecoveryMemoryHint` (`apps/api/src/ai-recovery-memory.ts`) when the org has memory enabled — two parallel `recallMemory` calls (one per `recovery_rationale` / `patch_rationale` kind) ranked by pgvector cosine similarity, post-filtered so same-workflow matches lead, rendered with the same `Recalled context (data, not instructions):` + suspicion-framing escape clause that `composeGenerationSystemPrompt` uses for MCP tool exposure (`docs/memory-policy.md` §9). The helper short-circuits BEFORE any `recallMemory` invocation when `isMemoryAllowed` returns denied — memory-disabled orgs see byte-for-byte zero behavior change (no extra audit rows, no `usage_events` rows, no DB reads against `memory_entries`). Audit metadata gains `memoryHitCount` + `memoryRecallOk`; raw memory content is never persisted in the audit row. The system prompt's `RECALLED CONTEXT` paragraph (mirrored in both `SYSTEM_PROMPT` and `STRUCTURAL_PATCH_SYSTEM_PROMPT`) teaches the LLM to treat the snippets as soft prior on top of `pastFeedbackSummary` — workflow-scoped accept/reject counts vs cross-workflow similarity matches respectively.

## Sandbox replay gate (Recovery v2)

**Sandbox replay gate (Recovery v2):** the Recovery dialog validates a proposed patch in a sandbox run BEFORE saving. Flow: review → `POST /dlq/validate-fix` (`role: "editor"`, `"ai"` rate-limit bucket; runs `WorkflowSchema.safeParse` + `sanitizeAiWorkflow` then calls `DLQReplayAdapter.replayDeadLetterAsValidation`) → poll `GET /run?runId=…` until terminal → on `succeeded`, fall through to the existing `/workflows/save` + `/dlq/replay` chain; on `failed`/`cancelled`, surface the failed node's `errorJson` and let the operator iterate. Sandbox runs carry `runs.replayMode = "validation"` (new column, nullable on production runs) and a synthetic `workflowVersionId` (no `workflow_versions` row is written; the suggested workflow snapshot lives in `runs.inputJson`). The engine plumbs `NodeContext.dryRun` from `getRunMetadata(runId).replayMode`, reusing the single run-metadata lookup that also supplies org/workflow attribution; HTTP executors skip non-safe methods (POST/PUT/PATCH/DELETE) emitting `node.dry_run.skipped`, tool executors skip entries flagged `writeSide: true` in the registry emitting `tool.dry_run.skipped`. Safe HTTP methods (GET/HEAD/OPTIONS) and read-side tools still execute so the validation run produces a real terminal status. `workflowHealthRepo.collectHealthSignals`, `failureClusterRepo.queryDeadLetters`, and `failureClusterRepo.queryFailedRunNodes` filter `isNull(runs.replayMode)` so validation runs are excluded from production rollups. The dialog's polling effect claims the terminal path (`cancelled = true`) before yielding so concurrent in-flight polls don't double-fire save+replay. Audited as `recovery.validation_started`. Don't add a write-side tool without setting `writeSide: true` on its `ToolDefinition` — the dryRun gate is the only thing keeping a sandbox replay from double-charging external APIs. **Replay Lab is a sibling consumer of the same gate**: `POST /runs/replay-lab` (`editor`, `"ai"` bucket) creates a `replayMode="validation"` run from ANY source run (not just a DLQ entry) via `replayRunAsValidation` in `packages/engine/src/adapters/replay-lab.ts`; trigger input flows through `runs.inputJson.input` so `{{input.*}}` template references resolve identically to the source run; nested labs (source `replayMode` already set) are rejected at the route. Audit action is `replay_lab.started` — distinct from `recovery.validation_started` so the two surfaces are distinguishable in audit logs. Comparison shape lives in `packages/data/src/runComparisonRepo.ts:getRunComparison`; `GET /runs/compare` (`viewer`) is the route, and the existing `GET /runs` prefix matcher excludes `/runs/compare` so first-match-wins routing works.

## Recovery before/after delta

**Recovery before/after delta:** `GET /workflows/health/delta?workflowId=…&afterVersion=…&windowDays=…&priorFailureSignature=…` (`role: "viewer"`) splits the same time window by version cutoff into a "before" and "after" side, calls `collectHealthSignals` once per side via the new optional `versionFilter: { side, cutoffVersion }` 4th argument (single new `lt`/`gte` predicate on the joined `workflow_versions.version`), and composes both sides through `computeWorkflowHealth`. Returns `before` / `after` health scores, a `delta` payload (score / p95 / cost-per-run), an always-populated `recentRunsAgainstAfter` counter (so the dialog never feels dead before the 5-run threshold), an optional `sameFailureSinceApply` block (re-normalizes new DLQ rows against the caller-supplied prior signature; defense-in-depth — the route never echoes back a freshly-derived signature, only the caller-supplied prior one, so a leaked-secret-in-error-message can't slip through), and `priorVersion` for the regression-rollback affordance. `MIN_RUNS_FOR_DELTA = 5` constant exported from `packages/engine/src/workflow-health.ts` so the dialog and route agree. `delta` is `null` until `after.signals.totalRuns >= MIN_RUNS_FOR_DELTA`. `normalizeErrorSignature` lives in `@janusly/shared/src/error-signature` (relocated from engine for web-bundle compat); `@janusly/engine/src/error-signature` is a back-compat thin re-export. Mounted in the dialog by `<RecoveryDeltaCard>` inside the `applied` step's success ribbon — render the run counter + same-failure pill always, and the three delta pills (health / p95 / cost-per-run) once `hasEnoughData` flips. Regression band (`delta.score ≤ -3` AND `priorVersion != null`) surfaces a "Roll back to v{N-1}" button only for the effective `editor` / `admin` role, lazy-fetches both versions via the existing `/workflows/versions` endpoint, and mounts the existing `<RollbackConfirmDialog>`. Don't bypass the multi-tenant gate on either the workflow lookup or the DLQ same-failure scan; both queries carry `eq(<table>.orgId, auth.orgId)`.

## Recovery feedback loop (operator → system)

**Recovery feedback loop (operator → system):** `POST /recovery/feedback` (`role: "editor"`, `"ai"` rate-limit bucket, audited as `recovery.feedback`) captures every accept/reject decision the operator makes in the Recovery dialog into the new `recovery_feedback` table (id / orgId / userId / deadLetterId / workflowId / suggestionMode / approachLabel / accepted / comment / createdAt; two indexes both leading with `org_id`). Body validated via Zod (closed `approachLabel` + `suggestionMode` enums); anonymous workflows (no saved id) are rejected with 422. The dialog writes a row at four moments: Apply success → `accepted: true`; Cancel from review or validation-failed → `accepted: false` with the chip text or free-text comment as the reason; Iterate from validation-failed → `accepted: false, comment: "validation_failed"` BEFORE re-entering generateSuggestion. Free-text comments run through `scrubSecretShapes` from `@janusly/shared/src/error-signature` at write time and are truncated to 2000 chars — defense-in-depth on the secret-leak invariant. The read path closes the loop: `/ai/patch-workflow` calls `summarizePastFeedback` (capped at 100 rows / 30-day window) → `composeFeedbackHint` (pure helper in `apps/api/src/ai-patch-feedback.ts`, ≤280 chars) and threads the result through `extraContext.pastFeedbackSummary`. The patch helper's `SYSTEM_PROMPT` includes one line teaching the LLM to treat the field as soft prior — prefer high-acceptance approaches for THIS workflow, deprioritize already-rejected ones, signal residual uncertainty via lower confidence and a rationale that addresses the prior pushback. Don't add a write tool that bypasses the dialog without also writing through `/recovery/feedback` — the labeled signal is what makes the loop *learn*, and silent dialog paths break that contract. **Memory-write side of the loop:** when the org has memory enabled (both flags), `/recovery/feedback` also commits a `recovery_rationale` `memory_entries` row on every `accepted: true` (always) and a `patch_rationale` row when the body carries the optional `rationale` field (the dialog passes it on the apply-success path). The route runs `isMemoryAllowed` FIRST and short-circuits BEFORE any `commitMemory` call so memory-disabled orgs see byte-for-byte zero behavior change — no `usage_events` row, no `memory.*` audit row. Memory commits go via `void Promise.allSettled([...])` AFTER `recordRecoveryFeedback` + the `recovery.feedback` audit have already succeeded; a `commitMemory` failure never breaks the feedback `{ ok: true }` response (the repo's own `memory.entry.failed` audit row captures the failure mode). Rejections (`accepted: false`) DO NOT commit memory by default — the catalog's `memory.allowedKinds` granularity supports adding rejection-capture later as a one-line change. **Confidence calibration rides on the same loop:** the dialog now persists the decided-on suggestion's `rawConfidence` (nullable `recovery_feedback.raw_confidence` column) on every accept/reject; a global `system:confidence-calibration` daily cron (`packages/engine/src/confidence-calibration-scheduler.ts`, env `JANUSLY_CONFIDENCE_CALIBRATION_CRON` default `30 1 * * *` UTC, never-throws, mirrors the retention sweeps) walks every opted-in org and fits a per-`(orgId, approachLabel)` linear curve (`packages/engine/src/confidence-calibration.ts` — pure math, `fitCalibrationCurve` buckets by raw confidence, weighted-least-squares, returns `null` below `MIN_CALIBRATION_SAMPLES=20` OR on a non-positive slope so calibration can NEVER invert suggestion ordering) into the new `confidence_calibrations` table (data repo `confidenceCalibrationRepo.ts`, audit `confidence.calibration.computed` per org per fire). `/ai/patch-workflow` reads the curves (gated on `org_configs.ai.confidenceCalibrationEnabled`, default true) and emits BOTH `confidence` (raw) AND `calibratedConfidence` per suggestion — the sort stays on raw so ordering is preserved; the dialog renders calibrated as primary with a "(model self-rated X%)" subtitle when they differ ≥10 pts (`CALIBRATION_SUBTITLE_DELTA`). Opt-out / <20-samples / no-curve all degrade to raw unchanged. Don't bucket calibration by anything other than `raw_confidence` (the AC's contract) and don't relax the positive-slope monotonicity guard.

## Eval datasets from recoveries

**Eval datasets from recoveries:** accepted recovery decisions become a reusable regression bed ONLY with explicit opt-in. `recovery_feedback.eval_consent` (boolean, default `false`, threaded through `RecoveryFeedbackBodySchema` → `recordRecoveryFeedback` → `recovery.feedback` audit metadata) is the gate; an admin builds a dataset via `POST /eval/datasets` (`evals.write`, admin) and the build query `queryEligibleFeedbackForEval` (`packages/data/src/evalDatasetsRepo.ts`) filters `accepted = true AND eval_consent = true AND eq(orgId)` — no consent → never eligible. Two new `orgId`-scoped tables: `eval_datasets` (unique `(orgId, name)`) + `eval_examples` (self-describing SCRUBBED snapshot of failure signature + input context + expected `approachLabel` + retention metadata — durable so a `recovery_feedback` retention purge can't shrink a published dataset). `deleteEvalDataset` hard-deletes examples then the dataset (children first, cascade per the `workflow_versions` precedent). `scrubSecretShapes` runs at WRITE time (the repo, when an example is built) AND at READ time (`serializeEvalExamplesToJsonl` / `composeEvalExamplePrompt` in `@janusly/shared/src/eval-dataset.ts`) — defense in depth. Export is JSONL (one scrubbed object/line, `GET /eval/datasets/:id/export?format=jsonl|json`, dual-form Content-Disposition via the shared `report-download` helpers). When examples are surfaced to an LLM they are framed as DATA via `composeEvalExamplePrompt` (data-framed header + per-example `- ` list lines + the same suspicion-framing escape clause `composeGenerationSystemPrompt` uses for MCP tool exposure), NEVER as instructions. New permission category `evals` (`evals.read` viewer / `evals.write` admin); audit actions `eval.dataset.created` / `_deleted` / `_exported`; error codes `eval_dataset_not_found` / `_name_exists` / `_name_required`. v1 ships no LLM eval-runner (the dataset IS the regression bed; running it against the patch route is a follow-up) and no rejection-capture (only accepted+consented rows eligible).

## Cluster recovery apply

**Cluster recovery apply:** `FailureClustersCard` opens Recovery in cluster mode only for clusters with frequency ≥2 and DLQ samples. `GET /dlq/cluster-members` returns open DLQ ids whose normalized signature still matches the selected cluster, capped at 100. `POST /dlq/cluster-apply` is `role: "editor"`, rechecks every row's org scope/status/signature before replay, runs replays in series, marks accepted rows replayed, and writes one `recovery.cluster_apply` audit row per accepted row. The dialog must pass through the sandbox validation gate once on the representative before calling cluster apply; if the representative went stale, use the first still-open member instead. Don't bulk-replay closed rows or skip the per-row signature recheck. **Bulk resolve (multi-select dismiss):** `POST /dlq/bulk-resolve` `{ deadLetterIds }` (`role: "editor"`, ≤ `CLUSTER_MEMBERS_MAX_LIMIT`) is the dismiss counterpart to cluster-apply's replay — it loops `markDeadLetterResolved` + audits the existing `dlq.resolved` action (`metadata.bulk=true`, since each entry is a genuine single resolve) + `autoResolveRecoveryItemFromReplay({ resolutionReason: "accepted_loss", via: "dlq_resolve" })`, returning a `{ resolved, failed, errors }` partial-success envelope (a not-found / cross-org id lands in `errors` without aborting the batch). The `DeadLettersPanel` drives it with the Flows-list multi-select idiom (a `dlq-select-toggle` mode → per-row checkboxes + `dlq-select-all` → a `.we-list-bulk-bar` over the same ticked set). **Bulk replay (multi-select retry):** `POST /dlq/bulk-replay` `{ deadLetterIds }` (`role: "editor"`, `permission: "dlq.replay"` — matches single `/dlq/replay`, ≤ `CLUSTER_MEMBERS_MAX_LIMIT`) is the retry counterpart to bulk-resolve. Unlike `cluster-apply` it does NOT require the rows to share an error-cluster signature, so an arbitrary mixed-cause selection replays in one request — it loops `dlqReplay.replayDeadLetter` (the shared adapter) + `markDeadLetterReplayed` + audits the existing `dlq.replayed` action (`metadata.bulk=true`, since each entry is a genuine single replay) + `autoResolveRecoveryItemFromReplay` (auto-close only, NOT cluster-apply's ensure-then-close), returning a `{ replayed, failed, errors }` partial-success envelope. **Only `open` rows replay** — a non-`open` row is reported in `errors` so a batch can't double-enqueue downstream work (mirrors cluster-apply's status guard); a not-found / cross-org id lands in `errors` without aborting. No rate-limit (matches single `/dlq/replay`; the 100-cap bounds it). The bulk bar shows **"Replay selected"** (primary, the recover path) beside **"Resolve selected"** (secondary, accept-the-loss dismiss). NOTE: `/dlq/cluster-apply` still gates on `role` only (no `dlq.replay`) while single + bulk replay require it — a pre-existing authz asymmetry, not tightened here.

## Recovery metrics rollup

**Recovery metrics rollup:** `GET /recovery/metrics?windowDays=…` (`role: "viewer"`) composes `collectRecoveryMetricsSignals` (`packages/data/src/recoveryMetricsRepo.ts`, 30-day window default, seven parallel windowed queries with caps: 1k MTTR samples, 10k usage rows, 5k events) + `composeRecoveryMetrics` (`packages/engine/src/recovery-metrics.ts`) into the org-level Operations dashboard payload — recovery metric cards (success rate, MTTR, p95 latency, approvals pending, replay rate, SLA attainment, cost) each with `value` / `display` / `severity` / `rationale`. Severity bands are exported constants (`SUCCESS_RATE_BANDS` / `MTTR_BANDS_MS` / `LATENCY_BANDS_MS` / `APPROVALS_BANDS` / `REPLAY_RATE_BANDS`) so future tuning lives in one place. Multi-tenant scope on every query (`eq(<table>.orgId, orgId)` direct or via `workflow_versions` join). `approvals pending` is current-state, not windowed — operators read it as "right now blocking", documented in the card's rationale. Cost is grouped in JS (not via PG JSON ops) — keeps the query plan identical to other repos and microsecond-cheap at the 10k cap. "Auto-fixes suggested/applied" + "rollbacks triggered" counters from the AC are deferred — they need new audit-log actions that don't exist yet; will plug in when the Recovery MVP ships the apply path. **Value Dashboard extension** lives in the same composer — additive `clustersResolved` metric (counts distinct failure signatures that flipped to `replayed` / `resolved` in the window via the new `queryFailureClustersResolved` query) + a `valueEstimate` block (`hoursSaved`, `dollarSaved`, `mttrDeltaSeconds`, `assumptions`) computed by the pure `estimateValueSavings(clustersResolved, mttrSeconds, assumptions)` helper. Assumptions come from three safe `org_configs` keys under the new `value` category: `value.hourlyCost` (default 50, range 0..2000), `value.minutesSavedPerRecovery` (default 30, range 0..480), `value.baselineMttrSeconds` (default 0 = sentinel for "operator has not measured a baseline yet"; range 0..86400). Formula `clustersResolved × minutesSavedPerRecovery / 60 × hourlyCost = dollarSaved`. **UI invariant: every dollar / hour surface MUST carry an "estimate" badge + tooltip linking to the assumptions** — the dashboard never claims accounting precision. The Markdown export (`GET /reports/value-dashboard?windowDays=N&format=markdown|json`, audited as `report.value_dashboard.exported`) writes the formula out plainly + lists the three knob values in an Assumptions section labeled "Estimate based on operator-supplied assumptions". The web `ValueDashboardSection` mounts inside `RecoveryCenterPanel` as a section (NOT a new tab); when `terminalRuns === 0` it shows a private-beta-pending fallback so the surface ships before any private-beta partner data lands. Don't extend `composeRecoveryMetrics` to accept additional non-`value.*` config without a matching catalog key + snapshot branch — the additive 3rd-arg signature is the chokepoint. **SLA attainment metric** (additive): `queryRecoverySlaAttainment(orgId, since)` aggregates in Postgres (`count(*) filter (where resolvedAt <= slaTargetAt)` over `recovery_items` resolved in-window) into a `slaAttainment` `RecoveryMetric` with exported `SLA_ATTAINMENT_BANDS` (green ≥90, amber ≥75, red <75). Empty (nothing resolved in-window) → `value: null` / neutral, NOT 0% — attainment of an empty set is undefined. It's surfaced as an SLA-attainment tile in the **Recovery Center metric strip** (`RecoveryCenterPanel`, reusing `VitalSignsTile` band coloring + `tRecoveryMetricRationale` — the sibling home of the replay/mttr tiles, not a bespoke `ValueDashboardSection` card) and a row in the `/reports/value-dashboard` markdown export. Rationale codes `sla_attainment.empty` / `sla_attainment.summary` follow the existing `recoveryMetricRationale.<code>` i18n chokepoint (EN/ES).

## Failure clustering

**Failure clustering:** `GET /dlq/clusters?windowDays=…` (`role: "viewer"`) composes `collectFailureSamples` (`packages/data/src/failureClusterRepo.ts`, 30-day window default, 500-sample cap, parallel queries over `dead_letters` + failed `run_nodes`) + `clusterFailureSamples` (`packages/engine/src/cluster-failures.ts`) into a list of normalized failure clusters. Multi-tenant scope comes from persisted owner rows (`dead_letters.org_id`, `runs.org_id`); saved workflows left-join `workflow_versions` for names, and ad-hoc runs fall back to the persisted workflow snapshot. The DLQ writer carries `orgId` from run metadata, defaulting only as last resort. The pure normalizer `normalizeErrorSignature` (`packages/engine/src/error-signature.ts`) runs 7 first-match-wins rules — `secret_missing` / `http_error` / `network_timeout` / `ai_provider` / `parse_error` / `tool_input` / `unknown` — to produce a stable cluster label like `"Missing secret: GITHUB_TOKEN"` or `"HTTP 401 on http node"`. Hard safety property: **no secret value ever appears in a returned signature**. Every produced label passes through `scrubSecretShapes` (closed regex: `sk-…` / `ghp_…` / `github_pat_…` / `gh[ousr]_…` / `xox[baprs]-…` / `AKIA…` / `AIza…` / `Bearer …` / 3-segment JWT) before return — defense-in-depth on top of the safe-persist chokepoint that already key-redacts the JSON we read from. Free-form error MESSAGES escape key-redaction, so this final scrub is the last line of defence. `(runId, nodeId)` deduplication preserves the DLQ-source sample over the failed-`run_nodes` sample so a failed run that landed in DLQ counts once. The route registers BEFORE the wildcard `/dlq` dispatcher in the route registry — first-match-wins; reordering would silently break the cluster surface. Compute is on-demand per request; cluster persistence + drift alerts are a future ticket.
