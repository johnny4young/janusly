## DLQ

**DLQ:** every failed node beyond `retryPolicy.maxAttempts` lands in `dead_letters`. Replay via `POST /dlq/replay`. The Operations card in Runs surfaces counts and filters. `BullMQQueueAdapter` composes `DeadLetterQueueAdapter` so DLQ insertion is part of the queue contract — don't bypass it. **The recovery queue filters + sorts SERVER-SIDE** so the result is cap-correct: `GET /dlq` accepts `status` (on `dead_letters`) + `owner` (`me`→`auth.userId`) + `severity` + `search` (case-insensitive substring over node id / run id / `error_json->>'message'`, ≤100 chars, LIKE-escaped via the shared `escapeLikePattern`, applied before the cap like the other filters) + `sort` (`newest`/`oldest`/`severity`/`sla`) and routes through `listRecoveryQueue` (`apps/api/src/dlq.ts`), a `dead_letters` LEFT JOIN `recovery_items` (on `(orgId, deadLetterId)`) that applies the filter + ORDER BY BEFORE the 200-row cap (`DLQ_LIST_MAX_LIMIT`) and folds the recovery overlay (severity/owner/SLA/status/comments…) INLINE onto each row — so a P1 older than the newest 200 surfaces under a severity filter, and the panel renders from ONE cap-correct fetch (no separate `/recovery/items` overlay call). An `owner`/`severity` filter excludes a dead letter with no recovery item (its LEFT-joined columns are null → no match); `severity`/`sla` sorts push no-recovery-item rows last (`NULLS LAST`) with a `createdAt desc` tie-break. `GET /dlq` with no params preserves the existing newest-first default page (100 by default, 200 max via `limit`; the inline `recovery` field is additive and ignored by legacy callers), so the Recovery Center home preview remains behavior-compatible. The web `useRecoveryQueueFilters` hook OWNS this fetch (filter/sort state + localStorage persistence); `DeadLettersPanel` takes no `deadLetters` prop. **Keyset ("load more") pagination** lives on the sibling `GET /dlq/queue` route (registered BEFORE the `/dlq` wildcard, first-match-wins): it routes through `queryRecoveryQueuePage` (the SAME join, over-fetching `pageSize+1` through `listRecoveryQueue` then folding via the pure `buildRecoveryQueuePage`) and returns a `{ items, nextCursor, hasMore }` envelope. The cursor is an opaque `base64url(JSON)` `{ sort, createdAtIso, id, leadKey|null }` (a plain `(createdAt,id)` keyset for `newest`/`oldest`; a COMPOSITE `NULLS LAST` keyset for `severity`/`sla` where the lead key is the severity text / slaTargetAt ISO / `null` for the no-recovery-item tail) — `decodeRecoveryQueueCursor` is defensive (malformed / sort-mismatch / corrupt sla key → `null` → page 1, mirroring `parseEventsCursor`); every `recoveryQueueOrderBy` branch ends with a `deadLetters.id` tie-break for a stable total order. The cursor is UNSIGNED but org-scope is re-applied independently of it, so a tampered cursor can only reorder the caller's own page (never cross-tenant). **Bare `/dlq` stays a back-compat ARRAY** (no envelope, no cursor) for the Recovery Center home preview; `/v1/dlq` wraps that same bounded summary projection for stable clients such as MCP, while only `/dlq/queue` paginates. The stable list deliberately rejects the legacy `?id=` detail selector. The hook's `loadMore()` appends pages (with a request-epoch guard against a stale append) and resets to page 1 on any filter/sort/refresh change; `DeadLettersPanel` renders a "Load more" button below the virtual list. **The mini-grid (Total/Open/Retried/Resolved) + the card warning stripe read a THIRD sibling route `GET /dlq/counts`** — `countDeadLettersByStatus(orgId)`, a single org-scoped `GROUP BY status` folded to `{ total, open, replayed, resolved }`, deliberately UNSCOPED by owner/severity/status (it is the whole-queue health summary, NOT the filtered page — preserves the original whole-queue semantics). The hook fetches it in a SEPARATE effect keyed ONLY on `[platformVersion, refreshNonce]` (NEVER refetched on a filter/sort change — that's the point), and the warning stripe keys off `counts.open > 0`. So the panel makes two server reads: the filtered/paginated `/dlq/queue` list + the org-wide `/dlq/counts` summary. Adding a recovery-queue sort key means extending `RECOVERY_QUEUE_SORTS` (api) + the web `SORT_KEYS` in lockstep AND adding its keyset branch to `recoveryQueueKeysetPredicate`. **List rows are SUMMARY projections:** `listRecoveryQueue` deliberately excludes `workflow_json` / `node_json` (persisted with `maxBytes: Infinity` for replay fidelity — a 200-row page would otherwise ship 200 unbounded workflow snapshots) and instead carries cheap `nodeType` (`node_json->>'type'`) + `workflowName` (`workflow_json->>'name'`) projections; the full row comes from the `GET /dlq?id=` detail read (`getDeadLetter`), which the web fetches on row selection / before opening the Recovery dialog (the summary row is the graceful fallback while the detail loads). Don't reintroduce full-column selects on the list path.

**Stable recovery boundary:** `/v1/dlq`, `/v1/dlq/clusters`, and `/v1/dlq/replay` share the legacy tenant-scoped handlers but add strict request/response validation and stable envelopes. Every DLQ GET route requires both `role: "viewer"` and `permission: "dlq.read"`; every production replay route keeps `role: "editor"` + `permission: "dlq.replay"`. The stable replay accepts only `deadLetterId` (plus an optional suggested workflow and paired playbook/validation evidence), ensuring the generation-bound claim can attribute terminal impact to the exact DLQ row. The legacy run/node replay shape remains available only on unversioned `/dlq/replay` for compatibility; MCP never uses it.

**Measured Recovery Drill outcomes:** after `GET /dlq?id=…` verifies bounded `solution_pack_drill` provenance, it calls `queryRecoveryDrillOutcome` (`packages/data/src/recoveryDrillOutcomeRepo.ts`) and attaches a locale-neutral `drillOutcome` block to that legacy detail response only; list rows and stable `/v1/dlq` remain unchanged. The projection follows the bounded same-run/node DLQ chain (100 rows maximum); a 101st row produces `measurement_incomplete` and suppresses terminal/recurrence claims instead of treating a partial scan as complete. `recovery_impact_events` is the only `recovered` proof; enqueue acceptance remains `replay_in_progress`. Explicit `accepted_loss` uses the recovery item's `resolvedAt`, with the append-only `dlq.resolved` audit timestamp as a fallback when item auto-creation is disabled. Elapsed time always starts at the original drill DLQ arrival and ends at the verified terminal fact, even when a later DLQ generation carries the impact event. Seven-day recurrence uses the same normalized recovery-item signature and production-only (`runs.replayMode IS NULL`) semantics as `queryRecoveryRecurrence`; before the full window closes the UI says monitoring, never clear. Direct deterministic drills invoke `recordRecoveryItemCreationEvent` only after their synthetic transaction commits, matching the production DLQ ownership seam without allowing config/audit/alert failures to roll back the drill. The selected web detail refetches on `platformVersion` so a same-row resolve or replay cannot leave stale outcome evidence on screen.

**Recovery Validation dossier:** `queryRecoveryValidation` (`packages/data/src/recoveryValidationRepo.ts`) projects the newest server-authored `solution_pack_drill` runs for one organization and rolling 1–90 day window in one database round trip. The run scan over-fetches one row to reveal a 100-drill cap; every lateral same-run/node DLQ chain independently over-fetches one row to preserve the existing 100-attempt incomplete-measurement boundary. Outcome precedence remains centralized in `buildRecoveryDrillOutcome`; a run with no durable DLQ anchor stays `missingEvidence` instead of being dropped or inferred. The pure report composer publishes separate completion (`completed / all drills`) and recovery (`recovered / (recovered + accepted loss)`) rates, median/discrete-p90 elapsed samples over verified recovered outcomes only (accepted loss is never recovery-time evidence), supporting average/discrete-p95 diagnostics, and bounded failure-mode/recovery-path breakdowns. Resolution ownership is a closed `operator | automated | unknown` classification: `system` / `system:*` actors are automated, other non-null actors are operators, and raw user identifiers never leave the repo. `GET /recovery/validation?windowDays=N` and `GET /reports/recovery-validation?windowDays=N&format=markdown|json` both require `role: viewer` + `reports.read`; every export writes `report.recovery_validation.exported`. The JSON export carries explicit machine-readable limitations and the Markdown renderer states the same boundary: this is per-organization controlled evidence, not partner recruitment, setup-time, willingness-to-pay, or private-beta completion proof. `RecoveryValidationSection` reads the report alongside the other heavy Recovery Center projections, refetches on `platformVersion`, localizes the evidence in EN/ES, and keeps soft read failure distinct from an empty drill window.

## Failure-path precedence (design note)

A failing node can be intercepted by FOUR layers before and around the DLQ. Their order is fixed, each layer's contract names what it absorbs, and every wedge metric states which arrivals it counts — because each layer silently reshapes the numbers of the ones below it.

**The order:** per-node `retryPolicy` (same-attempt retries) → **transient tier** (class-aware ladder for rate_limit/connection/timeout; write-side errors NEVER tier) → **terminal failure → DLQ row** (the durable anchor; `persistTerminalFailure` commits node fail + DLQ + run fail atomically) → **circuit breaker** (counts consecutive failed RUNS after the DLQ write; pauses the workflow, buffers triggers, drops cron ticks) → **supervised auto-healing** (consent-gated, acts on the DLQ row after the fact).

**What each metric counts:** TTFA (first-action latency) and seven-day recurrence denominate on **DLQ arrivals** — so a transient absorbed by the tier never enters them (by design: it healed without an operator). The recovery ledger and impact rollups count **generation-bound terminal outcomes** (replay-driven wins only; replay initiation is never a win). Breaker trips are counted per CAS winner (one audit row per pause, `workflow.circuit_breaker.tripped`). Any future on-error edge or canary-rollback layer MUST state its position in this order and which of these denominators it feeds before it ships — that statement is part of its spec, not an afterthought.

**Why this order and not another:** retries-before-tier keeps the operator's explicit `retryOn` policy authoritative; tier-before-DLQ keeps self-healing transients out of the operator's queue (alert fatigue is the category's #1 churn driver); breaker-after-DLQ means the streak is counted over DURABLE failures (a crash can't lose the count); auto-healing last because it consumes the DLQ row every other layer produced.

## Recovery circuit breaker

**Circuit breaker (containment):** a workflow whose runs fail over and over is a flood, not a queue of independent incidents — every retry burns budget, deepens the DLQ, and pages the operator again for a fault they already know about. When a terminal failure is persisted, `maybeTripCircuitBreaker` (`packages/engine/src/adapters/dead-letter-queue.ts`, called at the end of `afterDeadLetterCommitted`) counts the CONSECUTIVE failure streak at the head of the workflow's terminal-run history and pauses the workflow at the threshold.

**Decision layer is pure:** `packages/engine/src/core/circuit-breaker.ts` owns `resolveCircuitBreakerThreshold` (per-workflow `config.recovery.circuitBreaker.consecutiveFailures` → org `runs.circuitBreakerThreshold` → built-in `DEFAULT_CIRCUIT_BREAKER_THRESHOLD = 5`; `false` or a threshold below `MIN_CIRCUIT_BREAKER_THRESHOLD = 2` OPTS OUT — 1 would be a hair trigger), `shouldTripCircuitBreaker` (only trips a workflow whose status is `active`), and the `JANUSLY_CIRCUIT_BREAKER_ENABLED` kill switch. No I/O. The org tier is a closed-catalog key (`runs` category, range 2..100, default 5) the adapter reads via `getOrgConfigSnapshot` — don't pass a hardcoded `orgThreshold: null` back into the resolver, which silently made this tier unreachable once already.

**Persistence:** `packages/data/src/circuitBreakerRepo.ts`. `countConsecutiveWorkflowFailures` is bounded by the caller's threshold (`LIMIT` — answering "are the last N all failed?" reads at most N rows), counts only ORDINARY terminal runs (`isNull(runs.replayMode)` — a sandbox replay is a rehearsal, so testing a fix must never pause the workflow you're fixing), and stops at the first success. It resolves a run's workflow through a LEFT JOIN + `coalesce(workflowVersions.workflowId, runs.workflowVersionId)`: `startRun` falls back to `workflow.id` for runs started from the authoring surface, so an inner join silently never matches the most common way runs actually start.

**One pause, one page:** `tripWorkflowCircuitBreaker` is a CAS (`WHERE status = 'active'`), mirroring `pauseWorkflowsForUpstream`. Two workers racing the same streak produce exactly one flip; only the winner logs and fires `recordAlertEvent({ trigger: "workflow.circuit_breaker_tripped" })`. A workflow already paused for another reason keeps its reason. The flip and its `workflow.circuit_breaker.tripped` audit row commit together via `withAuditTx` — the breaker stops a workflow with no human in the loop, so a pause the audit trail can't explain is not acceptable.

**Never breaks the DLQ path:** the whole evaluation is wrapped in try/catch. The dead letter is already durable and the operator still sees the failure; a breaker bug must never take down the recovery substrate itself.

**Resume is deliberately manual:** nothing can automatically know the underlying fault is fixed, so `POST /workflows/:id/resume` (`permission: workflows.write`) has an operator assert it, and the audit row records who plus the `clearedReason` it cleared. `resumeWorkflowCircuitBreaker` only clears a `paused_circuit_breaker` status, so it can never un-pause an upstream-outage pause (that source clears itself when the status page recovers) — and the route reports a miss by the workflow's actual status (`workflow_not_circuit_breaker_paused` + the status) rather than a bare 404, because "already active" and "paused for something else" are different operator situations.

**The pause holds at every entry point.** `/start` was never the flood: in production a workflow's repeated runs come from its cron and its webhooks, so a pause only the Run button respected paused the button nobody was pressing. Both other entry points now gate on the workflow's status, and they resolve it from the persisted row's `orgId` — never a payload hint.

**Crons are dropped, triggers are buffered — deliberately different.** An inbound trigger event carries data the upstream system already committed and will never re-send, so dropping it trades a run flood for silent data loss: it parks as `buffered` (`trigger_events.status`, distinct from `skipped`, which means deliberately discarded — deduping the two would make backfill lose the window) and the ingest returns **202**, not 200 (the event is accepted, its run deferred; a 4xx/5xx would make the relay retry or give up). A cron tick has no such payload: "the 3am run" means nothing at 6am, and replaying three hours of ticks on resume is a thundering herd — the opposite of what pausing was for. So the tick is dropped loudly and the next scheduled fire after the resume is the correct next run. An unresolvable status is not evidence of a pause: both gates fail OPEN, so a hiccuping row read can't silently strand an org's events.

**Backfill on resume.** `backfillBufferedTriggerEvents` (`apps/api/src/routes/trigger-ingest-routes.ts`) replays the buffered window oldest-first (the payloads are a causal sequence — replaying "order updated" before "order created" inverts the upstream's story) against the CURRENT latest version of the workflow that buffered the event: the operator resumed because they fixed something, so the backfill runs on that workflow's fix rather than the first same-type trigger elsewhere in the org. Capped at `TRIGGER_BACKFILL_MAX_PER_RESUME` (100) — dumping an unbounded backlog back into the queue re-creates the flood the pause just stopped — with the remainder reported as `remaining`; repeated `POST /workflows/:id/resume` calls on the now-active workflow idempotently drain the next page, and the Flows row exposes that action while its page-scoped `bufferedTriggerCount` is non-zero. That projection counts both `buffered` rows and expired `backfilling` leases, while hiding fresh in-flight leases. `claimBufferedTriggerEvents` leases each page with one oldest-first `FOR UPDATE SKIP LOCKED` statement; abandoned `backfilling` leases expire after five minutes, and an infrastructure failure before run creation releases the exact token. `startRun` consumes that token and transitions `backfilling → started` in the SAME transaction as the new run, so concurrent resume requests and stale workers cannot duplicate or lose an event. The path deliberately does NOT reuse `persistEventAndSpawnRun`: that path is behind the per-trigger INGEST rate limit (a storm guard against an upstream flooding us — a backfill is operator-initiated, already capped, and replaying a storm that was already absorbed, so the guard throttles it into failure) and it RECORDS A NEW EVENT ROW (correct for `/replay`, where a replay is genuinely a new event; for a backfill the buffered row IS the event owed a run, so cloning doubles the table and leaves the original still owed). Never throws — the workflow is already resumed, and a backfill fault must not read as a failed resume; one poisoned payload is counted and skipped rather than stranding the window behind it.

**Naming the cause:** `POST /start`'s pause gate is generic over pause sources, but the error code is not — a breaker pause returns `workflow_circuit_breaker_paused`, not `upstream_degraded`, so the operator isn't sent to check a status page for an outage that isn't there.

**Web surface:** `FlowRow` renders a paused pill (reason as the tooltip) for ANY non-active status and a Resume action ONLY for a breaker pause. `SavedWorkflow.status` / `.pausedReason` are the workflow's OPERATIONAL state — distinct from `lastRunStatus`, the outcome of its most recent run. A row with no `status` is treated as active so older cached rows never render as paused.

## Production redrive

**Production redrive:** `POST /runs/redrive` (`role: "editor"`, `permission: "runs.start"`, MCP write action `runs.redrive`) continues one failed saved run from an explicitly failed node on the latest or requested version. It copies only target-graph predecessors that succeeded in the source, queues the failed node, leaves its successors pending, and marks unrelated branches skipped so real write-side effects are not repeated. Production mode applies the same deterministic, rollback-availability, and credential-readiness gates as `/start`; paused or deleted workflows reject. The continuation inherits the source trace id and records trace-only `parentLinkKind="replay"` lineage. A partial unique index on `(orgId,parentRunId,parentNodeId,workflowVersionId)` for production rows whose `inputJson` contains `redrive` makes concurrent retries converge on one continuation; only the insert winner publishes the queue job and writes `run.redrive` audit evidence. To try a second repair, redrive the failed continuation or save a new target version rather than reissuing the identical source/node/version tuple.

No new vendor SDK, no new credential kind — Slack URL / GitHub PAT / shared webhook secret reuse the existing `slack_webhook` / `github_token` / `webhook_secret` kinds. Don't bypass `executeTool` from the route; the per-tool chokepoint owns the inner per-tool rate-limit bucket (`tool.slack.post` / `tool.github.create_issue` / `tool.webhook.send`), credential lookup, usage events, and the SSRF / body-cap / timeout guards via `fetchHttpTarget`. The route's `writeSide` posture is by design distinct from the runtime workflow `dryRun` gate — the route runs outside a workflow run, so the rate-limit + credential + audit gates are the right safeguards at this layer.

## Recovery alerting

Booted behind `JANUSLY_ALERTS_ENABLED=true` from `apps/api/src/alerts-bootstrap.ts` (mirrors `auto-healing-bootstrap.ts` 1:1); the DI seam registration happens unconditionally so event-driven hooks reach the dispatcher even when the scanner Worker is off, but the scanner Worker itself only boots with the env flag on. ## Recovery ownership workflow

**Recovery ownership workflow:** every open DLQ row gets a paired `recovery_items` row (one per `(orgId, deadLetterId)`) tracking `owner` + closed-enum `severity` (`p1`/`p2`/`p3`/`p4`) + `slaTargetAt` + closed-enum `status` (`open` → `acknowledged` → `in_progress` → `waiting_external` → `resolved`, with `reopened` for reflows) + closed-enum `resolutionReason` (`fixed_by_patch` / `rolled_back` / `upstream_fixed` / `accepted_loss` / `not_a_bug` / `sandbox_replay_succeeded`) + append-only `comments` jsonb (cap 200 via `MAX_COMMENTS_PER_ITEM`). **SLA defaults** in `@janusly/shared/src/recovery-item.ts` (`SLA_SECONDS_BY_SEVERITY`): p1=1h, p2=4h, p3=1d, p4=7d; overridable per item via `slaTargetAtOverrideIso` (capped 30 days). **Per-severity targets are org-configurable** via `org_configs.recovery.slaPolicies` — a JSON object of MINUTES keyed by `p1`..`p4` (empty default = the built-in map; partial map allowed, omitted severities keep their default; per-severity range 1..43200min = 30d, matching the per-item override cap). The scoped reader `getRecoverySlaSeconds(orgId)` (`orgConfigRepo.ts`; narrow single-row read, fail-open to defaults) merges the config over `SLA_SECONDS_BY_SEVERITY`; `defaultSlaTargetAt(severity, from, secondsBySeverity?)` takes the merged map (stays pure/zero-I/O) and `createRecoveryItem` / `acknowledgeRecoveryItem` / `escalateRecoveryItem` pass it (an explicit `slaTargetAtOverrideIso` still wins). Unconfigured (empty string) = byte-for-byte the built-in defaults. **State machine** enforced via CAS-style `UPDATE … WHERE status IN (allowed_pre_states)` in `packages/data/src/recoveryItemsRepo.ts` — mirrors `recordDecision` in `autoHealingRepo.ts:264-297`. CAS-loser transitions return HTTP 409 with `{ code: "recovery_item_transition_invalid", currentStatus }` so concurrent operator-click vs auto-apply can't double-apply. **Idempotent creation** by `(orgId, deadLetterId)` unique index: `createRecoveryItem` is safe to call N times from the cluster-apply fan-out without dup audit rows or alert events (the result type carries `wasCreated: boolean`; only `wasCreated === true` writes the audit and dispatches the `recovery_item.created` alert). **The creator helper** lives in `packages/engine/src/recovery/recovery-item-hook.ts` (NOT `apps/api`) so BOTH the API and worker processes can register it via the `setRecoveryItemCreator` DI seam in `@janusly/data/src/recovery-item-creator.ts`. The worker is the primary DLQ writer — registering only in api would miss every worker-side insert. Same posture as the alert dispatcher: inline audit writes via `db.insert(auditLogs)` + `safePersistPayload`, never throws on the caller. **Auto-create toggle** per org: `org_configs.recovery.autoCreateItems` (default `true` for new orgs, opt-in per existing legacy tenant to avoid audit-row explosion on day 1 — backfill script is a follow-up). **Failure-storm debounce** (`org_configs.recovery.debounceWindowSeconds`, default 300, range 0..3600, `0` = off): before creating, `createRecoveryItemForDeadLetter` calls `findOpenRecoveryItemForDebounce` — when a still-open item (`status <> 'resolved'`) shares the `(orgId, workflowId, errorSignature)` key AND its `lastOccurredAt` is within the (engine-clamped to `[30,3600]`s) sliding window, the new DLQ row attaches as a `recovery_item_children` row (idempotent on the `(recoveryItemId, deadLetterId)` unique index — a replayed insert is a no-op) and bumps the parent `occurrenceCount` + `lastOccurredAt` instead of spawning a new incident. The window is anchored on `lastOccurredAt` (each occurrence refreshes it), and the error signature is persisted on `recovery_items.error_signature` as the match key (a signature-less failure can't be grouped and always creates). The attach path returns BEFORE `recordAlertEvent`, so a storm fires `recovery_item.created` once — alert deduplication operates over the parent for free; the `recovery.item.occurrence_attached` audit fires only when a child was actually inserted (no double-count on replay); a defensive guard skips self-attaching a parent's own DLQ row; the hook's never-throws posture holds (a debounce read failure degrades to creating the item). Children have NO independent lifecycle — resolving the parent closes the incident for every attached occurrence; `dead_letters` rows still persist 1:1 so cluster-apply + auto-healing (which cluster `dead_letters` by signature) are unaffected. The decision lives in the hook; the SQL (`findOpenRecoveryItemForDebounce` / `attachDeadLetterToRecoveryItem` / `listRecoveryItemChildren` / `countRecoveryItemChildren`) is in `recoveryItemsRepo.ts`; `GET /recovery/items/:id/children` (viewer, `recovery.read`, org-gated) backs the drawer's occurrence list. **Cluster-apply fan-out** (route `POST /dlq/cluster-apply` loop) creates a recovery_item per accepted DLQ row before enqueue. Replay acceptance leaves the incident open; the generation-matched terminal node-success transaction closes it with `resolutionReason: sandbox_replay_succeeded` and writes `recovery.item.resolved` atomically with the impact fact. `/dlq/replay` and bulk replay follow the same terminal-close rule. Manual `/dlq/resolve` is distinct: it closes immediately with `accepted_loss` because the operator explicitly dismissed the incident. **Eleven routes** in `apps/api/src/routes/recovery-items-routes.ts` — `GET /recovery/items` paginated (filters: `status` / `owner=me` / `severity` / `limit` / `cursor`), `GET /recovery/items/:id`, `GET /recovery/items/:id/children` (debounce occurrence list, viewer/`recovery.read`), plus 8 POST transition verbs (`acknowledge` / `in-progress` / `waiting-external` / `escalate` / `assign` / `resolve` / `reopen` / `comment`) under `permission: "recovery.write"` (`editor`/`admin` default — same key that already gated recovery-feedback writes; the three GETs are `recovery.read`). **Ten audit actions**: `recovery.item.{created,acknowledged,in_progress,waiting_external,assigned,escalated,resolved,reopened,commented,occurrence_attached}`; mutating verbs all carry `{ before, after }`. **Two new alert triggers** (extending the alert trigger enum): `recovery_item.created` (event-driven — fires inside `createRecoveryItemForDeadLetter` only on `wasCreated === true`) and `recovery_item.sla_breached` (state-driven — `scanRecoveryItemSlaBreaches` in `apps/api/src/alerts/scanner.ts` runs on the existing `*/2 * * * *` cron, reads `listOpenItemsWithBreachedSla(orgId)` = `status != 'resolved' AND sla_target_at <= now()`). Dedupe-key for the new triggers: `item:<deadLetterId>` and `sla:<itemId>` (NOT `sla:<deadLetterId>` — items can re-breach after reopen, so keying on itemId is correct). The web mounts `RecoveryItemBadge` inside `DeadLettersPanel`'s `we-list-row__meta` (severity pill cobalt→red for p4→p1, status chip, SLA timer with green/amber/red bands by % time remaining), and `RecoveryItemDrawer` (transition buttons enabled by current status, resolve sub-form with closed-enum reason select, comment textarea, escalate sub-buttons per remaining severity). Adding a new transition means: extend `ALLOWED_PRE_STATES` in shared + add a repo function via `applyCas(...)` + add a body schema + add a route + add an audit action + add EN/ES copy under `recoveryItems.action.*`; the CAS contract is the single source of truth.

## Recovery incident handoff

**Recovery incident handoff:** operator-driven cross-team dispatch of a `recovery_item`'s full context (severity, owner, error signature, recent comments, deep link) to one of four destinations: `slack` / `linear` / `github` / `webhook`. New route `POST /recovery/items/:id/handoff` (`role: "editor"`, `permission: "recovery.write"`, reuses the `"reports.deliver"` rate-limit bucket with default 60/min/org). Body validated via `HandoffRequestBodySchema` in `@janusly/shared/src/recovery-handoff` with per-destination `superRefine` (github requires `owner+repo`; webhook/linear require `url`; slack minimal). **The dispatcher** lives in `apps/api/src/recovery-handoff-dispatcher.ts` and routes through the shared per-tool `executeTool` invocation helpers in `@janusly/engine/src/integration-dispatch` (`callSlackPost` / `callGithubCreateIssue` / `callGithubAddIssueComment` / `callWebhookSend` — the SAME helpers `dispatchReportDelivery` AND the alert dispatcher use, so each tool's input-arg shape lives in ONE place) — slack via `slack.post`, github via `github.create_issue` (first call) or `github.add_issue_comment` (subsequent calls — the append-on-repeat branch), linear and webhook via `webhook.send` with `X-Idempotency-Key` header. Only the low-level invocation layer is shared; the dispatcher keeps its own result mapping (`externalId` / `externalUrl` / `commentId`), wall-clock latency, and error cap, which differ from the report-deliver envelope. All THREE callers of these tools (this handoff dispatcher, `dispatchReportDelivery`, and `packages/engine/src/alerts/dispatcher.ts`) now share the engine-side `integration-dispatch` helpers — the module lives in `packages/engine` so engine-side callers can import it (apps/api → engine is the established direction; engine never imports apps/api). The dispatcher NEVER throws; per-channel failures become `{ ok: false, error, latencyMs }`. **Idempotency** is enforced by the `recovery_item_handoffs` table — `(orgId, recoveryItemId, destination)` unique index makes `upsertHandoff` safe under concurrent operator clicks (Postgres serialises the INSERT ON CONFLICT). The `COALESCE(EXCLUDED.external_id, existing)` preserves the original GitHub issueNumber even when a later retry fails. **Slack cooldown** is the v1 substitute for thread-targeting (incoming webhooks are channel-bound — no Web API): if a `delivered` handoff exists within `SLACK_HANDOFF_COOLDOWN_SECONDS = 3600` (1h), the route short-circuits with 200 `{ alreadyDispatched: true, dispatchCount, lastDispatchedAt }` and audits `alreadyDispatched: true` — no second slack.post fires. v2 can move to Web API + `threadTs` when the demand justifies the auth flow. **GitHub append-on-repeat**: when the prior dispatch returned an `externalId` (issue number), the second call uses `github.add_issue_comment` instead of `github.create_issue` — the operator never spawns a duplicate issue, and the same UI panel surfaces both create + comment chains. `composeAppendMessage` re-composes the markdown with "Recovery item update (dispatch #N)" header to make the comment timeline readable. **Linear + webhook**: same dispatch path; `webhook.send`'s new optional `headers?: Record<string, string>` field (capped at 10 entries × 200 chars, CR/LF rejected — defense against header-injection via operator input) carries `X-Idempotency-Key: <recoveryItemId>:<destination>`. The receiver dedupes by that key; Janusly doesn't try to be smart about Linear's native API in v1. **Dry-run gate**: the route reads `runs.replayMode` for the run linked to the recovery item's `deadLetterId`; when it's `'validation'` the dispatch is skipped entirely (`{ ok: false, skipped: true, reason: "validation_run" }` response + audit row with `skipped: true`). Sandbox replays must NOT page the team channel. Four new audit actions: `recovery.handoff.{slack,linear,github,webhook}`; all carry `{ ok, statusCode, error, latencyMs, credentialName, idempotencyKey, dispatchCount, externalId, externalUrl }` — the env-var name behind the credential is NEVER echoed (same posture as `executeTool`'s `credential secret missing for <name>` envelope). Adding a new destination means: extend `RECOVERY_HANDOFF_DESTINATIONS` in shared + add the corresponding per-destination branch in `dispatchHandoff` + (if it's a webhook flavour) reuse `webhook.send`, otherwise add a new integration tool + add an audit action key + add EN/ES copy under `recoveryHandoff.destinations.*`. The idempotency contract is single-source-of-truth via the `recovery_item_handoffs` unique index — don't introduce a parallel state store for any future destination.

## Failure recovery patch surface

**Failure recovery patch surface:** `POST /ai/patch-workflow` (`role: "editor"` + `permission: "ai.write"`, stable alias `/v1/ai/patch-workflow`, rate-limited via the shared `"ai"` bucket) is the AI route the Recovery dialog calls. The route reads the failing node's type from `dlq.nodeJson.type`, picks one of ten per-type config envelopes via `patchEnvelopeForNodeType` (`apps/api/src/ai-schemas.ts`) — `AiPatchHttpConfigEnvelope` / `AiPatchToolConfigEnvelope` / `AiPatchAgentConfigEnvelope` / `AiPatchTransformConfigEnvelope` / `AiPatchConditionConfigEnvelope` / `AiPatchAiConfigEnvelope` / `AiPatchRouterConfigEnvelope` (also handles `router_llm`) / `AiPatchApprovalConfigEnvelope` / `AiPatchLoopConfigEnvelope` / `AiPatchGenericConfigEnvelope`. `multi_agent`, `human_form`, and `noop` intentionally fall through to the generic envelope — multi_agent's `agents` array is structurally too complex for v1, human_form is a resume-schema surface rather than a config-repair target, and noop has no actionable runtime config (empty patches trip the no-op guard). Each envelope wraps a `suggestions: Array<{ patchedConfig, rationale, approachLabel, confidence }>` with `min(1).max(3)` items — multi-suggestion is the only shape; single-suggestion responses are just an array of length 1. The http/tool/agent `patchedConfig` schemas are single non-union object schemas with leaf fields declared `.nullable()` (NOT `.optional()`). The http envelope's `headers` and the tool envelope's `input` use a bounded `Array<{ name, value: string | null }>` patch form (`max(20)` / `max(30)`) instead of an open `Record<string, ...>` (which OpenAI strict mode rejects via `propertyNames`). Transform `mapping` and loop `mapping` use the same array-of-pairs patch form. The merge layer in `apps/api/src/patch-workflow-merge.ts` folds each pair against the failing node's existing record (`PAIR_ARRAY_FIELDS_BY_NODE_TYPE = { http: ['headers'], tool: ['input'], transform: ['mapping'], loop: ['mapping'] }` scopes the fold per node type — generic-envelope nodes like `subworkflow` whose `config.input` is structurally different flow through verbatim); non-null `value` sets/replaces the key, `null` removes it, an empty array is a no-op preserving the existing record. Router `candidates` is an array but a verbatim-replace shape (no fold) — the LLM either replaces the full list or emits `null` to preserve. For `tool`-typed failures, the route enriches the prompt with `extraContext.toolInputContract` (the failing tool's `listTools()` entry: `name` / `description` / `required` / `optional` / `inputExample`) so the LLM has the exact required-field names instead of having to infer them from the runtime error message — closes the gap where the runtime error (e.g. "search is required") and the existing config's wrong key (e.g. `input.input`) would otherwise have the LLM emit field names that don't match the registered tool schema. This satisfies BOTH provider strict-mode contracts for the primary resilience patch path: Anthropic's compiled-grammar cap holds because each typed envelope has 3-7 leaf fields and the array is ONE repeated `items` constraint (not three branches), and OpenAI's strict-mode rule "every property in `properties` must be in `required`" holds because nullable-required is the fix (a `.optional()` field would be missing from `required` and OpenAI rejects). The generic envelope is best-effort for non-resilience node types until they get concrete provider-strict envelopes. Don't reintroduce a `discriminatedUnion` to a structured-output schema — `oneOf` is rejected outright by OpenAI strict mode and bloats Anthropic's grammar. The LLM emits ONLY the patched configs for the failing node (sending `null` for fields it doesn't want to change), each tagged with `approachLabel` (closed enum: `add_retry` / `raise_timeout` / `swap_secret_ref` / `add_approval` / `fix_url` / `other`) and a self-rated `confidence` 0-100. The route fan-out-merges each suggestion's `patchedConfig` into the original workflow snapshot after stripping nulls, validates each through the same `WorkflowSchema.safeParse` + `sanitizeAiWorkflow` chain `/ai/generate-workflow` uses, drops invalid suggestions, sorts survivors by confidence desc, and degrades to fallback when none survive. The route's response carries the new `suggestions: Array<{ workflow, rationale, approachLabel, confidence }>` AND legacy `suggestedWorkflow`/`rationale` fields mirroring `suggestions[0]` for back-compat — older clients reading just the legacy fields keep working. Audits both AI-mode and fallback paths as `ai.workflow.patch_suggested` with `envelopeKind` + `suggestionsCount` + `topApproachLabel` metadata. The patch helper (`packages/ai/src/patch-workflow.ts`) stays schema-agnostic — its `SYSTEM_PROMPT` instructs the LLM to emit 1-3 distinct alternatives ordered most-likely-fix first, with self-rated confidence and approachLabel. Per the AGENTS.md AI-fallback contract the helper never throws — null LLM / quota / network / schema mismatch all degrade to `mode: "fallback"` returning a single 0-confidence "other" item with the original workflow untouched. Don't bypass the sanitize step, the per-suggestion validation, or the audit row — all three are required for the AI-mutation invariant. **Release verification is Anthropic-only until explicit new direction**: smoke against `anthropic/claude-haiku-4-5-20251001` and expect `mode: "ai"` with a real structural diff on the failing node. OpenAI-compatible schema constraints may remain in code/tests for future expansion, but OpenAI smoke is not a shipping gate while the product is Anthropic-only. The recovery-matrix smoke (15 distinct failure shapes covering http / tool / transform / condition / ai / router / loop / approval-adjacent envelopes; `apps/api/src/recovery-matrix-fixtures.ts` + `scripts/seed-recovery-matrix.ts`) is the regression bed for the patch route — re-run it after any change to the envelopes, the merge layer, or the system prompt. Current observability target on Anthropic claude-haiku-4-5: ≥ 13/15 ai-mode rate, with each new envelope kind appearing in `audit_logs.metadata.envelopeKind` (the lone fallback was `write_side_without_approval`, now flipped to AI mode via the structural envelope described next). **Structural envelope (multi-node patches):** when the failing node is a write-side HTTP call (POST/PUT/PATCH/DELETE) AND has no `approval` ancestor in the upstream DAG, the route dispatches to `AiPatchStructuralEnvelope` (in `apps/api/src/ai-schemas.ts`) INSTEAD of the per-type config envelope. Dispatch reuses `isSensitiveAction` + `hasApprovalAncestor` exported from `packages/engine/src/workflow-readiness.ts` — the SAME rule that drives the production-readiness badge, so the readiness check and the recovery dispatcher can't drift. The structural envelope's suggestions emit `{ action: "insert_approval_upstream", approvalNodeId, approvalMessage, insertBeforeNodeId, rationale, approachLabel: "add_approval", confidence }` (single non-union object shape, provider-strict-safe — no `oneOf`, no `propertyNames`, no open `additionalProperties`). The `action` literal is the extensibility hook for future structural fix-classes (`split_for_retry`, `insert_error_handler`); v1 wires only `insert_approval_upstream`. The route swaps the helper's system prompt to `STRUCTURAL_PATCH_SYSTEM_PROMPT` (exported from `packages/ai/src/patch-workflow.ts`) which teaches the LLM the different output shape. Merge happens via `applyStructuralPatchToWorkflow` (in `apps/api/src/patch-workflow-merge.ts`) — pure function alongside `applyConfigPatchToWorkflow`: validates the target exists, rejects collisions with existing node ids, inserts a new `approval` node with `config: { message: approvalMessage }`, rewires every edge `to === insertBeforeNodeId` to flow through the new approval, and appends one outgoing `approval → target` edge. Multi-predecessor rewiring is comprehensive — no parallel-path bypass. The merged workflow re-validates through the same `WorkflowSchema.safeParse` + `sanitizeAiWorkflow` chain config patches use; invalid suggestions drop silently; all-invalid degrades to fallback. Audit metadata extends with `patchStyle: "structural" | "config_only"`. v1 covered HTTP write-side only; the dispatch gate now also opens for every `mcp_tool` node — every `mcp_tool` invocation is treated as write-side by default (the workflow JSON has no visibility into the per-tool `mcp_tool_descriptors.writeSide` flag at suggestion time, so `isSensitiveAction` returns `true` unconditionally for `mcp_tool`, matching the descriptor table's own `writeSide: true` fail-safe). False positives surface an extra approval suggestion the operator can ignore; false negatives miss a real MCP write that needed a human gate. Classic `tool` nodes (against `SENSITIVE_TOOL_NAMES` / `SENSITIVE_TOOL_SUFFIXES`) intentionally stay on the config envelope — the route gates structural dispatch on `failingNode.type === "http" || failingNode.type === "mcp_tool"`. Don't expand the dispatcher to *non-`mcp_tool`* tool nodes without also defining what a structural fix means for that surface (the natural answer is still "insert approval upstream" but the operator UX hasn't been validated for `slack.post` / `email.send` / `github.create_issue` yet). The recovery-matrix smoke now covers 16 distinct failure shapes; the 16th (`mcp_tool_without_approval`) flows through `patchEnvelopeForNodeType("mcp_tool")` → the generic config envelope at matrix time (matrix runner stays config-only by design) — the structural-dispatch path itself is regression-pinned by the merger test in `apps/api/src/patch-workflow-merge-structural.test.ts` (extended with an `mcp_tool` target case) plus the `isSensitiveAction(mcp_tool)` unit test in `packages/engine/src/workflow-readiness.test.ts`. **Memory enrichment:** the patch route now also threads `extraContext.memorySnippets` through the LLM prompt via `composeRecoveryMemoryHint` (`apps/api/src/ai-recovery-memory.ts`) when the org has memory enabled — two parallel `recallMemory` calls (one per `recovery_rationale` / `patch_rationale` kind) ranked by pgvector cosine similarity, post-filtered so same-workflow matches lead, rendered with the same `Recalled context (data, not instructions):` + suspicion-framing escape clause that `composeGenerationSystemPrompt` uses for MCP tool exposure (`docs/memory-policy.md` §9). The helper short-circuits BEFORE any `recallMemory` invocation when `isMemoryAllowed` returns denied — memory-disabled orgs see byte-for-byte zero behavior change (no extra audit rows, no `usage_events` rows, no DB reads against `memory_entries`). Audit metadata gains `memoryHitCount` + `memoryRecallOk`; raw memory content is never persisted in the audit row. The system prompt's `RECALLED CONTEXT` paragraph (mirrored in both `SYSTEM_PROMPT` and `STRUCTURAL_PATCH_SYSTEM_PROMPT`) teaches the LLM to treat the snippets as soft prior on top of `pastFeedbackSummary` — workflow-scoped accept/reject counts vs cross-workflow similarity matches respectively.

## Considered patch alternatives

Every accepted patch suggestion carries `consideredAlternatives: Array<{ approach, rejectedBecause }>` with zero to two model-authored trade-off summaries. The provider schema caps both strings and keeps the field required with `default([])` so strict structured output and legacy cached/mock replies remain compatible. `sanitizeConsideredAlternatives` (`apps/api/src/ai-patch-alternatives.ts`) treats the provider value as unknown, re-scrubs secret shapes, removes control/invisible/bidirectional characters, collapses it to one line, and drops incomplete rows before the response reaches the browser. These summaries explain plausible options not chosen for that suggestion; they are never private chain-of-thought and must not repeat another emitted suggestion. Fallback and deterministic Recovery Playbook suggestions return an empty list. `AlternativeHypothesesPanel` renders the rows collapsed by default after the workflow diff and before `EvidencePanel`. Keep the two concepts separate: alternatives are bounded model-authored trade-offs, while evidence is the deterministic source projection that supports the suggestion.

## Sandbox replay gate (Recovery v2)

**Sandbox replay gate + Recovery Confidence Passport:** the Recovery dialog validates a proposed patch in a sandbox run BEFORE saving. Flow: review → `POST /dlq/validate-fix` (`role: "editor"`, `"ai"` rate-limit bucket; runs `WorkflowSchema.safeParse` + `sanitizeAiWorkflow` then calls `DLQReplayAdapter.replayDeadLetterAsValidation`) → poll `GET /run?runId=…` until terminal → on `succeeded`, transition to a distinct `validated` review step and require an explicit operator click before `/workflows/save` + `/dlq/replay`; on `failed`/`cancelled`, surface the failed node's `errorJson` and let the operator iterate. Never collapse sandbox success and production apply back into one callback. Every review renders the deterministic Recovery Confidence Passport (`RecoveryPassportCard` + pure `evaluateRecoveryPassport`): failure signature/occurrences, suspect version, server-projected write-side and approval posture, sandbox status, evidence count, latest tenant-scoped terminal `auto_healing_runs` outcome for the same signature, and AI confidence as an informational-only fact. Stable verdicts are `safe_to_apply`, `needs_review`, and `unsafe`: fallback/no-op or sandbox failure is unsafe; an unvalidated, evidence-free, unknown-risk, or write-side patch needs review; only an evidenced read-side patch after sandbox success is safe. A write-side patch remains `needs_review` even after success because the explicit Apply action is the human decision. The API derives each suggestion's safety with the canonical `isSensitiveAction` + `hasApprovalAncestor` helpers; the web must not duplicate those rules. Sandbox runs carry `runs.replayMode = "validation"` (nullable on production runs) and a synthetic `workflowVersionId` (no `workflow_versions` row is written; the suggested workflow snapshot lives in `runs.inputJson`). The engine plumbs `NodeContext.dryRun` from `getRunMetadata(runId).replayMode`; HTTP executors skip non-safe methods and tool executors skip `writeSide: true` entries. Safe HTTP methods and read-side tools still execute. Production health/cluster repos filter `isNull(runs.replayMode)`. The polling effect claims the terminal path (`cancelled = true`) before yielding so concurrent polls cannot create duplicate transitions. Audited as `recovery.validation_started`. Don't add a write-side tool without `writeSide: true`. **Replay Lab is a sibling consumer of the same gate**: `POST /runs/replay-lab` (`editor`, `"ai"` bucket) creates a `replayMode="validation"` run from any source run via `replayRunAsValidation`; nested labs are rejected. Audit action is `replay_lab.started`. Comparison shape lives in `packages/data/src/runComparisonRepo.ts:getRunComparison`; `GET /runs/compare` is the viewer route.

## Evidence-gated Recovery Playbooks

**Recovery Playbooks:** `recovery_playbooks` is the single orphan-tolerant lifecycle table for manually promoted recovery procedures (`draft|active|retired`, versioned by `(orgId, normalizedSignature)`). Promotion through `POST /recovery/playbooks` (`editor` + `recovery.write`) accepts identifiers and bounded title/instructions only; the server resolves and verifies the org-scoped DLQ row, a successful `replayMode="validation"` run linked to its original run, a non-empty structural diff from the failed snapshot, the exact post-validation `workflow_versions` DAG, `dead_letters.status="replayed"`, and accepted `recovery_feedback`. Evidence JSON is assembled server-side and passes through `safePersistPayload`; no caller evidence or memory entry is trusted, and promotion never writes memory. Creation yields a draft. `POST /recovery/playbooks/:id/activate` is a separate audited action that retires the previous active match in the same transaction; retirement is always explicit except for a verified regression.

`GET /recovery/playbooks/match?deadLetterId=…` offers only an active exact `(orgId, workflowId, normalizedSignature)` match whose workflow is not soft-deleted and whose immutable source version still exists. `POST /recovery/playbooks/:id/use` is explicit and audited; it returns the source DAG as `mode:"playbook"` evidence but never saves or replays it. The dialog sends `recoveryPlaybookId` through the existing `/dlq/validate-fix` path, which rechecks the active match and exact source DAG before persisting the id in `runs.inputJson`. Every use therefore repeats the current sandbox and the separate production Apply click. Validation outcomes remain explicit, but production-use attribution does not trust the Apply request: the replay claim persists `{ recoveryPlaybookId, recoveryValidationRunId }` on `run_nodes`, and the generation-matched terminal-success transaction increments `successfulUses` plus writes `recovery.playbook.applied` beside the impact fact. The Applied UI stays pending until that terminal evidence exists. `POST /recovery/playbooks/:id/outcome` verifies the org-scoped validation run, DLQ linkage, embedded playbook id, and impact event; it is an idempotent confirmation/read-back path, not the source of production success. Atomic one-time timestamps on each validation `runs` row claim validation/apply accounting independently, so delayed duplicate outcomes remain idempotent even after newer uses; the playbook's `lastValidationRunId` and `lastAppliedValidationRunId` are observability pointers only. Failed/cancelled validation increments `regressions` and retires the playbook atomically; a passed sandbox increments `successfulUses` only after the exact production replay reaches terminal success. Promotion also proves causal order from validation to exact saved version to terminal DLQ recovery to accepted feedback, so stale earlier actions cannot satisfy the gate. Playbook feedback uses `suggestionMode:"playbook"` but omits `rawConfidence`, so deterministic reuse never pollutes AI confidence calibration. Lifecycle audit actions are `recovery.playbook.created|activated|retired|used|validated|regressed|applied`.

## Recovery before/after delta

**Recovery before/after delta:** `GET /workflows/health/delta?workflowId=…&afterVersion=…&windowDays=…&priorFailureSignature=…` (`role: "viewer"`) splits the same time window by version cutoff into a "before" and "after" side, calls `collectHealthSignals` once per side via the new optional `versionFilter: { side, cutoffVersion }` 4th argument (single new `lt`/`gte` predicate on the joined `workflow_versions.version`), and composes both sides through `computeWorkflowHealth`. ## Recovery feedback loop (operator → system)

**Recovery feedback loop (operator → system):** `POST /recovery/feedback` (`role: "editor"`, `"ai"` rate-limit bucket, audited as `recovery.feedback`) captures every accept/reject decision the operator makes in the Recovery dialog into the new `recovery_feedback` table (id / orgId / userId / deadLetterId / workflowId / suggestionMode / approachLabel / accepted / comment / createdAt; two indexes both leading with `org_id`). Body validated via Zod (closed `approachLabel` + `suggestionMode` enums); anonymous workflows (no saved id) are rejected with 422. The dialog writes a row at four moments: Apply success → `accepted: true`; Cancel from review or validation-failed → `accepted: false` with the chip text or free-text comment as the reason; Iterate from validation-failed → `accepted: false, comment: "validation_failed"` BEFORE re-entering generateSuggestion. Free-text comments run through `scrubSecretShapes` from `@janusly/shared/src/error-signature` at write time and are truncated to 2000 chars — defense-in-depth on the secret-leak invariant. The read path closes the loop: `/ai/patch-workflow` calls `summarizePastFeedback` (capped at 100 rows / 30-day window) → `composeFeedbackHint` (pure helper in `apps/api/src/ai-patch-feedback.ts`, ≤280 chars) and threads the result through `extraContext.pastFeedbackSummary`. The patch helper's `SYSTEM_PROMPT` includes one line teaching the LLM to treat the field as soft prior — prefer high-acceptance approaches for THIS workflow, deprioritize already-rejected ones, signal residual uncertainty via lower confidence and a rationale that addresses the prior pushback. Don't add a write tool that bypasses the dialog without also writing through `/recovery/feedback` — the labeled signal is what makes the loop *learn*, and silent dialog paths break that contract. **Memory-write side of the loop:** when the org has memory enabled (both flags), `/recovery/feedback` also commits a `recovery_rationale` `memory_entries` row on every `accepted: true` (always) and a `patch_rationale` row when the body carries the optional `rationale` field (the dialog passes it on the apply-success path). The route runs `isMemoryAllowed` FIRST and short-circuits BEFORE any `commitMemory` call so memory-disabled orgs see byte-for-byte zero behavior change — no `usage_events` row, no `memory.*` audit row. Memory commits go via `void Promise.allSettled([...])` AFTER `recordRecoveryFeedback` + the `recovery.feedback` audit have already succeeded; a `commitMemory` failure never breaks the feedback `{ ok: true }` response (the repo's own `memory.entry.failed` audit row captures the failure mode). Rejections (`accepted: false`) DO NOT commit memory by default — the catalog's `memory.allowedKinds` granularity supports adding rejection-capture later as a one-line change. **Confidence calibration rides on the same loop:** the dialog now persists the decided-on suggestion's `rawConfidence` (nullable `recovery_feedback.raw_confidence` column) on every accept/reject; a global `system:confidence-calibration` daily cron (`packages/engine/src/confidence-calibration-scheduler.ts`, env `JANUSLY_CONFIDENCE_CALIBRATION_CRON` default `30 1 * * *` UTC, never-throws, mirrors the retention sweeps) walks every opted-in org and fits a per-`(orgId, approachLabel)` linear curve (`packages/engine/src/confidence-calibration.ts` — pure math, `fitCalibrationCurve` buckets by raw confidence, weighted-least-squares, returns `null` below `MIN_CALIBRATION_SAMPLES=20` OR on a non-positive slope so calibration can NEVER invert suggestion ordering) into the new `confidence_calibrations` table (data repo `confidenceCalibrationRepo.ts`, audit `confidence.calibration.computed` per org per fire). `/ai/patch-workflow` reads the curves (gated on `org_configs.ai.confidenceCalibrationEnabled`, default true) and emits BOTH `confidence` (raw) AND `calibratedConfidence` per suggestion — the sort stays on raw so ordering is preserved; the dialog renders calibrated as primary with a "(model self-rated X%)" subtitle when they differ ≥10 pts (`CALIBRATION_SUBTITLE_DELTA`). Opt-out / <20-samples / no-curve all degrade to raw unchanged. Don't bucket calibration by anything other than `raw_confidence` (the AC's contract) and don't relax the positive-slope monotonicity guard.

**Learning-health visibility:** `GET /recovery/calibration-status` (`role: "viewer"`) returns only the org's calibration posture plus bounded stored curve metadata (`approachLabel`, accept rate, sample size, slope, intercept, last-computed time); it never exposes feedback comments. `GET /recovery/feedback-health?deadLetterId=…` (`viewer`) resolves the saved workflow from the caller's org-scoped DLQ row before returning the compact per-approach freshness state. The data layer persists that state in `recovery_feedback_health` (`(orgId, workflowId, approachLabel)` unique): `recordRecoveryFeedback` inserts the source decision and upserts the projection in one transaction, updating the accepted-fix timestamp only on acceptance and taking the greater timestamp in a conflict update so concurrent writes cannot regress the freshness clocks. The projection is intentionally not retention-managed, so an old workflow remains visibly stale after raw feedback rows expire instead of looking like a first-time workflow; the migration backfills existing source rows. `/ai/patch-workflow` includes this health snapshot as a best-effort additive response side channel — a tracker read failure never weakens the AI fallback contract. The Recovery Center's Model calibration tile and the dialog's per-approach learning badge render the locale-aware operator surface.

## Eval datasets from recoveries

**Eval datasets from recoveries:** accepted recovery decisions become a reusable regression bed ONLY with explicit opt-in. `recovery_feedback.eval_consent` (boolean, default `false`, threaded through `RecoveryFeedbackBodySchema` → `recordRecoveryFeedback` → `recovery.feedback` audit metadata) is the gate; an admin builds a dataset via `POST /eval/datasets` (`evals.write`, admin) and the build query `queryEligibleFeedbackForEval` (`packages/data/src/evalDatasetsRepo.ts`) filters `accepted = true AND eval_consent = true AND eq(orgId)` — no consent → never eligible. Two new `orgId`-scoped tables: `eval_datasets` (unique `(orgId, name)`) + `eval_examples` (self-describing SCRUBBED snapshot of failure signature + input context + expected `approachLabel` + retention metadata — durable so a `recovery_feedback` retention purge can't shrink a published dataset). `deleteEvalDataset` hard-deletes examples then the dataset (children first, cascade per the `workflow_versions` precedent). `scrubSecretShapes` runs at WRITE time (the repo, when an example is built) AND at READ time (`serializeEvalExamplesToJsonl` / `composeEvalExamplePrompt` in `@janusly/shared/src/eval-dataset.ts`) — defense in depth. Export is JSONL (one scrubbed object/line, `GET /eval/datasets/:id/export?format=jsonl|json`, dual-form Content-Disposition via the shared `report-download` helpers). When examples are surfaced to an LLM they are framed as DATA via `composeEvalExamplePrompt` (data-framed header + per-example `- ` list lines + the same suspicion-framing escape clause `composeGenerationSystemPrompt` uses for MCP tool exposure), NEVER as instructions. New permission category `evals` (`evals.read` viewer / `evals.write` admin); audit actions `eval.dataset.created` / `_deleted` / `_exported`; error codes `eval_dataset_not_found` / `_name_exists` / `_name_required`. v1 ships no LLM eval-runner (the dataset IS the regression bed; running it against the patch route is a follow-up) and no rejection-capture (only accepted+consented rows eligible).

## Cluster recovery apply

**Cluster recovery apply:** `FailureClustersCard` opens Recovery in cluster mode only for clusters with frequency ≥2 and DLQ samples. `GET /dlq/cluster-members` returns open DLQ ids whose normalized signature still matches the selected cluster, capped at 100. `POST /dlq/cluster-apply` is `role: "editor"` + `permission: "dlq.replay"`, rechecks every row's org scope/status/signature before replay, runs replay enqueues in series, marks accepted rows replayed, and writes one `recovery.cluster_apply` audit row per accepted row. Here `replayed` means queue acceptance only; it never closes downtime or the linked incident. The dialog must pass through the sandbox validation gate once on the representative before calling cluster apply; if the representative went stale, use the first still-open member instead. Don't bulk-replay closed rows or skip the per-row signature recheck. **Bulk resolve (multi-select dismiss):** `POST /dlq/bulk-resolve` `{ deadLetterIds }` (`role: "editor"`, ≤ `CLUSTER_MEMBERS_MAX_LIMIT`) is the dismiss counterpart to cluster-apply's replay — it loops `markDeadLetterResolved` + audits the existing `dlq.resolved` action (`metadata.bulk=true`, since each entry is a genuine single resolve) + `resolveRecoveryItemForDismiss({ via: "dlq_resolve" })`, returning a `{ resolved, failed, errors }` partial-success envelope (a not-found / cross-org id lands in `errors` without aborting the batch). The `DeadLettersPanel` drives it with the Flows-list multi-select idiom (a `dlq-select-toggle` mode → per-row checkboxes + `dlq-select-all` → a `.we-list-bulk-bar` over the same ticked set). **Bulk replay (multi-select retry):** `POST /dlq/bulk-replay` `{ deadLetterIds }` (`role: "editor"`, `permission: "dlq.replay"`, ≤ `CLUSTER_MEMBERS_MAX_LIMIT`) is the retry counterpart to bulk-resolve. Unlike `cluster-apply` it does NOT require the rows to share an error-cluster signature, so an arbitrary mixed-cause selection replays in one request — it loops `dlqReplay.replayDeadLetter` (the shared adapter) + `markDeadLetterReplayed` + audits the existing `dlq.replayed` action (`metadata.bulk=true`, since each entry is a genuine single replay); the linked recovery item stays open until generation-matched terminal success. The route returns a `{ replayed, failed, errors }` partial-success envelope. **Only `open` rows replay** — a non-`open` row is reported in `errors` so a batch can't double-enqueue downstream work (mirrors cluster-apply's status guard); a not-found / cross-org id lands in `errors` without aborting. No rate-limit for web callers (the 100-cap bounds it); all three production replay routes call `guardMcpWrite(auth, "dlq.replay")`, so MCP callers additionally require both consent flags and share the same per-tool Redis bucket. The bulk bar shows **"Replay selected"** (primary, the recover path) beside **"Resolve selected"** (secondary, accept-the-loss dismiss).

## Human-form recovery links

**Human-form recovery links:** a `human_form` node enters the same durable
`waiting` lifecycle as an approval, but its resume metadata carries a signed
org/run/node/purpose token and an input schema. New tokens sign `issuedAt` and
`expiresAt`; the tenant setting `runs.humanFormResumeTtlSeconds` is bounded to
300..604800 seconds and affects only links issued after the setting changes.
Legacy tokens without `expiresAt` retain their original fixed seven-day
boundary. `/resume` validates the binding, expiry, schema, and still-waiting
state before completing the node, so an expired, replayed, or cross-tenant link
cannot write output or enqueue downstream work.

## Recovery metrics rollup

**Recovery metrics rollup:** `GET /recovery/metrics?windowDays=…` (`role: "viewer"`) composes `collectRecoveryMetricsSignals` (`packages/data/src/recoveryMetricsRepo.ts`, 30-day window default, bounded parallel windowed queries with caps: 1k MTTR samples, 10k usage rows, 5k events) + `composeRecoveryMetrics` (`packages/engine/src/recovery-metrics.ts`) into the org-level Operations dashboard payload — recovery metric cards (success rate, MTTR, p95 latency, approvals pending, replay rate, SLA attainment, time to first action, fix durability, cost) each with `value` / `display` / `severity` / `rationale`. Severity bands are exported constants (`SUCCESS_RATE_BANDS` / `MTTR_BANDS_MS` / `LATENCY_BANDS_MS` / `APPROVALS_BANDS` / `REPLAY_RATE_BANDS` / `SLA_ATTAINMENT_BANDS` / `TIME_TO_FIRST_ACTION_BANDS_SECONDS` / `RECURRENCE_RATE_BANDS`) so future tuning lives in one place. Multi-tenant scope on every query (`eq(<table>.orgId, orgId)` direct or via `workflow_versions` join). `approvals pending` is current-state, not windowed — operators read it as "right now blocking", documented in the card's rationale. Cost is grouped in JS (not via PG JSON ops) — keeps the query plan identical to other repos and microsecond-cheap at the 10k cap. "Auto-fixes suggested/applied" + "rollbacks triggered" counters from the AC are deferred — they need new audit-log actions that don't exist yet; will plug in when the Recovery MVP ships the apply path. **Value Dashboard extension** lives in the same composer — additive `clustersResolved` metric (counts distinct failure signatures that flipped to `replayed` / `resolved` in the window via the new `queryFailureClustersResolved` query) + a `valueEstimate` block (`hoursSaved`, `dollarSaved`, `mttrDeltaSeconds`, `assumptions`) computed by the pure `estimateValueSavings(clustersResolved, mttrSeconds, assumptions)` helper. Assumptions come from three safe `org_configs` keys under the new `value` category: `value.hourlyCost` (default 50, range 0..2000), `value.minutesSavedPerRecovery` (default 30, range 0..480), `value.baselineMttrSeconds` (default 0 = sentinel for "operator has not measured a baseline yet"; range 0..86400). Formula `clustersResolved × minutesSavedPerRecovery / 60 × hourlyCost = dollarSaved`. **UI invariant: every dollar / hour surface MUST carry an "estimate" badge + tooltip linking to the assumptions** — the dashboard never claims accounting precision. The Markdown export (`GET /reports/value-dashboard?windowDays=N&format=markdown|json`, audited as `report.value_dashboard.exported`) writes the formula out plainly + lists the three knob values in an Assumptions section labeled "Estimate based on operator-supplied assumptions". The web `ValueDashboardSection` mounts inside `RecoveryCenterPanel` as a section (NOT a new tab); when `terminalRuns === 0` it shows a private-beta-pending fallback so the surface ships before any private-beta partner data lands. Don't extend `composeRecoveryMetrics` to accept additional non-`value.*` config without a matching catalog key + snapshot branch — the additive 3rd-arg signature is the chokepoint. **SLA attainment metric** (additive): `queryRecoverySlaAttainment(orgId, since)` aggregates in Postgres (`count(*) filter (where resolvedAt <= slaTargetAt)` over `recovery_items` resolved in-window) into a `slaAttainment` `RecoveryMetric` with exported `SLA_ATTAINMENT_BANDS` (green ≥90, amber ≥75, red <75). Empty (nothing resolved in-window) → `value: null` / neutral, NOT 0% — attainment of an empty set is undefined. It's surfaced as an SLA-attainment tile in the **Recovery Center metric strip** (`RecoveryCenterPanel`, reusing `VitalSignsTile` band coloring + `tRecoveryMetricRationale` — the sibling home of the replay/mttr tiles, not a bespoke `ValueDashboardSection` card) and a row in the `/reports/value-dashboard` markdown export. Rationale codes `sla_attainment.empty` / `sla_attainment.summary` follow the existing `recoveryMetricRationale.<code>` i18n chokepoint (EN/ES).

**Recovery effectiveness signals:** `recovery_items.first_action_at` is nullable and set once with `coalesce` on the first meaningful lifecycle transition, escalation, owner assignment, or operator comment; passive failure-storm attachment does not move it. Generation-matched terminal recovery fills a still-empty value from `dead_letters.replayClaimedAt` (historical `replayedAt`, then terminal time as fallbacks), so the reaction clock begins at the causal replay boundary without overwriting earlier human action. `queryTimeToFirstAction(orgId, since)` combines item samples with replayed DLQs that have neither a direct nor child incident, filters negative durations, and returns average, discrete p95, and sample size. Bands are healthy at ≤15 minutes, warning at ≤60 minutes, and unhealthy above that. Fix durability is derived from immutable `recovery_impact_events`, never from the mutable `resolvedAt` that reopen clears: one recovered incident is one trial, and a same-signature production incident or debounced child within seven days marks recurrence. Sandbox/validation runs never count. The UI reports the non-recurrence percentage (`held / recovered`, green ≥90%, amber ≥75%) and `/dlq/clusters` annotates matching signatures with `recurredAfterRecovery`; replay initiation is never a fix boundary. Keep the first-action and recurrence queries tenant-scoped and keep SDK/OpenAPI mirrors additive when their payload evolves.

**Terminal recovery impact ledger:** `dead_letters.status = 'replayed'` and its audit action mean the replay was accepted for enqueue; they are NOT proof that the failure was recovered. `claimReplayTransition` commits the node claim and the DLQ's opaque `replayClaimToken + replayClaimedAt` in one transaction BEFORE BullMQ can observe the job; outcome queries use `coalesce(replayClaimedAt, replayedAt)`, where `replayedAt` is only the historical fallback and operator-facing queue timestamp. A qualifying claim writes `{ recoveryDeadLetterId, recoveryRequestedBy, recoveryClaimToken, recoveryPlaybookId?, recoveryValidationRunId? }` on the matching `run_nodes` row and carries the opaque claim token in the slim BullMQ job. Runtime `queued → running`, retry, waiting, failure, and success transitions CAS against that generation; a queued/running node rejects another manual replay, and a stale worker that returns after the reaper plus a newer replay cannot mutate the row or credit the newer DLQ/operator. Exhausted ordinary-runtime failure is also atomic: the generation CAS, failed node, DLQ row, `node.failed`, and first `run.failed` transition commit together before post-commit SSE/alerts/recovery-item creation. Stalled-worker terminal failure uses a sibling atomic adapter: its `running` CAS, optional DLQ row, causal event, and parent-run failure commit together; invalid legacy snapshots terminate without a replay row rather than leaving half-persisted state. Only a generation-matched terminal node-success transaction may call `recordRecoveryImpactTx`: it validates the DLQ/run/node tuple, converges a still-`open` DLQ to `replayed` (repairing an API crash after enqueue without overwriting an explicit `resolved` dismissal), inserts one immutable `recovery_impact_events` fact keyed by `deadLetterId`, increments `recovery_impact_rollups`, CAS-resolves the direct recovery item or a debounced child's org-scoped parent, records a claimed playbook use, and writes the corresponding audits in the SAME transaction as `run_nodes.status = 'succeeded'`. An ordinary subworkflow completion is accepted only while the parent node still waits for that exact `stateJson.waiting.childRunId`; a recovered child uses the separate failed-node CAS described below, so a late old child cannot consume a newer recovery claim. Direct, bulk, cluster, manually accepted auto-healing, and supervised auto-healing replays carry a claim; generic run/node replays clear old claim metadata. Failed or in-flight replay attempts create no impact fact. `GET /recovery/ledger` reads the per-org rollup in O(1); `GET /recovery/my-wins?days=N` counts indexed impact facts for `auth.orgId + auth.userId` over a 1–90 day rolling window. MTTR, downtime-ended, replay outcomes, heatmap recoveries, resolved-cluster value, Markdown/JSON exports, and the UI ledger all use terminal impact events rather than enqueue status. Recovery Center celebrates all-clear only from a verified ledger increment or explicit accepted loss, buffers that signal until the independently fetched open count reaches zero, and polls the cheap ledger/wins/count projections every 10 seconds so terminal success for a background run is still visible. Historical reconstruction is deliberately outside Drizzle's transactional DDL migration: operators repeatedly run the bounded, idempotent `production-reconciliation.sql` batch after deploy; it pre-joins candidate audit evidence, inserts only missing events, and increments rollups only from `INSERT ... RETURNING`. Missing actor evidence contributes to organization value but not personal wins. Keep these reads event/rollup-backed and never put an unbounded backfill behind an `ALTER TABLE` migration lock.

**Recovered subworkflow reattachment:** ordinary child completion still CAS-matches a parent node that is `waiting` on `state_json.waiting.childRunId`; when a child replay later succeeds, the parent node may instead be `failed` and the run may be `failed` or already `running` because a sibling replay won first. `runs.parent_link_kind` distinguishes that executable `subworkflow` edge from trace-only `replay` provenance; the depth walker stops at replay boundaries, and validation parents propagate `replay_mode='validation'` into executable children so nested writes remain sandboxed without disabling child→parent completion. A failed parent still settles every exact waiting sibling failure before acknowledgement, so one replay cannot reopen around another child's unresolved wait; reopen eligibility also counts failed/cancelled child runs whose outbox delivery has not yet moved the matching parent node out of `waiting`. `reattachFailedSubworkflowNode` locks that parent run, CAS-repairs only the failed node whose `error_json.childRunId` matches the exact recovered child and whose child row is still succeeded, persists both output and child identity, and reopens a failed parent only when no sibling failures remain. That same transaction marks every still-pending parent row for durable readiness reevaluation before commit, because the last recovered sibling can unblock successors of an earlier one. Worker entry uses the same parent-run lock through `claimNodeForExecution`: if reattachment reopens first, the exact queued generation proceeds; if a worker consumes that generation while the run is still failed, the claim atomically restores the node to `pending` with its `attempt` and `recoveryClaimToken` intact for readiness repair. Every terminal executable child also owns a leased, millisecond-precision `runs.parent_notification_after` marker; recovery and parent reopening clear obsolete markers atomically, and the terminal reconciler retries and acknowledges the exact lease marker only after the parent CAS plus readiness or rollup settles. Reattachment emits `node.subworkflow.reattached` and, when applicable, `run.reopened`, but deliberately writes no second recovery-impact event: the child's generation-matched terminal success already owns the operator credit.

**Durable node queue publication:** every transition that makes a node executable persists `run_nodes.queue_publication_repair_after` before calling BullMQ and clears it only after Redis accepts the generation. Initial production, validation, Replay Lab, and sandbox generations commit their `queued` row, attempt, physical generation, and marker in the same transaction as the run. `run_nodes.queue_publication_generation` separates physical delivery identity from `(attempt, recoveryClaimToken)`: producer retries reuse the value, while a consumed failed-run delivery returns to `pending` and rotates it before a new publish. `execute-node` jobs use a deterministic SHA-256 id over `(runId, nodeId, attempt, recoveryClaimToken, publicationGeneration)`, so a retry cannot duplicate one publish and a required redelivery cannot collide with the old active/completed BullMQ job; execution still CAS-matches the attempt so legacy generation-zero jobs cannot claim a newer retry. `system:queue-publication-reconciler` runs once per minute, claims at most 500 compact due `pending`/`queued` rows under still-running parents with `FOR UPDATE … SKIP LOCKED` plus a two-minute lease, directly republishes exact queued generations, and loads, processes, and releases one distinct pending-run workflow snapshot at a time while rerunning DAG readiness. Retry markers become eligible only after their configured delay, so reconciliation cannot bypass backoff. The partial `run_nodes_queue_publication_repair_idx` keeps the sweep bounded; production builds it concurrently before the transactional migration. Pre-outbox API and worker processes are protocol-incompatible: production pauses ingress, drains the whole old fleet, applies the acknowledgement-gated concurrent rollout and migration, deploys the new fleet in full, then resumes. Do not clear the marker before successful `Queue.add`, publish node jobs without the deterministic physical-generation id, or replace the leased claim with an unbounded scan.

## Failure clustering

**Failure clustering:** `GET /dlq/clusters?windowDays=…` (`role: "viewer"` + `permission: "dlq.read"`) composes `collectFailureSamples` (`packages/data/src/failureClusterRepo.ts`, 30-day window default, 500-sample cap, parallel queries over `dead_letters` + failed `run_nodes`) + `clusterFailureSamples` (`packages/engine/src/cluster-failures.ts`) into a list of normalized failure clusters. Multi-tenant scope comes from persisted owner rows (`dead_letters.org_id`, `runs.org_id`); saved workflows left-join `workflow_versions` for names, and ad-hoc runs fall back to the persisted workflow snapshot. The DLQ writer carries `orgId` from run metadata, defaulting only as last resort. The pure normalizer `normalizeErrorSignature` (`packages/engine/src/error-signature.ts`) runs 7 first-match-wins rules — `secret_missing` / `http_error` / `network_timeout` / `ai_provider` / `parse_error` / `tool_input` / `unknown` — to produce a stable cluster label like `"Missing secret: GITHUB_TOKEN"` or `"HTTP 401 on http node"`. Hard safety property: **no secret value ever appears in a returned signature**. Every produced label passes through `scrubSecretShapes` (closed regex: `sk-…` / `ghp_…` / `github_pat_…` / `gh[ousr]_…` / `xox[baprs]-…` / `AKIA…` / `AIza…` / `Bearer …` / 3-segment JWT) before return — defense-in-depth on top of the safe-persist chokepoint that already key-redacts the JSON we read from. Free-form error MESSAGES escape key-redaction, so this final scrub is the last line of defence. `(runId, nodeId)` deduplication preserves the DLQ-source sample over the failed-`run_nodes` sample so a failed run that landed in DLQ counts once. The route registers BEFORE the wildcard `/dlq` dispatcher in the route registry — first-match-wins; reordering would silently break the cluster surface. Compute is on-demand per request; persistence and drift alerts are intentionally outside this read contract.
