## AuthContext is Janusly-resolved

**AuthContext is Janusly-resolved.** `auth.orgId` is produced by `resolveJanuslyMembership` in `apps/api/src/auth.ts`, and `auth.userId` comes from the provider-stable user id carried by the resolved principal. Four auth modes today: `janusly-session` (SSO-issued HMAC token in `x-janusly-session`, runs first in `PROVIDER_CHAIN` so a fresh SSO login beats a stale Supabase cookie), `supabase` (Bearer JWT), `service-token` (Bearer matches `API_SERVICE_TOKEN`), and `dev-headers`. Each mode is a private `extract*` function returning a module-internal `ProviderPrincipal`; the principal's `providerOrgHint` (the `x-org-id` request header wins, with Supabase JWT `user_metadata.orgId` as a backward-compat fallback) is treated as a SCOPE selector, not as authority. The grant is the `org_members` row. The Supabase / Janusly-session resolver order: (1) direct `org_members` row for `(hint, providerUserId)`; (2) legacy-orphan lazy backfill — when no UUID match but an `org_members` row exists with `userId` equal to the user's email (the placeholder we used before invite-acceptance shipped), rewrite the row's `userId` to the real UUID and audit `member.userid.migrated`; (3) no hint + exactly one membership for the user → silent default; (4) no hint + multiple memberships → return null (401 — forces the client to send `x-org-id`); (5) hint + email → try pending `invitations` row (`acceptInvitation` + `upsertMembership` + audit `member.joined` with `via: "invitation"`), then `verified_domains` row (`upsertMembership` with the row's `defaultRole` + audit `member.joined` with `via: "verified_domain"`), then `sso_connections` row with `status: "active"` → return null (the JIT seam — the SSO callback in `apps/api/src/routes/sso-routes.ts` upserts the `org_members` row BEFORE the resolver runs, so a properly-SSO-authenticated user arrives here at step 1); (6) otherwise null. Service-token preserves `providerOrgHint ?? "default"` (no implicit admin — `requireRole` still requires an `org_members` row to grant a role); dev-headers is unchanged (admin auto-grant only for `mode === "dev-headers"`). **Centralized auth policy evaluator** lives in `apps/api/src/auth-policy.ts` — both the membership resolver and the SSO callback call `evaluateAuthPolicy(input)` instead of inlining gate logic. The evaluator runs three policies in deterministic order (enforced-SSO → allowed-email-domains → MFA marker) and emits a single `auth.policy.rejected` audit row per rejection with `{policyKey, reason, mode, email?}`. Policies live in `org_configs.auth.*` (3 keys: `allowedEmailDomains` CSV with `allowEmpty: true`, `mfaRequired` boolean marker only, `sessionTtlSeconds` range `300..86400` default `28800`). The narrow `getAuthPolicyConfig(orgId)` repo function reads just those 3 keys via a single scoped `SELECT` so the resolver hot path stays cheap — never read the full `OrgConfigSnapshot` from auth code. Mode matrix: `service-token` bypasses all (infrastructure); `dev-headers` runs only enforced-SSO (no email); `supabase` runs all gates; `janusly-session` runs domain + MFA but NOT enforced-SSO (user just SSO'd) — the SSO callback calls the evaluator BEFORE `upsertMembership` so a domain policy fires even on Okta-authenticated users whose domains aren't in the org's allow-list. **Enforced-SSO**: when the org's `sso_connections` row has `enforced_sso: true`, the resolver rejects `supabase` / `dev-headers` modes (service-token + janusly-session pass); `ALLOW_DEV_SSO_BYPASS=true` is the explicit dev escape hatch — the gate fires outside production too, so a staging-on-prod misconfig fails closed instead of silently bypassing. **MFA marker** is informational only — Janusly stores the flag and warn-logs server-side when set, but enforcement is provider-side (Okta / Azure AD carry the claim, not Supabase). **Session TTL** is read by the SSO callback at issuance time from `auth.sessionTtlSeconds`; existing tokens keep their original expiry, only newly-minted ones use the new TTL. Adding a new auth policy means extending `getAuthPolicyConfig` + adding a branch to `evaluateAuthPolicy` + a catalog entry; don't sprinkle policy checks across route handlers. **WorkOS SSO flow**: `GET /auth/sso/start?orgId=X` (skipAuth) signs an HMAC state token (`signSignedToken` with `purpose: "sso_state"`, 10-min TTL, payload `{ orgId, nonce, callbackUrl }`), persists the nonce in `sso_state_nonces`, redirects to WorkOS; `GET /auth/sso/callback` (skipAuth) verifies the state HMAC + nonce (DELETE-and-check; replays fail) + callback URL binding, exchanges the code via `apps/api/src/workos.ts` (REST over `fetchHttpTarget`, pins `WorkOS-Version: 2024-07-01`, no SDK so the SSRF / body / redirect / timeout chokepoint applies), verifies `profile.connectionId === sso_connection.providerConnectionId`, upserts `org_members`, issues a session token (`purpose: "sso_session"`, 8-hour TTL, payload `{ orgId, userId, email }`), redirects to `${JANUSLY_WEB_BASE_URL}/auth/sso/complete#janusly_session=<token>`. The web (`apps/web/src/auth.ts`) extracts the URL fragment on boot via `consumeSsoSessionFragment` and strips it with `history.replaceState` so the token never lands in browser history. The web client (`apps/web/src/api.ts`) ships `x-janusly-session` when set (SSO mode), otherwise `Authorization: Bearer <supabase JWT>`, always with `x-org-id` from `localStorage["janusly:activeOrg"]`. `AuthProvider.updateOrg` writes only to localStorage — the Supabase `updateUser({ data: { orgId } })` call is gone. Adding a new auth provider is one new `extract*` function plus one entry in `PROVIDER_CHAIN`; if the provider has its own SSO-style provisioning, do it inside the extractor's path (or in a dedicated callback route like WorkOS) so the membership exists by the time the resolver runs. Eight audit actions land alongside SSO + policy: `org.sso.connection_added` / `_updated` / `_revoked`, `auth.sso.start`, `auth.sso.login`, `auth.sso.state_invalid`, `auth.sso.callback_failed`, `auth.policy.rejected`. Route handlers consume `AuthContext` only — they MUST NOT read provider-native claim shapes (Supabase `user_metadata.*`, raw service-token request bodies, etc.) for authorization decisions, and they MUST scope tenancy with `eq(<table>.orgId, auth.orgId)`. `AuthContext.source` is informational only — real consent gates (`isMcpWriteAllowed`) check server-controlled state (env var + `org_configs.mcp.writeConsent`), never `auth.source`. Supabase JWTs hardcode `source: "web"`; SSO sessions hardcode `source: "sso"`; service-token / dev-headers map `x-janusly-source: mcp` to `"mcp"` and otherwise default to `"service"` / `"dev"`. **Known intentional 401:** a brand-new Supabase signup with no `org_members` row, no pending invite, no verified-domain match, and no SSO connection gets 401 — was `orgId: "default"` pre-membership-hardening. An enforced-SSO org outside production with `ALLOW_DEV_SSO_BYPASS` unset also rejects every non-SSO mode. Dev mode (no Supabase, no SSO) is unaffected — dev-headers still target `default` directly.

## SCIM directory sync (WorkOS-backed)

**SCIM directory sync (WorkOS-backed).** `org_members` lifecycle for enterprise tenants is driven by inbound SCIM webhooks normalized through WorkOS Directory Sync. Schema lives in 6 tables: `scim_directories` (one per org, attached by admin via `POST /org/scim/directories` with a `defaultRole`), `scim_user_state` (per-`(directory, providerUserId)` mirror of IdP-side state, keyed by the stable WorkOS `directory_user.id`, carries the `email` join key into `org_members`), `scim_group_state` (group existence mirror — the anchor the group→role admin UI's group picker validates against), `scim_processed_events` (event-id idempotency keyed PK, `INSERT … ON CONFLICT DO NOTHING`), and the two group→role-mapping tables `scim_group_role_mappings` (operator-configured IdP-group → built-in-role mapping, unique `(scimDirectoryId, providerGroupId)`) + `scim_user_groups` (the user↔group membership join, unique `(scimDirectoryId, providerUserId, providerGroupId)`, maintained by the now-live membership events). The webhook receiver at `POST /webhooks/workos/directory` (skipAuth) verifies a Stripe-style `WorkOS-Signature: t=<unix-milliseconds>,v1=<hex>` HMAC-SHA256 over the raw body via `apps/api/src/workos-webhook.ts` against `WORKOS_WEBHOOK_SECRET` — missing / empty secret rejects every webhook (fails closed) with ±5 minute timestamp tolerance and constant-time hex compare. Org binding goes through `getScimDirectoryByProviderDirectoryId(directory_id)` (the ONLY un-scoped DB read in the SCIM module by design) — never trust the webhook payload's tenant claim. The pure dispatcher in `apps/api/src/scim-event-handler.ts` runs three idempotency / safety guards in deterministic order: (1) **replay** via `scim_processed_events`, (2) **out-of-order** via `scim_user_state.lastEventTimestamp` comparison, (3) **resurrection** — a `dsync.user.created` for a deactivated user with `created_at <= last_event_timestamp` is blocked with audit `scim.user.resurrection_blocked`. A genuine reactivation (newer timestamp) is allowed and audited with `metadata.reactivated: true`. SCIM-provisioned `org_members` rows go in with `userId = lower(email)` (the same legacy-orphan placeholder shape invitations use); the existing membership-resolver step-2 backfill rewrites `userId` to the real WorkOS profile id on first SSO login with no SCIM-specific code. SCIM event handlers always look up `org_members` by `(orgId, lower(email))`, stable across the rewrite. `allowedEmailDomains` policy (from ENG-100's `getAuthPolicyConfig`) applies at SCIM provision time (not just login) — out-of-policy domains audit `scim.user.provision_rejected` and never get an `org_members` row. **Membership-collision guard (fail-safe, never silently clobber):** both user paths read the target email's existing `org_members` row (`findMemberByEmail` dep) BEFORE writing, so a SCIM write can't overwrite a row that belongs to a different principal. Two predicates by path: **re-key** (`handleUserUpdated`, email change) blocks on ANY pre-existing row at the new email (it should be empty — also catches the cross-SCIM case where user A is re-keyed onto user B's own SCIM-owned row) → audit `scim.user.rekey_collision` and return `processed:false` with NO delete / overwrite / state-advance; **create** (`handleUserCreated`) blocks ONLY a human-invited row (`invited_by !== "scim:webhook"`, via the pure `isScimOwnedMembership` helper) → audit `scim.user.provision_collision`, while a SCIM-owned row at the same email is ABSORBED (proceeds) so directory re-attach / idempotent re-delivery / reactivation aren't broken (a genuine reactivation has no row — deprovision deleted it). Both guards return BEFORE any write, mirroring the resurrection / out-of-order early-return pattern; the refused event keeps its `scim_processed_events` dedup row (release is throw-only) so a re-delivery can't re-audit, and the operator resolves the conflict via the audit trail (`scim.user.*_collision`, visible + prefix-filterable in the audit panel). The asymmetry is intentional: absorbing SCIM-owned rows on create is required for re-attach, while re-key stays strict because the new email genuinely should be free; fully reconciling create by `providerUserId` (vs WorkOS's per-directory unique-email guarantee) is a deferred follow-up. **Per-group role mapping (v2):** a SCIM-provisioned member's role is now DERIVED from their IdP group memberships instead of the flat directory `defaultRole`. The pure `deriveScimRole(userGroupIds, mappings, defaultRole)` in `scim-event-handler.ts` picks the HIGHEST-rank built-in role (`viewer < editor < admin`, ranks local to the module — it does NOT import the DB-touching `permissions.ts`) among the groups the user belongs to that carry a mapping; with no mapped group it returns `defaultRole` — so an org with zero mappings configured is byte-for-byte the pre-v2 flat-role behavior (unknown / custom role names in a mapping rank as -1 and never win, falling through to `defaultRole`). Built-ins ONLY in v2 — mapping to a custom `org_roles` role is a v3 follow-up. The two no-op membership events are now live: `dsync.group.user_added` persists the `scim_user_groups` join row FIRST then recomputes the member role; `dsync.group.user_removed` drops the join row FIRST then recomputes (a removal may lower the role back toward `defaultRole`). A membership event arriving BEFORE the user is provisioned (no active `scim_user_state`) records the join row and audits `scim.group.membership_changed` with `roleRecomputed: false` but skips the `org_members` write — the later `dsync.user.created` derives the role from the already-present join row. Both user handlers (`created` / `updated`) run the same derivation in place of the old hardcoded `defaultRole`. `dsync.user.deleted` clears that user's `scim_user_groups` rows so stale memberships cannot survive reactivation; `dsync.group.deleted` captures affected users, deletes the group's join rows, then recomputes active members so roles derived from the deleted group drop immediately (orphan-tolerant best-effort — no FK). Admin CRUD lives at `GET /org/scim/group-role-mappings` (viewer) + `POST` create / `POST :id` update / `DELETE :id` (admin), all gated by `role:` only (matching the directory routes' convention); create validates the `role` is a built-in AND the `providerGroupId` exists in `scim_group_state` for this directory (rejecting typo'd / cross-directory ids), and rejects a duplicate `(directory, group)` mapping with 409. The admin UI ships as a "Group → role mappings" section inside `ScimDirectorySettingsPanel` (Operations → Access, admin-only), rendered only when an active directory exists: a group `<select>` picker populated by the read-only `GET /org/scim/groups` (viewer) — which lists the directory's synced `scim_group_state` rows via `listScimGroupState(orgId, scimDirectoryId)` so the operator picks a group by NAME, not by raw `directory_group_…` id — plus an inline per-row role `<select>` (update) and a remove button; the picker excludes already-mapped groups, and every mutation `bumpPlatformVersion()`s. A mapping change is lazy by default — it applies to each member on their next SCIM event — but an admin can apply it immediately via **bulk re-sync**: `POST /org/scim/resync` (admin) + the "Re-sync now" button in the mappings panel re-derive every ACTIVE member's role against the current mappings in one pass. The pure `resyncScimMemberRoles({ scimDirectory, deps })` (`apps/api/src/scim-resync.ts`, dep-injected + unit-tested like `handleScimEvent`) reuses the exported `deriveScimRole` (no logic fork), fetches the mappings map ONCE, loops `listActiveScimUserState(orgId, dirId)` (org-scoped, capped at `SCIM_RESYNC_MAX_MEMBERS = 5000`), and `upsertMembershipByEmail` per member WITHOUT `invitedBy` (so the original provisioning actor survives); per-user faults are isolated into a `skipped` tally. It writes only the SAME role the next event would produce (no new authority path) and returns `{ membersResynced, membersChanged, skipped, capped, changes[] }`. ONE `org.scim.resynced` summary audit row per sweep (not one per member — avoids log spam); the synchronous 5000-member cap is honest via the `capped` flag (a queue-backed sweep for larger directories is a follow-up). New repo modules `scimGroupRoleMappingsRepo` (`getScimGroupRoleMappingsMap` is the hot-path derivation reader) + `scimUserGroupsRepo`, both org-scoped. Webhook ALWAYS 200s on signature-pass + parseable JSON (regardless of guard outcome) so WorkOS doesn't retry guard-rejected events for hours; real I/O failures bubble to 5xx so WorkOS retries those. New audit actions: `org.scim.directory_{attached,updated,revoked}`, `org.scim.group_role_mapping_{created,updated,deleted}`, `org.scim.resynced`, `scim.user.{provisioned,updated,deprovisioned,provision_rejected,resurrection_blocked,rekey_collision,provision_collision}`, `scim.group.{synced,membership_changed}`, `scim.webhook.{signature_invalid,event_replayed,out_of_order,unknown_event,unknown_directory,unknown_user,directory_revoked,missing_directory_id,malformed_payload,malformed_timestamp}`. Adding a new SCIM event class means a new branch in `handleScimEvent` plus a fixture in `scim-event-handler.test.ts`; don't bypass the three guards. **Revoke is HARD-delete** (the `scim_directories` row goes away) so an admin can immediately re-attach a different (or the same) WorkOS directory id without manual DB intervention — the unique-on-`orgId` and unique-on-`providerDirectoryId` indexes would otherwise block re-attach. Audit history lives in `audit_logs` (`org.scim.directory_revoked`); the SCIM-provisioned `org_members` rows are NOT touched by revoke. **`org_members` join key for SCIM ops is `(orgId, lower(email))`, not `(orgId, userId)`**, because `userId` gets rewritten by the SSO callback's legacy-orphan backfill on first login. The dedicated `upsertMembershipByEmail` helper in `orgMembersRepo` does a SELECT-then-UPDATE-or-INSERT keyed by email to avoid duplicate rows after SSO rewrite. **Replay-row claim is released on dispatch throw** via `deleteProcessedEvent` — without this, a transient DB blip mid-handler would silently lose the event because WorkOS' next retry would see the dedup row and skip. Release is best-effort (a secondary failure is swallowed and the original error rethrows).
