# Auth & Identity (AuthContext resolver + SCIM directory sync)

## AuthContext is Janusly-resolved

**Identity and tenant authorization are separate boundaries.** Provider extractors in `apps/api/src/auth.ts` first produce a provider-neutral `IdentityContext` (`userId`, verified email when available, mode, source, and an untrusted organization hint). Bootstrap routes marked `identityOnly` may consume it before a tenant exists: `GET /auth/context`, `POST /organizations`, `POST /auth/invitations/accept`, and cookie-session organization rotation. The sole `optionalIdentity` route, `GET /auth/session`, may also run with no identity because it is a non-error discovery probe. Every tenant route continues to receive an `AuthContext` only after Janusly resolves an `org_members` grant. An organization hint selects a scope; it never grants one.

**Four provider modes remain in `PROVIDER_CHAIN`.** `janusly-session` runs first and reads the signed opaque id from the `janusly_session` HttpOnly cookie, then resolves a live, unrevoked `auth_sessions` row. `supabase` verifies a Bearer JWT. `service-token` compares a Bearer token in constant time. `dev-headers` is the explicit local-development path. Browser session rows carry user, normalized email, selected organization, expiry, and revocation state; no identity claims or reusable session credential are exposed to JavaScript.

**Membership resolution is the authority.** For Supabase and browser SSO principals, the resolver checks the hinted `(orgId, userId)` membership, performs the legacy email-placeholder migration when necessary, chooses the sole membership when no hint exists, and requires explicit selection when several memberships exist. A matching pending invitation is accepted atomically with the member grant, profile synchronization, and audit record. Verified-domain provisioning remains bounded by organization policy. The WorkOS callback persists its member grant before issuing the browser session. Service tokens receive no implicit admin role. Only `dev-headers` may receive the documented development fallback.

**Bootstrap is bounded and works before the first tenant exists.** `GET /auth/context` returns the global profile, at most `IDENTITY_MEMBERSHIP_LIMIT` organizations with each custom role's effective permissions, bounded pending invitations, the server-selected current organization, and explicit truncation/selection flags. `POST /organizations` transactionally creates an organization, owner membership, profile, and audit row for personal Supabase/dev identities. `POST /auth/invitations/accept` verifies the identity email and commits invitation acceptance plus membership atomically. `POST /users/me` updates the global profile through a tenant-authenticated route. The web `WorkspaceGate` owns organization creation, invitation acceptance, and organization selection before tenant data loads.

**Authorization has two independent layers.** `requireRole(minimum)` enforces the inherited rank (`viewer < editor < admin`) and `requirePermission(permission)` evaluates the selected organization's effective built-in/custom-role grants. When a route declares both, both must pass. The API registry is the enforcement boundary; the web consumes the effective permission list only to remove misleading navigation, buttons, forms, and keyboard shortcuts. Never infer an action from a role name or rank in the browser.

**Browser sessions are cookie-backed and revocable.** The WorkOS callback creates `auth_sessions` inside the same transaction as membership/audit, sends `janusly_session` with `HttpOnly; SameSite=Lax; Path=/`, and redirects to `/auth/sso/complete` without URL session material. `Secure` is inferred from `JANUSLY_WEB_BASE_URL` or forced with `JANUSLY_SESSION_COOKIE_SECURE`. The web uses `credentials: "include"`; it never reads or stores the cookie. `GET /auth/session` is an optional bootstrap probe and returns `{ authenticated: false }` with HTTP 200 when signed out, so an ordinary login-page load does not generate a browser error. `POST /auth/session/logout` revokes the server row and expires the cookie. `POST /auth/session/organization` proves membership, rotates the cookie envelope around the same active row, and preserves the original expiry.

**Cookie-authenticated mutations require explicit CSRF proof.** The dispatcher requires `x-janusly-csrf: 1` and an `Origin` accepted by `API_ALLOWED_ORIGINS` for every non-GET/HEAD request whose resolved mode is `janusly-session`. This complements `SameSite=Lax`; it does not replace route authorization. The logout route applies the same check before authentication because it must also clear invalid/expired cookies. CORS enables credentials and echoes only an allowed concrete origin. Do not add wildcard production origins for cookie-authenticated deployments.

**WorkOS SSO flow.** `GET /auth/sso/start?orgId=X` signs a one-time HMAC state token (`purpose: "sso_state"`, ten-minute TTL, payload `{ orgId, nonce, callbackUrl }`), persists the nonce, and redirects to WorkOS. `GET /auth/sso/callback` verifies state, consumes the nonce, checks callback binding and `profile.connectionId`, evaluates the organization policy, and atomically writes membership, audit, and browser session before redirecting. The WorkOS REST client continues through `fetchHttpTarget` so timeout, body, redirect, SSRF, and DNS-pinning controls stay centralized.

**Centralized policy evaluation** remains in `apps/api/src/auth-policy.ts`: enforced SSO, allowed email domains, MFA visibility, and `auth.sessionTtlSeconds` are resolved once through the narrow config reader. Service tokens bypass human login policies; dev headers run only the enforced-SSO policy; Supabase runs all applicable gates; a WorkOS callback evaluates domain/MFA policy before membership/session creation. Existing browser sessions retain their issued expiry when the tenant TTL changes.

**Lifecycle cleanup is isolated from tenant history.** The daily `system:identity-retention` maintenance job removes expired or sufficiently old revoked `auth_sessions` rows and expired one-time SSO nonces in bounded batches. `JANUSLY_IDENTITY_RETENTION_CRON` controls the schedule and `JANUSLY_IDENTITY_SESSION_RETENTION_DAYS` controls the post-expiry/revocation cleanup window. It deliberately does not delete `users`, memberships, runs, or audit history.

Route handlers must not inspect provider-native claims for authorization, and every tenant query must scope by `auth.orgId`. Adding a provider means one extractor plus an entry in `PROVIDER_CHAIN`; adding an account bootstrap route requires `identityOnly` and must not access tenant data without an independently proven membership.

## Unified local database boundary

The persistent local profile has exactly one PostgreSQL instance, owned by the
Supabase CLI. Supabase Auth owns `auth`; Janusly's Drizzle migrations and all
domain repositories own `public`. Migration, API, and worker containers receive
the captured local `DB_URL` only through the process environment and connect
through `host.docker.internal`; there is no Compose PostgreSQL service or
second domain database.

Normal startup is intentionally data-empty and never runs fixture scripts.
The browser begins with a blank untitled workflow. Provider qualification may
explicitly invoke `scripts/setup-local-smoke-fixtures.ts`, but that path is
owned by smoke commands and must never become a service dependency. Supabase
CLI telemetry is disabled by `scripts/local-stack.mjs`.

## Web auth loading boundary

The browser keeps provider code behind `apps/web/src/supabase-runtime.ts`, a
demand-loaded module reached only through the cached `getSupabaseClient()`
factory in `apps/web/src/auth.ts`. An unconfigured dev-header build returns
`null` before evaluating that dynamic import; a valid Janusly SSO session also
takes precedence inside `AuthProvider`, so the coalesced cookie probe,
organization rotation, listener, API requests, downloads, and streams never
initialize Supabase. Sign-out is the deliberate exception in a configured
build: after revoking the server session and expiring its cookie, it demand-loads
Supabase and calls its sign-out so a stale provider session cannot silently
authenticate the next reload. A configured Supabase
session loads the runtime during the normal App auth bootstrap, caches one
client, and retries the module import after a transient chunk failure.
`apps/web/src/api.ts` obtains only the current token through
`getSupabaseAccessToken()` and must not import or retain the client.
Keep the production performance regression that proves Home in dev-header mode
does not request `supabase-runtime-*.js`; a static Supabase value import or a
forced eager `manualChunks` vendor would violate this boundary.

## SCIM directory sync (WorkOS-backed)

**SCIM directory sync (WorkOS-backed).** `org_members` lifecycle for enterprise tenants is driven by inbound SCIM webhooks normalized through WorkOS Directory Sync. Schema lives in 6 tables: `scim_directories` (one per org, attached by admin via `POST /org/scim/directories` with a `defaultRole`), `scim_user_state` (per-`(directory, providerUserId)` mirror of IdP-side state, keyed by the stable WorkOS `directory_user.id`, carries the `email` join key into `org_members`), `scim_group_state` (group existence mirror — the anchor the group→role admin UI's group picker validates against), `scim_processed_events` (event-id idempotency keyed PK, `INSERT … ON CONFLICT DO NOTHING`), and the two group→role-mapping tables `scim_group_role_mappings` (operator-configured IdP-group → built-in-role mapping, unique `(scimDirectoryId, providerGroupId)`) + `scim_user_groups` (the user↔group membership join, unique `(scimDirectoryId, providerUserId, providerGroupId)`, maintained by the now-live membership events). The webhook receiver at `POST /webhooks/workos/directory` (skipAuth) verifies a Stripe-style `WorkOS-Signature: t=<unix-milliseconds>,v1=<hex>` HMAC-SHA256 over the raw body via `apps/api/src/workos-webhook.ts` against `WORKOS_WEBHOOK_SECRET` — missing / empty secret rejects every webhook (fails closed) with ±5 minute timestamp tolerance and constant-time hex compare. Org binding goes through `getScimDirectoryByProviderDirectoryId(directory_id)` (the ONLY un-scoped DB read in the SCIM module by design) — never trust the webhook payload's tenant claim. The pure dispatcher in `apps/api/src/scim-event-handler.ts` runs three idempotency / safety guards in deterministic order: (1) **replay** via `scim_processed_events`, (2) **out-of-order** via `scim_user_state.lastEventTimestamp` comparison, (3) **resurrection** — a `dsync.user.created` for a deactivated user with `created_at <= last_event_timestamp` is blocked with audit `scim.user.resurrection_blocked`. A genuine reactivation (newer timestamp) is allowed and audited with `metadata.reactivated: true`. SCIM-provisioned `org_members` rows go in with `userId = lower(email)` (the same legacy-orphan placeholder shape invitations use); the existing membership-resolver step-2 backfill rewrites `userId` to the real WorkOS profile id on first SSO login with no SCIM-specific code. SCIM event handlers always look up `org_members` by `(orgId, lower(email))`, stable across the rewrite. `allowedEmailDomains` policy (from `getAuthPolicyConfig`) applies at SCIM provision time (not just login) — out-of-policy domains audit `scim.user.provision_rejected` and never get an `org_members` row. **Membership-collision guard (fail-safe, never silently clobber):** both user paths read the target email's existing `org_members` row (`findMemberByEmail` dep) BEFORE writing, so a SCIM write can't overwrite a row that belongs to a different principal. Two predicates by path: **re-key** (`handleUserUpdated`, email change) blocks on ANY pre-existing row at the new email (it should be empty — also catches the cross-SCIM case where user A is re-keyed onto user B's own SCIM-owned row) → audit `scim.user.rekey_collision` and return `processed:false` with NO delete / overwrite / state-advance; **create** (`handleUserCreated`) blocks ONLY a human-invited row (`invited_by !== "scim:webhook"`, via the pure `isScimOwnedMembership` helper) → audit `scim.user.provision_collision`, while a SCIM-owned row at the same email is ABSORBED (proceeds) so directory re-attach / idempotent re-delivery / reactivation aren't broken (a genuine reactivation has no row — deprovision deleted it). Both guards return BEFORE any write, mirroring the resurrection / out-of-order early-return pattern; the refused event keeps its `scim_processed_events` dedup row (release is throw-only) so a re-delivery can't re-audit, and the operator resolves the conflict via the audit trail (`scim.user.*_collision`, visible + prefix-filterable in the audit panel). The asymmetry is intentional: absorbing SCIM-owned rows on create is required for re-attach, while re-key stays strict because the new email genuinely should be free; fully reconciling create by `providerUserId` (vs WorkOS's per-directory unique-email guarantee) is a deferred follow-up. **Per-group role mapping (v2):** a SCIM-provisioned member's role is now DERIVED from their IdP group memberships instead of the flat directory `defaultRole`. The pure `deriveScimRole(userGroupIds, mappings, defaultRole)` in `scim-event-handler.ts` picks the HIGHEST-rank built-in role (`viewer < editor < admin`, ranks local to the module — it does NOT import the DB-touching `permissions.ts`) among the groups the user belongs to that carry a mapping; with no mapped group it returns `defaultRole` — so an org with zero mappings configured is byte-for-byte the pre-v2 flat-role behavior (unknown / custom role names in a mapping rank as -1 and never win, falling through to `defaultRole`). Built-ins ONLY in v2 — mapping to a custom `org_roles` role is a v3 follow-up. The two no-op membership events are now live: `dsync.group.user_added` persists the `scim_user_groups` join row FIRST then recomputes the member role; `dsync.group.user_removed` drops the join row FIRST then recomputes (a removal may lower the role back toward `defaultRole`). A membership event arriving BEFORE the user is provisioned (no active `scim_user_state`) records the join row and audits `scim.group.membership_changed` with `roleRecomputed: false` but skips the `org_members` write — the later `dsync.user.created` derives the role from the already-present join row. Both user handlers (`created` / `updated`) run the same derivation in place of the old hardcoded `defaultRole`. `dsync.user.deleted` clears that user's `scim_user_groups` rows so stale memberships cannot survive reactivation; `dsync.group.deleted` captures affected users, deletes the group's join rows, then recomputes active members so roles derived from the deleted group drop immediately (orphan-tolerant best-effort — no FK). Admin CRUD lives at `GET /org/scim/group-role-mappings` (viewer) + `POST` create / `POST :id` update / `DELETE :id` (admin), gated by exact effective permissions (`members.read` for directory state, `org.config.write` for directory lifecycle, and `members.role_set` for group-role mutations and re-sync), with the declared role floors still applied as defense in depth; create validates the `role` is a built-in AND the `providerGroupId` exists in `scim_group_state` for this directory (rejecting typo'd / cross-directory ids), and rejects a duplicate `(directory, group)` mapping with 409. The admin UI ships as a "Group → role mappings" section inside `ScimDirectorySettingsPanel` (Operations → Access, admin-only), rendered only when an active directory exists: a group `<select>` picker populated by the read-only `GET /org/scim/groups` (viewer) — which lists the directory's synced `scim_group_state` rows via `listScimGroupState(orgId, scimDirectoryId)` so the operator picks a group by NAME, not by raw `directory_group_…` id — plus an inline per-row role `<select>` (update) and a remove button; the picker excludes already-mapped groups, and every mutation `bumpPlatformVersion()`s. A mapping change is lazy by default — it applies to each member on their next SCIM event — but an admin can apply it immediately via **bulk re-sync**: `POST /org/scim/resync` (admin) + the "Re-sync now" button in the mappings panel re-derive every ACTIVE member's role against the current mappings in one pass. The pure `resyncScimMemberRoles({ scimDirectory, deps })` (`apps/api/src/scim-resync.ts`, dep-injected + unit-tested like `handleScimEvent`) reuses the exported `deriveScimRole` (no logic fork), fetches the mappings map ONCE, loops `listActiveScimUserState(orgId, dirId)` (org-scoped, capped at `SCIM_RESYNC_MAX_MEMBERS = 5000`), and `upsertMembershipByEmail` per member WITHOUT `invitedBy` (so the original provisioning actor survives); per-user faults are isolated into a `skipped` tally. It writes only the SAME role the next event would produce (no new authority path) and returns `{ membersResynced, membersChanged, skipped, capped, changes[] }`. ONE `org.scim.resynced` summary audit row per sweep (not one per member — avoids log spam); the synchronous 5000-member cap is honest via the `capped` flag (a queue-backed sweep for larger directories is a follow-up). New repo modules `scimGroupRoleMappingsRepo` (`getScimGroupRoleMappingsMap` is the hot-path derivation reader) + `scimUserGroupsRepo`, both org-scoped. Webhook ALWAYS 200s on signature-pass + parseable JSON (regardless of guard outcome) so WorkOS doesn't retry guard-rejected events for hours; real I/O failures bubble to 5xx so WorkOS retries those. New audit actions: `org.scim.directory_{attached,updated,revoked}`, `org.scim.group_role_mapping_{created,updated,deleted}`, `org.scim.resynced`, `scim.user.{provisioned,updated,deprovisioned,provision_rejected,resurrection_blocked,rekey_collision,provision_collision}`, `scim.group.{synced,membership_changed}`, `scim.webhook.{signature_invalid,event_replayed,out_of_order,unknown_event,unknown_directory,unknown_user,directory_revoked,missing_directory_id,malformed_payload,malformed_timestamp}`. Adding a new SCIM event class means a new branch in `handleScimEvent` plus a fixture in `scim-event-handler.test.ts`; don't bypass the three guards. **Revoke is HARD-delete** (the `scim_directories` row goes away) so an admin can immediately re-attach a different (or the same) WorkOS directory id without manual DB intervention — the unique-on-`orgId` and unique-on-`providerDirectoryId` indexes would otherwise block re-attach. Audit history lives in `audit_logs` (`org.scim.directory_revoked`); the SCIM-provisioned `org_members` rows are NOT touched by revoke. **`org_members` join key for SCIM ops is `(orgId, lower(email))`, not `(orgId, userId)`**, because `userId` gets rewritten by the SSO callback's legacy-orphan backfill on first login. The dedicated `upsertMembershipByEmail` helper in `orgMembersRepo` does a SELECT-then-UPDATE-or-INSERT keyed by email to avoid duplicate rows after SSO rewrite. **Replay-row claim is released on dispatch throw** via `deleteProcessedEvent` — without this, a transient DB blip mid-handler would silently lose the event because WorkOS' next retry would see the dedup row and skip. Release is best-effort (a secondary failure is swallowed and the original error rethrows).
