## Live run streaming (SSE over Redis pub/sub)

**Live run streaming (SSE over Redis pub/sub):** `GET /runs/:runId/stream` (`permission: "runs.read"`) streams a run's `run_events` rows + run-status transitions to the web in real time, replacing per-connection DB polling. The engine is the single publish chokepoint: `packages/engine/src/run-event-stream.ts` exposes the `setRunEventPublisher` DI seam (`publishRunEvent` NEVER throws — streaming is best-effort telemetry, a publisher fault must not break the persistence write that precedes it) plus `createRedisRunEventPublisher({ publish, resolveOrgId })`, which centralizes the channel name `janusly:run-events:<runId>`, the `{ orgId, event }` message shape, and a bounded immutable `runId→orgId` cache. `appendEvent` publishes every event row (the SAME `safePersistPayload`-redacted object it persists — no secret reaches a subscriber that wasn't safe to persist), and the `succeeded`/`failed`/`cancelled` flips in `updateRunStatusFromNodes` / `cancelRun` publish an ephemeral `{ kind: "run.status", status }` signal. The signal has no cursor and is not replayed; reconnect reads the durable run status, while live delivery patches the web summary, hands terminal convergence to polling, and arms the stream's grace close. Both processes register a publisher at boot: the API (`apps/api/src/run-stream.ts`, reusing the request-path `redis` client for PUBLISH) and the worker (`packages/engine/src/run-event-redis.ts`, its own PUBLISH client; the worker is the load-bearing writer). **Org isolation is layered:** per-run channel (a run's `orgId` is immutable, so a cross-org subscriber is structurally impossible) + the route's `run.orgId === auth.orgId` gate before subscribing + the hub's `msg.orgId === subscriber.orgId` re-check before writing each frame. The API subscriber hub holds ONE dedicated ioredis subscriber connection (subscriber mode is exclusive — never reuse the request-path client), refcounts per-run channel SUBSCRIBE/UNSUBSCRIBE, and enforces a **per-replica** per-org connection cap via an in-process `Map` (default 50, safe `org_configs.runs.streamMaxSubscriptions`, range 1..1000, env `JANUSLY_STREAM_MAX_SUBSCRIPTIONS`; per-replica is correct — SSE connections are process-pinned, and a Redis counter would leak on crash with no natural TTL); over-cap connect returns 429. The route writes a 25s heartbeat comment (the API sets a 60s idle-socket timeout — without the heartbeat an idle run's stream dies), replays the `Last-Event-ID` gap with the existing `(createdAt,id)` keyset (the SSE `id:` is the composite `<iso>|<uuid>` cursor `parseEventsCursor` already understands), and arms a 30s terminal grace close. `closeRunStreamHub()` quits the subscriber connection on API shutdown. **The web uses `fetch` + `ReadableStream`, NOT native `EventSource`** — `EventSource` can't send the `x-org-id` / `Authorization` / `x-janusly-session` headers Janusly auth requires, and a query-param token would leak auth into logs; `openRunEventStream` (`apps/web/src/api.ts`) reuses the exact `api()` header builder and `useRunEventStream` (`apps/web/src/hooks/`) parses frames into the store via the merge path (`addEvents`, never `setEvents`). The existing 1.5s `/status` poll loop stays as the fallback: its tick is a no-op while `streamTransport === 'sse'` (read imperatively from the store — `streamTransport` is deliberately NOT a dep of the poll effect so a transport flip never tears the interval down and races the hook's `streamStatus` write) and resumes on any stream fault. The new store field `streamTransport` (`'idle' | 'sse' | 'polling'`) drives the `RunStreamChip` Live/Polling pill mounted in `RunsPanel` + the Operations header; the SSE hook owns `streamStatus='connected'` on first byte so the existing operator-online indicator stays correct. CORS `Access-Control-Allow-Headers` includes `x-janusly-session`, `Accept-Language`, `Last-Event-ID` so the cross-origin stream fetch + reconnect work in every auth mode. The legacy DB-polling `/events` route was removed (zero consumers). Don't add a new live-event source without going through `publishRunEvent` (engine) → the hub (API); don't reintroduce native `EventSource` on the web (the header-auth blocker is the reason).

**Reconnect ordering is lossless and bounded:** `addSubscriber().ready` is the ordering barrier — the route waits for Redis to acknowledge `SUBSCRIBE` before reading the database gap. Publications are buffered until catch-up completes, so a new live event cannot advance the browser cursor beyond older missing rows; a connection without `Last-Event-ID` performs the same bounded replay from the beginning to close the initial-empty-timeline race. Catch-up reads `STREAM_CATCHUP_MAX + 1` rows: at most 500 are emitted, and the sentinel row produces a named `catchup-truncated` frame before the response closes. `useRunEventStream` flushes that page into the sorted/deduped store, reconnects immediately from its newest composite cursor, and repeats until a page is complete; truncated pages are protocol progress, not transport failures, so they do not consume the four-failure retry budget. Replay writes wait for Node response `drain`; live frames waiting behind catch-up or backpressure share a 1 MiB per-connection queue, and overflow closes the stream because every persisted event remains recoverable by cursor. Post-header query/write failures close and clean up inside the SSE route rather than falling through to the JSON error dispatcher. After complete catch-up, the route re-reads tenant-scoped run status and reconciles statuses buffered during that query before emitting the snapshot. A terminal snapshot immediately switches the web to polling for final convergence, but the reader continues consuming SSE until the server's 30-second grace close so trailing cancellation/node events are not discarded.

### Stable agent reasoning event

`runAgentLoop` emits additive `agent.reasoning` rows after the existing `<scope>.step.planned` event for both single-agent and multi-agent scopes. The shared `AgentReasoningEventPayload` is the cross-process contract: `{ agent, iteration, planner, mode, scope, replacesEventId, decision, tool, reason }`; `replacesEventId` is the exact legacy planned-event id, so the operator timeline can deduplicate deterministically even when both inserts share a timestamp and random UUID ordering disagrees with insertion order. `reason` is a bounded, single-line, secret-scrubbed operational rationale (500 characters maximum), never raw prompt/context, recalled memory, tool input/output, provider error, final answer, or hidden chain-of-thought; a finish decision must carry `tool: null`. Keep the legacy planned event because `MultiAgentTimeline` still uses it. Streaming needs no special branch: `appendEvent` persists and publishes the safe canonical event through the existing SSE chokepoint, and the web fail-closed parser validates/scrubs the payload again before specialized rendering.

### Active-run observability

The bounded `GET /runs` page deliberately omits `inputJson`; selecting a row loads the full `GET /run` detail and merges `data.run` into that summary through `patchRunSummary`, preserving detail-only workflow identity and trigger input across later list refreshes. Both freshness paths update the same summary: every `/status` snapshot patches its full run row, while an SSE `run.status` signal patches the status immediately before terminal handoff to polling. Do not keep a second active-run object beside the bounded list — the merge helper is the single web reconciliation path, and the explicit `runId` argument remains authoritative over a payload's `id`.

Every ordinary root `startRun` now receives a UUID correlation id when none is supplied; subworkflows keep the inherited parent value, so the Runs overview can expose one copyable trace reference for the chain. Historical and adapter-created rows may still have `traceId = null`, so the UI must keep the trace fact conditional. Trigger input is projected from `inputJson.input`; never render the full captured workflow snapshot as if it were operator input.

Waiting metadata is classified at the executor (`approval`, `human_form`, `webhook`, `timer`, `subworkflow`) and the runtime stamps one `waitingSince` value into both `run_nodes.state_json.waiting` and the emitted `node.waiting` event. Timer waits also carry `wakeAt`. The web falls back to historical reason strings and `run_nodes.started_at`, but a subworkflow wait never offers manual resume: child completion is the only safe signal across that join boundary. Run event arrays are not order-stable across reads (`GET /run` is newest-first; streamed merges normalize oldest-first), so timeline projections sort by `(createdAt,id)` before computing deltas or choosing a terminal timestamp.

The Reasoning timeline is built for histories that grow beyond one page. `ReasoningPanel` sorts before delta calculation, displays newest-first, filters locally across event type, localized label, `nodeId`, and payload text, and can clear that filter + focus the chronologically first loaded `.failed` event. When `eventsHasMore` is true, count, no-match, and jump copy explicitly says **loaded events** rather than claiming a whole-history result. Its scroll owner remains mounted for data, empty, and no-match states. `useVirtualList` renders fixed 172px rows (164px card + 8px pitch), with payload content scrolling inside the card so expanded JSON cannot invalidate the window math; the labelled ARIA `list` reports each rendered `listitem`'s absolute `aria-posinset` / `aria-setsize` without promising the keyboard contract of `feed`. Filter changes reset scroll, while stable item keys preserve the first visible row and its intra-row offset when SSE prepends new events or older pages load. The jump action uses the hook's bounded `scrollToIndex` helper and programmatically focuses the revealed item.

The loaded-history diagnostics strip above that timeline is an honest projection of the **currently loaded event page**, never a whole-run claim. `summarizeRunDiagnostics` (`apps/web/src/run-timeline.ts`) reports loaded-event count, the span between valid timestamps, `node.retry`, `node.failed`, `decision.made`, and the positive integer episode counts carried by `agent.memory.recalled`; when `eventsHasMore` is true the UI labels the projection as partial. A separate resource-usage card calls contracted `GET /run/usage?runId=` (`permission: "runs.read"`) and projects persisted `usage_events` for the whole run: LLM calls, input/output/total/cache tokens, known cost plus unknown-price calls, and generic memory recall/commit/failure counts by kind. Every run-triggered recall caller forwards `runId`; otherwise its usage row cannot participate in this projection. `queryRunUsage` scopes by `(orgId, runId)`, orders newest-first, reads at most 10,001 rows, returns 10,000, and declares `truncated` plus `rowCap`; malformed/fractional token metadata contributes zero and safe-integer totals saturate instead of violating the v1 contract. The partial `usage_events_org_run_created_idx` supports that exact predicate/order. The web refreshes this projection when a node or run reaches a terminal checkpoint, aborts superseded requests, and never infers resource usage from event payloads. Router rows with a recorded `decision.made` event expose one localized What-if action backed by `GET /causal?runId=&eventId=&nodeId=` (`permission: "runs.read"`, tenant-scoped run lookup, exact event identity, bounded reads). The UI validates that wire response through `parseCausalReplay`, renders the deterministic candidate ranking rather than the route's English explanation string, aborts superseded requests, and discards stale results when the selected run changes. **Do not present this route on generic `condition` or `node.skipped` events:** the causal helper replays recorded router candidates only and cannot support a broader counterfactual claim without a new engine contract. Malformed responses fail closed into the localized retry state.

### Cross-run diagnostic history

The bounded `GET /runs` list remains the only history feed (100 rows by default, 200 maximum) and still omits the full `inputJson`. Its lightweight projection resolves `workflowId` as `coalesce(workflow_versions.workflow_id, runs.workflow_version_id)` and extracts only the captured workflow name from `input_json.workflow.name`. The `runs` predicate and the `workflow_versions` left join are both tenant-scoped, so an inconsistent cross-org version reference cannot disclose another tenant's workflow identity. The direct-ID filter fallback applies only when that join is absent; otherwise an accidental workflow-id/version-id collision across the two tables could misclassify a version-backed run. Optional `workflowId`, closed `status`, closed `runKind` (`production` means `replay_mode IS NULL`; `validation` means `replay_mode='validation'`), and strict descending `before=<createdAt>|<id>` predicates compose on this same capped query. Keep `(createdAt,id)` together in filtering and ordering so equal-timestamp rows never skip or repeat.

The Runs panel uses the shell's bounded page while filters are empty and performs a server read when workflow or status changes; it never presents a client-filtered first page as complete history. Its virtual scroll owner stays mounted through loading, error, and empty states because `useVirtualList` installs its observer and scroll listener once. A terminal non-success row with resolved workflow identity can open historical comparison. Baseline discovery is deliberately `workflowId=<id>&status=succeeded&runKind=production&before=<selectedCreatedAt>|<selectedId>&limit=1`; the production discriminator prevents a successful sandbox/replay from becoming the claimed prior-green baseline, and the cursor prevents any newer success from being selected. The dialog then reuses `GET /runs/compare` plus `RunComparisonView`; do not add a second comparison implementation or an unbounded history read.

## Queue pressure and Prometheus metrics

**Queue pressure:** the worker registers asynchronous gauges for both delivery lanes through independent, coalesced BullMQ observability readers with bounded retries and a hard read timeout: `workflow_queue_waiting_jobs` / `workflow_queue_active_jobs` and `maintenance_queue_waiting_jobs` / `maintenance_queue_active_jobs`. Neither reader reuses the canonical delivery connection whose unbounded retries are correct for job execution but unsafe for scrapes. Redis or malformed adapter values omit only that lane's scrape instead of affecting execution. API and worker also register `janusly_rate_limit_degraded_buckets` from their own process-local degradation tracker, so dashboards aggregate by the shared `service.name="janusly"` resource plus `service.instance.id` instead of assuming one global in-memory view. Prometheus startup is explicit after each process's migration check (`apps/api/src/index.ts`, `packages/engine/src/worker.ts`), with local defaults 9464 for API and 9465 for worker; both honor `OTEL_METRICS_PORT`, bind to loopback unless `OTEL_METRICS_HOST` explicitly opens another interface, fail startup on bind conflicts, and shut the exporter down during graceful termination. The API owns one bounded request-path reader and five-second cache per queue. Oldest waiting age is derived from BullMQ eligibility (`timestamp + original delay`), not raw creation time, so newly promoted approval/timer jobs do not appear overdue immediately. BullMQ does not retain the exact transition when previously processed work returns through retry or stalled recovery; those jobs therefore expose unknown age rather than deriving it from the earlier attempt start and publishing a false alert. Unauthenticated `GET /health` exposes only `queue: { degraded: boolean } | null`, combining the two lane thresholds without live details. Admin `GET /system/queue` preserves the workflow `{ waiting, active, oldestWaitingSeconds, warnSeconds }` fields at the top level and adds a nullable `maintenance` snapshot. `JANUSLY_QUEUE_LAG_WARN_SECONDS` defaults to 60; `JANUSLY_MAINTENANCE_QUEUE_LAG_WARN_SECONDS` defaults to 300; both accept 1..86400. Operations polls the admin projection on the existing 20-second infrastructure cadence and renders each lane independently. Never add queue counts, ages, Redis errors, or keys to public `/health`.

## Workflow health rollup

**Workflow health rollup:** `GET /workflows/health?workflowId=…` (`role: "viewer"`) composes `collectHealthSignals` (`packages/data/src/workflowHealthRepo.ts`, 30-day window) + `computeWorkflowHealth` (`packages/engine/src/workflow-health.ts`) into a single 0–100 score plus six per-category sub-scores: reliability (success rate − DLQ/retry penalties), safety (readiness fail/warn penalties), cost ($/run band), latency (p95 band), maintainability (declared outputs + multiple versions + approval node), AI risk (AI-node count + token volume + raw-secret findings). Weights and bands are constants exported from the engine module — tune in one place. Status thresholds: `≥80 healthy / ≥60 warn / <60 unhealthy`. Neutral default 80 covers brand-new workflows (totalRuns < 5 → reliability/cost neutral; p95 null → latency neutral) so an untested workflow isn't graded as if it were unhealthy. The repo's signal-collection queries enforce multi-tenant scope by joining through `workflow_versions` with `eq(workflowVersions.orgId, orgId)` AND `eq(workflowVersions.workflowId, workflowId)`. The `HealthSignals` type is defined in the data layer and re-shaped structurally in the engine to keep the dependency direction clean (engine → data, never the reverse) — adding a field means editing both definitions; engine tests plus TypeScript structural checks pin the contract. Compute is on-demand per request, not persisted; tracking score history / drift alerts is a future ticket.

## Workflow SLO policy

**Workflow SLO policy:** per-workflow reliability targets live in `workflow_versions.slo_json` (nullable JSONB). The closed-key Zod 4 schema + the pure `evaluateWorkflowSlo(slo, signals)` helper live in `@janusly/shared/src/workflow-slo` so both the engine and the web bundle can import without dragging Drizzle in. Schema fields: `successRatePercent` (0..100), `mttrSeconds` / `p95DurationMs` / `budgetBlocksPerWindow` / `stuckWaitingNodesMax` (int ≥0), `windowDays` (`7 | 14 | 30`); every threshold field is nullable so an operator can declare any subset, and SLO breaches do not fire when the threshold is null. `MIN_SAMPLE_SIZE = 5` suppresses success-rate / p95 breaches below that run count (mirrors `computeWorkflowHealth`'s neutral-default rule — a never-run workflow is untested, not breaching). `computeWorkflowHealth` accepts an optional `slo: WorkflowSlo | null` input; when present the breach booleans land on the response as `slo: { slo, breaches } | null`. **The breach booleans do NOT change the numeric health score** — the contract is an orthogonal surface consumed by recovery alert policies. v1 evaluates only `successRatePercent` and `p95DurationMs` against the already-shipped `HealthSignals`; `mttrSeconds` / `budgetBlocksPerWindow` / `stuckWaitingNodesMax` persist in the schema for forward-compat but their breach flags always return `false` until the corresponding signals are wired — adding signal coverage is a code-only change, no migration. **Data chokepoint** is `packages/data/src/workflowSloRepo.ts` (`getWorkflowSlo` reads the latest version, `setWorkflowSlo` writes the latest version in place and returns the prior SLO for the audit row). **Carry-forward is automatic:** the save chokepoint in `apps/api/src/workflows-save.ts` reads the prior latest's `sloJson` BEFORE inserting a new version row and writes it onto the new row, and `packages/data/src/workflowRollbackRepo.ts` mirrors the same carry-forward (rolling back the DAG does not roll back the reliability contract — the operator's current SLO survives). **Admin route** `POST /workflows/:id/slo` is the only writer; body validated via `z.object({ slo: WorkflowSloSchema.nullable() })`, `null` clears, every mutation audits `workflow.slo.set` with `{ slo, previousSlo, versionId }`. `/workflows/health` and `/workflows/health/delta` both load the SLO and pass it into `computeWorkflowHealth`. Don't introduce a separate SLO mutation path (the carry-forward + the single admin route are the chokepoint); don't change the numeric health score from SLO state (the contract is orthogonal). The web surface is the "SLO breach" pill in `WorkflowHealthBadge` plus the new `WorkflowSloPanel` mounted in the Inspector right panel — non-admins see the form but the server's `role: "admin"` rejects the write via the standard 403 toast envelope.

## Workflow snippets library

**Workflow snippets library.** Composable node+edge fragments an operator drops into the workflow being edited. Two flavours share `SnippetDefinition` (`@janusly/shared/src/workflow-snippets.ts`, zero-dep besides Zod): the eight BUILT-IN snippets live in CODE (`BUILTIN_SNIPPETS`, `builtin:<slug>` wire ids, `builtin: true`) and are NEVER persisted; org-private CUSTOM snippets live in the `snippets` table (unique `(orgId, name)`, `builtin` always false on rows). Closed `SNIPPET_CATEGORIES` enum (`retry`/`approval`/`error_handling`/`notification`/`transform`/`custom`). Insertion is the PURE `insertSnippet(workflow, snippet, targetNodeId?)` delta — mints fresh nanoid-shaped ids via `generateNodeId` (zero-dep `crypto.getRandomValues`; the repo has no `nanoid` dep, so this is the honoured form of the AC's "nanoid" intent), resolves id collisions against the existing graph (`resolveFreshNodeId`), remaps the snippet's internal edges to the fresh ids, and appends ONE stitch edge `target → entry` only when the operator selected a target (none otherwise). Never mutates inputs. Snippets do NOT run standalone — they only insert; the inserted workflow re-validates through `WorkflowSchema` downstream, so snippet node-type strings are intentionally not validated against `nodeTypeValues` inside the shared module (avoids a circular dep). Repo `packages/data/src/snippetsRepo.ts` scopes every read/write with `eq(snippets.orgId, orgId)`. Routes `apps/api/src/routes/snippets-routes.ts`: `GET /snippets` (`viewer`/`snippets.read`, concatenates built-ins AHEAD of custom rows), `POST /snippets` create + `POST /snippets/:id` update + `DELETE /snippets/:id` (`admin`/`snippets.write`, both reject a `builtin:` id with 409 `snippet_builtin_immutable` — built-ins are read-only), and `POST /snippets/:id/inserted` (`editor`/`snippets.read`) — an audit beacon that persists nothing (insertion is client-side; the workflow only persists on the next Save). Audit actions `snippet.created` / `_updated` / `_deleted` / `_inserted`. The web `SnippetInsertMenu` (Inspector "Insert snippet…" button + Cmd+K `action.insertSnippet`) applies the delta to the Zustand graph and fires the beacon. Adding a new built-in is one entry in `BUILTIN_SNIPPETS` plus EN/ES `snippets.builtin.<slug>.{name,description}` copy (gated by `apps/web/src/i18n/snippets-copy.test.ts`); adding a category means extending `SNIPPET_CATEGORIES` + a `snippets.category.<value>` key. Don't fork `insertSnippet`; don't let a built-in reach the DB.

## Solution packs

**Solution packs:** installable, ICP-shaped workflow starters live in code under `packages/solution-packs/` (`@janusly/solution-packs`); a pack is never a database row, and only the workflow version created by an install is persisted. Each `pack.json` is validated through `SolutionPackSchema` at module load and declares dependency hints, a workflow, sample inputs, and deterministic recovery fixtures. Installing never provisions credentials, secrets, or organization configuration. Public catalog responses expose bounded descriptors and omit the DAG, sample bodies, raw failure errors, and internal node ids.

The three bundled packs are production-shaped rather than presentation-only: each starts with `webhook_received`, declares a strict nested event input contract, exposes terminal outputs, uses schema-validated AI output, and sets `resultPolicy: "require_ok"` on every write-side tool. The incident pack gates GitHub creation on `classification.valid === true`; the support pack prefills the human review from the validated draft. Generic inbound delivery uses authenticated `POST /triggers/webhook/ingest` with an operator-known endpoint key plus a stable upstream `eventId`. Retries converge through `trigger_events`; conflicting selectors across active workflows return 409 instead of choosing one silently.

Five routes in `apps/api/src/routes/solution-packs-routes.ts` serve the catalog, dependency detail, copy-on-use installation, sandbox sample runs, and deterministic recovery drills. Sample runs use `replayMode="validation"`, so write-side tools are skipped. Reaching an approval or form still requires valid AI output and a configured supported provider; the strict template policy intentionally stops incomplete AI data before an external action. Direct failure fixtures seed a failed run and DLQ entry through `injectSampleFailure`; worker interruption uses `runStalledNodeDrill` and the real scoped stalled-node reaper. Every drill carries bounded source evidence and uses the production recovery ownership seam.

Package tests enforce unique ids, valid fixture targets, real inbound wiring, strict templates, AI schemas, write-envelope promotion, and catalog-wide failure-mode coverage. `apps/api/src/solution-packs-qualification.test.ts` runs the real workflow validator, production-readiness gate, and recursive input validator against every pack and sample. The web `packs` tab provides dependency status, installation, sandbox preview, and an accessible failure-scenario selector. Adding a pack requires one folder, one catalog entry, localized public copy, and green qualification tests. User-uploaded or marketplace packs and automatic credential provisioning remain out of scope.

## Onboarding ("first recovered run")

**Onboarding ("first recovered run"):** the guided checklist is **DERIVE-ON-READ**, not event-driven. The `onboarding_progress` table (unique `(orgId, userId)`) is a thin per-user CACHE — it persists only the high-water `step` (one of the closed `ONBOARDING_STEPS` in zero-dep `packages/shared/src/onboarding.ts`) + a `status` (`active`/`skipped`/`completed`) + skip/complete timestamps. The SIX advanceable milestones are derived LIVE on every `GET /onboarding` from durable org-state via `resolveOnboardingMilestones` (`packages/data/src/onboardingProgressRepo.ts`): `credential_configured` = a `credentials` row exists; `pack_installed` = an `audit_logs` row with `action='workflow.pack_imported'` (the only durable pack-provenance signal — `workflow_versions` has no `source` column); `first_run_succeeded` = a `runs` row with `status='succeeded'` (ANY run regardless of `replayMode`, so the sandbox sample-run demo advances); `failure_injected` = a `dead_letters` row; `recovery_applied` = a `dead_letters` row with `status IN ('replayed','resolved')` OR a resolved `recovery_items` row. `org_created` is always true once authenticated; `completed` is the aggregate. This means **ZERO event hooks** into the solution-pack, credentials, or DLQ routes or the engine (two milestones complete asynchronously in the worker, where a synchronous route hook can't reach them). The route in `apps/api/src/routes/onboarding-routes.ts` composes the ordered `milestones[]` (independent `done` booleans — `failure_injected` can precede `first_run_succeeded`; `currentStep` = first undone, a UI hint only), advances the high-water (monotonic — `advanceOnboardingHighWater` writes only when the index advances), and auto-completes via `completeOnboardingCas` (`UPDATE … WHERE status<>'completed' RETURNING *` so the `onboarding.completed` audit fires exactly once under parallel reads). A persisted `status='completed'` SHORT-CIRCUITS all derivation (so a large org pays nothing — and the deferred `runs(org_id,status)` / `audit_logs(org_id,action)` indexes aren't needed at onboarding scale). Idempotent create is `ensureOnboardingRow` (`ON CONFLICT (org_id,user_id) DO NOTHING` + re-select). `POST /onboarding` body `{ action: 'skip'|'resume'|'restart' }`: skip/resume are a CAS (skip from `active`, resume from `skipped`) auditing `onboarding.skipped` / `onboarding.resumed` only on a real transition; **`restart`** (`restartOnboarding`, unconditional from any status) replays the whole flow on the same tenant by stamping the `onboarding_progress.restarted_at` **epoch** — `resolveOnboardingMilestones(orgId, since?)` then windows EVERY derived signal to `created_at >= restarted_at`, so even a completed onboarding shows the banner again from step one and re-advances only on NEW activity (a new credential / pack / run / failure / recovery); audits `onboarding.restarted`. `org_created` stays done (always-true), the five timestamped milestones reset. New `onboarding` permission category (`onboarding.read` + `onboarding.write`, both viewer-default — per-user self-service); 4 audit actions; 1 error code (`onboarding_invalid_action`). **Tenant toggle:** `org_configs.onboarding.enabled` (new `onboarding` config category, default `true`) gates the whole feature per org — when `false`, `GET /onboarding` short-circuits to a hidden state (`enabled: false`, NO row create, NO derivation) and the banner renders nothing, so an admin can turn onboarding off once the team is past it (set via the existing `POST /org/config`). The narrow `isOnboardingEnabled(orgId)` reader (scoped single-key SELECT, fail-OPEN to `true` on a config-store blip) is the gate; flipping the toggle back on resumes from the org's derived progress. **AI-unavailable never deadlocks** — no milestone requires AI (pack install deterministic, sample-run AI nodes fall back, inject-failure + dlq.replay deterministic); the `aiAvailable` flag (`aiStatus(orgId).enabled`) is UX-only (drives the banner's manual-path copy), the guarantee is structural + pinned by a no-AI-key route test. **Secret posture:** `credential_configured` checks only row EXISTENCE, never a `secretRef`. The web `OnboardingBanner.tsx` is a self-fetching OVERLAY (mirrors `BudgetBlockedBanner`, NOT a new tab) mounted in `App.tsx`; it reads `/onboarding` on mount + every `platformVersion` bump (so it advances after any onboarding mutation without re-rendering App, which is deliberately not subscribed to `platformVersion`) and renders only while `status==='active'`. Adding a milestone means a new `ONBOARDING_STEPS` entry + a derivation read + an `ONBOARDING_STEP_TARGETS` target + EN/ES `onboarding.step.<step>.*` copy. Don't event-hook the engine for progress; don't make the high-water `step` the source of truth for the per-step display (it's a cache — the live derivation is authoritative).
