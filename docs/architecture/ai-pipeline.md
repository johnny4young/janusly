## AI integration

**AI integration:** every AI surface (`/ai/generate-workflow`, `/ai/explain-workflow`, `/ai/review-workflow`, `/ai/suggest-improvement`, `/ai/patch-workflow`, `/ai/explain-run`, the `agent` planner `"openai"`, the `ai` step type) routes through the provider-neutral `LlmClient` in `packages/ai/src/llm-client.ts` (built on the Vercel AI SDK). Env still supplies provider API keys; `org_configs` may override safe tenant-level provider/model/limits before the API or engine creates the client. The runtime registry still contains `openai` + `anthropic` for compatibility and future expansion, but **the supported operating posture for LLM completions is Anthropic-only until explicit new direction** (`anthropic/claude-haiku-4-5-20251001`) — Anthropic is the only provider that currently handles Janusly's structured-output grammar requirements; the set will broaden when other providers' structured-output support matures. **Embeddings and other non-completion AI surfaces are a separate concern** — they pick their provider based on capability + cost + self-host fit (the v1 embedding provider is self-hosted Ollama BGE-m3 per [`docs/memory-policy.md`](docs/memory-policy.md) §7; the `Anthropic-only` rule does NOT extend to it). Production deployments, tenant config, demos, evals, and release smoke for LLM completions should use `ai.provider=anthropic` / `JANUSLY_LLM_PROVIDER=anthropic` — and `anthropic` is also the code default when both are unset (the `resolveLlmConfig` env fallback and the catalog `defaultValue` agree with the posture), so a deployment that forgets the variable degrades loudly through the missing-key fallback path instead of silently routing completions to another vendor. Treat OpenAI / Mistral as unverified completion providers and do not switch a tenant's `ai.provider` or per-call model override away from Anthropic unless product explicitly re-opens that provider and a verification plan exists. The `constrained`-mode blocker on OpenAI is the `oneOf` strict-mode rejection on `/ai/generate-workflow`; `free_json` mode (the default) removes that structural blocker — no schema is sent to the provider, so generation is mechanically provider-agnostic — but the *verified* posture stays Anthropic-only — ENG-194 ran the OpenAI verification through the (now provider-aware) eval harness on 2026-06-10: gpt-4o-mini beat Haiku free-JSON on reliability (93% vs 87% ai-mode) at 1/12 the cost but lost 13% relative blind-judge quality, missing the pre-declared bar, so OpenAI stays unverified for generation; re-opening is a product decision (cost/quality trade-off) or a newer-model re-run. The patch route keeps provider-safe schema constraints for future compatibility, but OpenAI is not a supported runtime target right now. Per-call overrides go through the `model` field on workflow nodes / API request bodies: a bare id uses the configured provider; `"<provider>/<model>"` (e.g. `"anthropic/claude-haiku-4-5-20251001"`) overrides provider for that one call, but supported use is Anthropic-only until further notice. **Per-surface model routing:** the safe JSON-map config key `ai.surfaceModels` (keys validated against the closed `AI_SURFACES` enum = the six route slugs `generate-workflow` / `explain-workflow` / `review-workflow` / `patch-workflow` / `suggest-improvement` / `explain-run`; values are free model ids) lets an admin route each AI surface to a different model — e.g. patch/suggest on Sonnet while generation stays Haiku. The pure `resolveSurfaceModel(orgConfig.ai.surfaceModels, surface, requestOverride)` helper (`apps/api/src/ai-runtime.ts`) gives precedence `body.model` > per-surface default > global default, and all six routes thread the result as `modelHint`/`model` (patch + explain-run now read `body.model` too, for parity). The surface-model value is handed VERBATIM to the same chokepoint that routes `body.model`, so a bare id uses the org provider and `"<provider>/<model>"` overrides it; a mismatch (e.g. a Claude id on an OpenAI org) degrades through the AI-fallback contract, never breaks. Stays Anthropic-only by posture (model change, not provider switch — NOT enforced at config-set time; the value is a free model id keyed to a known surface). **Anthropic prompt caching:** the opt-in `cacheSystemPrompt` flag on `LlmGenerateTextInput`/`LlmGenerateObjectInput` (`packages/ai/src/llm-client.ts`) marks the system prompt as an Anthropic ephemeral cache breakpoint — when set AND the EFFECTIVE provider (post-`parseModelSpec`, NOT the configured default) is Anthropic AND a `system` prompt is present, the `system` field becomes a `SystemModelMessage` carrying `providerOptions.anthropic.cacheControl: { type: "ephemeral" }` (the AI SDK's documented caching idiom — `prompt` stays a plain string). Any other provider / flag-off path is byte-for-byte unchanged, so the breakpoint never reaches OpenAI. Four surfaces set it today: `/ai/generate-workflow` (threaded through `generateWorkflowFreeJson` / `generateWorkflowCandidates` / `repairGeneratedWorkflow` / constrained `generateObject`), plus `/ai/review-workflow`, `/ai/patch-workflow` (via `suggestWorkflowPatch`'s `cacheSystemPrompt`), and `/ai/suggest-improvement` (via `suggestWorkflowImprovement`'s `cacheSystemPrompt`) — each sends a static system prefix with the dynamic context in the user prompt. The generation win is repeated traffic against the same static system prompt (Best-of-N and cross-request calls both get provider-side cache opportunities, but parallel candidates are not ordered cache reads); review/patch/suggest are single-shot so their win is cross-request reuse within the cache window (valuable on the recovery loop where patch fires repeatedly). `/ai/explain-run` + `/ai/explain-workflow` are intentionally NOT cached — they have no static `system` field (the instruction is inlined in the user prompt), so caching them would need a prompt-structure refactor + eval re-run. The cache savings are provider-side and NOT $0-verifiable — unit tests pin the wire shape, the operator observes the cost/latency win live. Adding a new provider (Ollama, Mistral, Google) is a four-field entry in the `PROVIDERS` registry — no other code changes; see `packages/ai/README.md`. Every AI path has a deterministic fallback **and** wraps the SDK invocation in try/catch — on any failure (quota, rate, network, bad output, unknown provider, missing key for an override) the response stays `{ mode: "fallback", aiError: "<reason>", ... }` with the local content attached. Never break the fallback or remove the try/catch. `GET /ai/health` reports `enabled`, `provider`, and `model` reflecting the current tenant runtime config. `/ai/generate-workflow` lets free_json emit 13 node-type shapes the system prompt teaches the model to emit: `noop`, `http`, `transform`, `condition`, `ai`, `tool`, `agent`, `router`, `approval`, `human_form`, `loop`, `parallel_fork`, and `join` (in `constrained` mode the first 11 are a hard provider grammar cap — Anthropic rejects 12+; free_json validates the wider 13-branch `AiGenerationWorkflowSchemaFreeJson` server-side, so it emits `parallel_fork` / `join` directly while `constrained` stays at 11). Advanced/operator-only types still start as `noop` placeholders unless the free_json grammar emits them directly (`parallel_fork` / `join`) or Pass 2 has a wired deterministic/LLM-backed family (`wait_until`, `schedule`, uniquely matched exposed `mcp_tool`). Remaining operator-only types (`multi_agent`, `webhook`, `subworkflow`, `router_llm`, `agent_reflection`, trigger nodes) are promoted in the Inspector. `/ai/generate-workflow` generates in one of two modes selected by the safe `org_configs.ai.generationMode` key (`free_json` default / `constrained`; env fallback `JANUSLY_AI_GENERATION_MODE`). **`free_json` (default):** the model emits the workflow as JSON *text* via `llm.generateText({ responseFormat: "json" })` and the route parses it server-side through `parseGeneratedWorkflow` (`apps/api/src/ai-generate-freejson.ts`) — `JSON.parse` → `AiGenerationWorkflowSchemaFreeJson.safeParse` (the 13-shape free-JSON subset: the constrained 11 plus `parallel_fork` / `join`) → `sanitizeAiWorkflow`, with retry-on-parse-fail (`FREE_JSON_MAX_ATTEMPTS = 2`: blind re-sample plus a terse JSON-only nudge) before degrading to fallback. **Best-of-N:** when the safe `org_configs.ai.generationCandidates` key is `> 1` (number, default `1` = single-shot, range `1..5`, env fallback `JANUSLY_AI_GENERATION_CANDIDATES`), free_json generation samples N candidates in parallel (`apps/api/src/ai-generate-bestofn.ts:generateWorkflowCandidates`, unparseable replies dropped) and `selectBestCandidate` keeps the one with the fewest `checkWorkflowReadiness` issues (a `fail` weighs 10× a `warn`) — a deterministic $0 score, NOT an LLM judge; when none pass the strict `sanitizeAiWorkflow` gate it returns the first parsed draft best-effort so the repair pass still runs. The winner flows through the UNCHANGED Pass-2 promote → sanitize → repair tail; `candidateCount` rides the response + the `ai.workflow.generated` audit (success AND fallback), `validCandidates` rides the audit. Default `1` is byte-for-byte the pre-Best-of-N behavior (opt-in, no silent cost increase); `constrained` mode stays single-shot. **Cost-aware Best-of-N:** the effective candidate count is `budgetAwareCandidateCount(configured, budgetGate.envelope)` (`ai-generate-bestofn.ts`) — once monthly spend crosses the budget's WARNING threshold, N collapses to single-shot (deliberately binary: the warning threshold is the tenant's own "start being careful" line, and a graduated curve would muddy the sampled-count telemetry); no budget configured keeps the configured N, and the check reuses the envelope the route's budget gate already loaded (no extra read). **Few-shot exemplars:** when memory is enabled (both consent flags) AND `generated_workflow` ∈ `org_configs.memory.allowedKinds`, `/ai/generate-workflow` recalls the top 3 similar prior `prompt → workflow-shape` exemplars from the pgvector memory substrate and frames them as a DATA block (`apps/api/src/ai-generation-memory.ts`: `composeGenerationExemplars` recalls + renders header + `- Request: … → Shape: …` items + a suspicion escape clause re-scrubbed via `sanitizeMcpToolDescription`; `composeGenerationSystemPrompt` appends it so exemplars steer free_json, constrained, AND every Best-of-N candidate), and fire-and-forgets a new `generated_workflow` exemplar on success (`recordGenerationExemplar`: `content` = the prompt (embedding key), `metadata.workflowShape` = node-types + edge-count + output-keys ONLY via `summarizeWorkflowShape` — never config values). `exemplarCount` + `exemplarIds` ride the `ai.workflow.generated` audit (success AND fallback; ids only, never raw content). Embeddings are self-hosted (Ollama BGE-m3) → ZERO Anthropic cost and no extra LLM call; memory-off orgs are byte-for-byte unchanged (consent short-circuit BEFORE any recall/commit/embedding). The new `generated_workflow` memory kind (365-day retention) is text-only — no schema migration. An A/B eval (`scripts/model-eval-compare.ts`) showed free-JSON beats constrained on Haiku across reliability, judge-quality, AND cost — constrained decoding guarantees JSON *shape* but not graph validity, so ~30% of constrained outputs failed `validateWorkflow`. **`constrained` (legacy):** `llm.generateObject({ schema: AiGenerationWorkflowSchema })` uses the provider's structured-output path directly. Constrained validates against `AiGenerationWorkflowSchema`; free_json validates against `AiGenerationWorkflowSchemaFreeJson`. Both then run the same `promoteNoopPlaceholders` + `sanitizeAiWorkflow` tail; audit metadata carries `generationMode` + `generationAttempts`. If the parsed-and-promoted draft still fails strict graph validation, `repairGeneratedWorkflow` (`apps/api/src/ai-repair-workflow.ts`) feeds the structured validator issue codes and messages back to the LLM for up to two targeted attempts before the normal fallback path; `repairAttempts` lands in success and fallback audit metadata. The route still runs a small `sanitizeAiWorkflow` step (`apps/api/src/ai-runtime.ts`) that filters edge `condition` strings and `condition`-node expressions through `validateExpression` (Janusly's limited grammar). Don't drop the sanitize step — `WorkflowSchema` + `validateWorkflow` remain the runtime gate after AI generation; the engine's expression evaluator is stricter than Zod's `z.string()`. Schema-validation failures and sanitize throws both flow through the route's existing try/catch into `{ mode: "fallback", aiError, ... }`. **Two-pass promotion (Pass 2):** `/ai/generate-workflow` runs an optional second pass between Pass-1 generation (either mode) and `sanitizeAiWorkflow` via `promoteNoopPlaceholders` in `packages/ai/src/promote-noop.ts`. Detection is **id-prefix heuristic + multi-family lookup**: each wired family in `PROMOTE_FAMILIES` (`packages/ai/src/promote-noop.ts`) pairs a list of id prefixes with a typed target node type. Today three families are wired — `wait_until` (`wait_*` / `sleep_*` / `pause_*` / `delay_*`) and `schedule` (`schedule_*` / `cron_*` / `every_*` / `daily_*` / `weekly_*` / `monthly_*` / `hourly_*`), both LLM-extracted, plus the DETERMINISTIC `mcp_tool` (`mcp_*`, resolved by matching the noop id against the org's exposed MCP tools — no LLM call). Matching is case-insensitive and requires a non-alphanumeric separator directly after the prefix (so `wait_3_days` matches but `waiting_room` does not). When a noop matches a family, Pass 2 calls the corresponding typed schema (`AiWaitUntilConfigSchema` or `AiScheduleConfigSchema` — single-shape, provider-strict-safe: no `oneOf`, no `propertyNames`, no open `additionalProperties`) with the operator's verbatim prompt as the hint and flips the noop's `type` to the target with the typed config. The Pass-1 system prompt teaches the LLM the id conventions; we did NOT use a Pass-1 `config.promote` flag because the model empirically ignored that instruction and kept emitting empty configs — id-based detection is the reliable signal because descriptive ids are what the LLM picks naturally. Per-noop failures (LLM throws, schema rejects, whitespace-only duration, non-cron string, empty operator prompt) degrade silently — the offending noop stays unpromoted and the response stays `mode: "ai"` with `promotionsSucceeded < promotionAttempts` surfaced in `audit_logs.metadata`. Audit metadata also carries `promotionsByFamily: { wait_until: { attempts, succeeded }, schedule: { attempts, succeeded } }` so operators can see per-family exercise rates. Pass 2 fires N additional LLM calls (one per detected wait/schedule noop) against the same `"ai"` rate-limit bucket; the bucket is billed but Pass-2 calls are NOT individually gated. **Adding a new promotable family** means a new entry in `PROMOTE_FAMILIES`, a new schema in `promoted-schemas.ts`, a new helper paired with the schema, and a new `case` in the dispatcher inside `promoteNoopPlaceholders` (a DETERMINISTIC family like `mcp_tool` skips the `promoted-schemas.ts` schema — its helper resolves config without an LLM call, e.g. from route-supplied context threaded through `PromoteNoopInput`); the other 7 operator-only types (`multi_agent` / `webhook` / `subworkflow` / `parallel_fork` / `join` / `router_llm` / `agent_reflection`) stay noop-promoted in the Inspector for now. Don't relocate the call after `sanitizeAiWorkflow` — sanitize must validate the promoted workflow against the engine's strict `WorkflowSchema` + structural `validateWorkflow` gate; a node flip past sanitize would bypass that.

## Agent episodic memory

The `agent` / `multi_agent` loop (`runAgentLoop` in `packages/engine/src/node-registry.ts`) gets durable cross-run memory through `packages/engine/src/agent-memory.ts`, whose `recallAgentEpisodes` / `recordAgentEpisode` wrappers are the only engine path to the `agent_episode` kind in `recallMemory` / `commitMemory`. The LLM planner receives every registered runtime tool from `listPlannerTools()` rather than maintaining a second catalog; each entry carries its Zod-derived JSON input schema, and `{ dryRun: true }` removes registration-time `writeSide` tools before the model sees them (the executor's independent skip stays in place). The planner rejects a model-selected tool that was not in that offered catalog and degrades through the deterministic fallback. On completion the loop records one bounded goal + outcome episode. Only a configured LLM planner (`planner: "openai"`) recalls semantically similar prior episodes and injects the scrubbed results into a DATA-framed prompt block; the deterministic rules planner and an unconfigured LLM client skip recall entirely, so they incur no embedding call. The path honors the same two-flag memory consent (`JANUSLY_MEMORY_ENABLED` + tenant `memory.enabled`, with `agent_episode` in `memory.allowedKinds`), skips write-back in `ctx.dryRun`, and never throws from recall or commit. Do not bypass the shared memory substrate or weaken its prompt-injection framing and secret scrubbing.

After the planner returns the first successfully parsed `mode: "ai"` plan generated with a non-empty recall block, `runAgentLoop` appends `agent.memory.recalled` once. Its payload is deliberately content-free: `{ count, fingerprints }`, where each fingerprint is the first 12 hexadecimal characters of SHA-256 over the memory-entry id. The event is absent for rules planners, disabled/empty recall, recall failures, no-client fallback, budget blocks, malformed replies, and thrown LLM calls. Never add episode text, goal/outcome content, embedding data, or secret-bearing metadata to this event; it exists to prove that durable memory influenced an accepted AI plan without turning the run timeline into a second memory export surface.

## AI audit

**AI audit:** `/ai/generate-workflow` and `/ai/explain-workflow` write `audit_logs` rows on AI-mode success AND fallback (`ai.workflow.generated` / `ai.workflow.explained`) — generate-workflow audits the no-provider-configured branch and the parse-exhausted / SDK-error catch so AI outages stay visible in the trail. `/ai/review-workflow`, `/ai/patch-workflow`, and `/ai/suggest-improvement` likewise audit on AI-mode AND fallback (`ai.workflow.reviewed` / `ai.workflow.patch_suggested` / `ai.workflow.improvement_suggested`) per the AI-mutation contract — don't ship a new AI mutation surface that skips the fallback audit row. `/ai/suggest-improvement` is read-only by design (no DB mutation) but counts as a mutation surface for audit purposes because the operator picks one of the suggestions and applies it through the existing `/workflows/save` chain. Keep the audit when adding new AI endpoints.

## AI cost governance

**AI cost governance:** every LLM call site routes through `checkBudget` (`packages/engine/src/budget.ts`) before firing. The chokepoint contract lives in `@janusly/shared/src/budget-types` (`BudgetCheckResult`, `BudgetChecker`, `BudgetPolicy`) so `data` (production composer) and `engine` (DI seam) can both reference the shape without inverting the dep graph. Production checker is `productionBudgetChecker` in `packages/data/src/budgetRepo.ts` — it resolves workflow override → org config (`ai.budgetMonthlyUsd > 0`) → no-budget, then sums `usage_events.metadata.costUsd` for the current calendar month scoped to the resolved scope. Registered via `setBudgetChecker(productionBudgetChecker)` at api + worker boot (`apps/api/src/index.ts` + `packages/engine/src/worker.ts`). **Fail-soft posture identical to the rate limiter** — checker throws / Redis or DB blip → `{ allowed: true, monthlyUsdLimit: null }` with a `[budget]` warn log. An AI Studio outage during an infra blip is worse UX than a brief over-budget window. API-side gate is `gateBudget(input)` in `apps/api/src/budget-gate.ts`; called BEFORE `enforceRateLimit` on each of the 6 `/ai/*` routes (`generate-workflow` / `explain-workflow` / `review-workflow` / `patch-workflow` / `suggest-improvement` / `explain-run`). On `policy: "block"` + `allowed: false` the helper writes `billing.budget.exceeded` (never de-duped) and the route returns HTTP 402 with `{ error: "budget_exceeded", budget: <envelope> }`. On `warningThresholdCrossed: true` the helper writes `billing.budget.warned` de-duped per `(orgId, scope, workflowId, day)` and the route proceeds. Engine-side: the `ai` node executor (`packages/engine/src/node-registry.ts`) and the `agent` planner (`packages/engine/src/agent-planner.ts`) gate the LLM call too; block path returns `{ mode: "fallback", aiError: "budget_exceeded", response: <fallback content> }` for the `ai` node and a `done`/terminate decision with `aiError: "budget_exceeded"` for the planner — the AI-fallback contract holds in both. Three new `audit_logs` actions: `billing.budget.configured` (org-config + per-workflow writes), `billing.budget.warned` (de-duped), `billing.budget.exceeded` (every block). New routes: `GET /billing/budget?workflowId=` (viewer) for the Recovery Center Budget tile; `POST /workflows/:id/budget` (admin) for per-workflow override → `upsertWorkflowBudget` (`packages/data/src/workflowBudgetsRepo.ts`). Web admin lives in `BudgetSettingsPanel` (mounted in `OperationsPage` Reliability); the Recovery Center 5th tile (`BudgetTile`) shows MTD-spend bar with cobalt / amber / red bands; AI Studio CTAs show "(~$X.XX)" via the zero-dep `@janusly/shared/src/llm-pricing` helper (frozen `MODEL_PRICES` table + `estimatePromptCostUsd`); `BudgetBlockedBanner` (mounted in `App.tsx` overlay) surfaces the 402 envelope captured by `apps/web/src/api.ts` into `useWorkflowStore.budgetBlocked`. Don't bypass the `gateBudget` helper from a new `/ai/*` route — the audit + de-dup + 402 envelope are the contract. Don't call `llm.generateText` from a new engine path without a `checkBudget` call first — the AI fallback contract requires the block path to degrade gracefully, not throw.

## Prompt/model experiment harness

**Prompt/model experiment harness:** `POST /experiments/run` (admin, `evals.write`) A/B-compares a CONTROL vs a CANDIDATE (`kind`: `prompt` / `model` / `prompt_and_model`) against an `eval_datasets` snapshot. The route resolves each `controlRef`/`candidateRef` into a runnable arm — prompt refs (`"name@N"` / `"name"`) flatten through `resolvePromptRef`, model ids ride as `modelHint`, `prompt_and_model` splits on `::` — budget-gates via `gateBudget` BEFORE the run, rate-limits on the shared `"ai"` bucket, then calls `runExperiment` (`packages/ai/src/experiment-runner.ts`, DATA-AGNOSTIC — `ai` has no `@janusly/data` dep). The runner executes every example through both arms via `LlmClient.generateText` (each call writes a `usage_events` row through the existing LLM-client recorder chokepoint — no separate writer), catches per-side model throws as `aiError` + empty-output + score-0 (AI fallback contract; NEVER throws), and scores each side with a configurable scorer from `packages/ai/src/experiment-scorer.ts` (`string_equality` / `json_schema` — output validated against the expected JSON Schema, Zod-compiled / `llm_judge` — the judge degrades to deterministic token-overlap when the client is null OR the call throws OR the reply is unparseable). **PROMOTION IS RECOMMENDATION-ONLY** — the route NEVER writes to `prompts` / `prompt_versions` / `org_configs`; a favourable result (`scoreDelta ≥ MIN_SCORE_DELTA`) only writes an `experiment.run.promotion_suggested` audit row and stamps `summary_json.recommendation`. The summary is sanitized through `safePersistPayload` IN THE ROUTE before the jsonb write (`data` can't import `engine`). Three audit actions (`experiment.run.started` / `_completed` / `_promotion_suggested`); reuses the `evals` permission category; `experiments` table is orphan-tolerant (deleting the eval dataset leaves the summary snapshot intact). Adding a new scorer means a new branch in `scoreOutput` + a `SCORER_KINDS` entry; adding a comparison kind means an `EXPERIMENT_KINDS` entry + a `resolveArm` branch — don't add an auto-apply path without re-deciding the recommendation-only invariant.

## AI improvement suggestions

**AI improvement suggestions:** `POST /ai/suggest-improvement` uses `AiSuggestImprovementEnvelope` with `suggestions: Array<{ patchedWorkflowJson, rationale, approachLabel, confidence }>` and `min(1).max(3)`. Keep this 1-3 shape; single-suggestion responses are just an array of length 1. The model emits each full workflow as a JSON-stringified blob to stay below provider grammar caps, and the route must run every item through `JSON.parse` → `WorkflowSchema.safeParse` → `sanitizeAiWorkflow`, drop invalid items, sort survivors by confidence desc, and fallback when none survive. Don't replace this with a "one improvement" prompt or a nested typed workflow schema unless the provider grammar cap has been revalidated.

## AI evidence side-channel ("Why this suggestion?")

**AI evidence side-channel ("Why this suggestion?"):** `/ai/patch-workflow`, `/ai/explain-run`, and `/ai/suggest-improvement` responses carry `evidence: EvidenceRow[]` (always present, possibly empty) — a deterministic projection of the context the prompt composer already gathered, emitted as a STRUCTURED SIDE-CHANNEL with NO second LLM call. The closed shape + the read-time scrubber live in `packages/shared/src/ai-evidence.ts` (zero-dep beyond zod; web imports the `@janusly/shared/src/ai-evidence` subpath): six closed `EVIDENCE_KINDS` (`recovery_feedback` / `memory_entry` / `runbook_excerpt` / `recent_error` / `signature_rule` / `tool_contract`), `scrubEvidenceRow` / `scrubEvidenceRows` (re-run `scrubSecretShapes`, collapse control chars, cap fields, clamp `weight` to `[0,1]`, drop empty-snippet rows, bound the list to `MAX_EVIDENCE_ROWS`). The api-side assembler `apps/api/src/ai-evidence.ts` owns the SOURCE → row mapping: six PURE per-kind builders (`sourceRef` is the deep-link target — approachLabel / memory entry id / workflow id / run id / signature category / tool name) + three async orchestrators that fetch the two supplemental sources the routes don't already hold (`getWorkflowMetadata` runbook + `queryFailureSamples` recent errors — both best-effort, a read failure degrades that source to empty) and funnel everything through `scrubEvidenceRows`. The patch route threads `composeRecoveryMemoryHint`'s NEW additive `entries` field (the post-filtered recall entries) so memory evidence emits one row per recall WITHOUT a second `recallMemory` call. All three routes attach evidence on BOTH the AI and fallback paths and audit only `evidenceCount` (the scrubbed rows ride the response, NEVER the audit row). Multi-tenant: every source the assembler reads is already gated to `auth.orgId`; no builder touches `process.env` or issues a cross-org query — NEVER include cross-org evidence. The web `EvidencePanel` (`RecoveryDialog.tsx`) renders a collapsible "Why this suggestion?" `<details>` with one chip per row + a monospace `sourceRef` token, re-scrubbing each row via `scrubEvidenceRow` at render (defense-in-depth) and hiding entirely when empty. Adding a new evidence kind is one entry in `EVIDENCE_KINDS` + a new pure builder + an `evidenceKindLabel` branch + EN/ES `recoveryDialog.evidence.kind.*` copy; don't add a kind without a deterministic source already on the route (the no-second-LLM-call rule is the chokepoint).

## PromptOps registry

**PromptOps registry.** Org-scoped reusable prompts live in `prompts` + `prompt_versions` tables (multi-tenant via `eq(<table>.orgId, orgId)` on every query). The single chokepoint from `promptRef: { name, version? }` to a resolved prompt string is `resolvePromptRef` in `packages/engine/src/prompt-resolver.ts` — never inline a `db.select` from `prompt_versions` in a node executor or AI route handler; route through the resolver. Inline prompts continue to work (the `config.prompt: string` path on `ai` nodes, the hardcoded planner system prompt in `agent-planner.ts`, and the `*_SYSTEM_PROMPT` constants in `apps/api/src/ai-prompts.ts` + `packages/ai/src/promoted-schemas.ts` + `packages/ai/src/patch-workflow.ts`) — promptRef is additive, not a migration. The resolver runs two substitution passes: includes first (`{{include.Y}}` with DFS visited-set cycle detection + `MAX_INCLUDE_DEPTH = 8` defensive cap; cross-org includes are structurally impossible because the only DB read is `getPromptByName(orgId, name)`), then variables (`{{var.X}}` validated against the declared `variables` array on the active version — required-missing throws `MissingVariableError` BEFORE the LLM call so no tokens are spent). Version numbers are server-assigned (monotonic per `(orgId, promptId)`); clients never supply a version field. Pin-or-latest is the active-version policy when a `promptRef` omits `version`. Audit actions: `prompt.created`, `prompt.version_created`, `prompt.version_pinned`. Permissions: `prompts.read` (viewer+) + `prompts.write` (editor+). The `ai` node executor surfaces resolver failures as `mode: "fallback"` with `aiError: "<resolver_code>"` (AI-fallback contract intact); the `agent` planner silently falls back to its hardcoded system prompt on resolver failure so the agent loop continues progress.
